# slide の設計

HTML スライドを、いつもの制作環境から公開し、読む人がさわって確かめ、話した言葉といっしょに読めるサービスを作る。設計段階であり、ここにある機能は実装済みを意味しない。各機能の実装状況はトップページのラベルと [ストーリーマップ](story-mapping.canvas) で確認する。更新日 2026-11-10。

## 何のために作るか

スライドを、見るものから、さわって確かめるものにする。読む人に届けたいことは 2 つある。

- **さわる**: 発表者がデモに使った入力欄やスライダーが、読む人の手元でも動く。知らない人が作ったスライドでも、安心して開ける。
- **わかる**: スライドだけでは残らない、発表で話した言葉といっしょに読める。複数のデッキを順に並べたコースで学べる。

作るクリエイターには、次の 3 つを用意する。

- **いつものツールで**: HTML を出力するツールならどれでも、ビルド済みのファイルをそのまま公開できる。
- **公開の面倒は AI に**: ページごとの OGP 画像、ノートから記事の文章への整形、翻訳、読まれ方の解析を、サービスが肩代わりする。
- **学びに、お礼を**: 知を共有しあう循環を続けるために、コースを売ったり、良かったデッキに投げ銭を受け取ったりできる。

あわせて、コース販売・投げ銭と PRO・TEAM を通じ、SaaS の契約・決済・権限管理を一通り学ぶ。売れることの検証は、着手の条件にしない。

一方、利用場面を想像できない機能は作らない。各機能の採用理由は、誰が、どんな場面で困り、何をして、どうなればよいかで説明する。技術的に作れることだけを採用理由にしない。

## 読む順序

1. [ストーリーマップ](story-mapping.canvas)で、利用者の行動、各段階の対象機能・前提・完了条件を確認する。
2. マップにある機能名のリンクから、各 feature の具体的な利用場面と受け入れ条件を読む。
3. 実装を考えるときは [開発者向け設計](dev/index.md)を読む。

実装する範囲と順序はストーリーマップ内で管理し、一覧を別の文書に複製しない。

## 決まっている方針

- 受け取るのはビルド済みの静的ファイルだけ。ビルド方法は作者が手元や CI で用意する。
- 作者の HTML は sandbox 付きの iframe で、管理画面とは別の origin から配る。読む人のログイン情報や管理画面の操作に、スライドの JS を届かせない。
- AI の生成物(記事の下書き、翻訳、レビュー)は、作者が確認して公開を選んだものだけを読者に見せる。作者が自分で用意したものがあれば、そちらを優先する。生成クレジットは持たず、生成の回数や量の上限はプランと運用設定で決める。
- OGP 画像は作者の画像を優先し、ない場合は必要なページをサービスが撮影して保存する。
- 収益はコース販売と投げ銭の手数料、PRO、TEAM。販売と投げ銭には Stripe Connect を使う。
- 売るのはデッキを順番に並べたコースだけで、デッキ単体やページごとには売らない。無料で読めるデッキを選べる。
- デッキ単体には読者が都度決済で投げ銭を送れる。サービス内にポイントや残高は持たない。
- 作者が販売・一般公開を止めたり退会したりしても、購入済みの読者の閲覧は維持する。資料更新後は編集後の内容を提供する。
- PRO は独自ドメイン、大容量、閲覧分析。TEAM は PRO にチーム限定共有と SSO を加える。
- 初期は本人だけがアップロードし、小さい容量・頻度の上限から始める。上限は後から運用設定で変更する。
- Workers を使い、配信と保存の費用を抑える。公開管理とアクセス制御はキャッシュより前で行う。
- タテブログへの適用は、はてな・KADOKAWA の許可が整ってから。slide 単独の開発を妨げない。

## まだ採用しない案

[発表用と観客用の画面を分ける](features/f04-presenter.md)、[ページの説明を音声で聴く](features/f07-narration.md)、登壇動画と文字起こしの対応づけは、利用場面はあるがトップページで約束する体験に含めないため保留する。共同編集・コメント、pedit や Peitho Studio からの直接連携、GitHub のネットワークを使う SNS、遠隔発表同期も保留。具体的な利用者の場面と既存手段の困りごとが明確になった時点で feature にする。広告と広告収益還元、音声のプラットフォーム側生成は今回の方針から外す。
