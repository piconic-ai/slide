# slide の設計

登壇するエンジニアが、HTML スライドを置く場所を作る。置いた時点で公開後の手間が済んでいて、スライド同士が引用でつながる。一部は実装済みで、残りは設計段階。各機能の実装状況は、各 feature 冒頭の状態で確認する。更新日 2026-11-22。

## 何のために作るか

AI や作成ツールで HTML スライドを作るが、置き場を自分で作り込む時間はない登壇者のために作る。自作のスライドアプリを育てている人は、対象にしない。

第一スコープで提供するものは、2 つに絞る。

- **置いた時点で、公開後の手間が済んでいる。** 共有 URL、SNS のカード、ページごとの画像、安全な表示、ブログへの埋め込みを、作者の追加作業なしで用意する。
- **スライド同士が引用でつながる。** スライドの中のリンクを読み取り、引用している側とされている側を互いに表示する。

機能を入れるかどうかは、「登壇者の手間が減るか」で決める。作者に新しい作業(確認、入力)を求める機能は入れない。「置くだけで済む」という約束と食い違うためである。引用だけは、この基準の例外である。手間を減らす機能ではないが、リンクが生きている HTML スライドでしか成り立たず、作者の作業を増やさない。

登壇者の流れと、slide が受け持つことは、次のとおり。

| 場面 | 登壇者がしたいこと | slide が受け持つこと |
| --- | --- | --- |
| 前 | スライドを置く | HTML か zip を渡すだけで置ける([スライドを、ドロップして置く](features/f22-browser-drop.md))。AI エージェントからも置ける([AI エージェントから置く](features/f23-agent-upload.md)) |
| 前 | 公開前に確かめる | 置いた直後は作者だけが見られる。作者は、読者が見るのと同じ viewer で確かめ、そこから公開する([作者のみ限定公開で発表し、一般公開する](features/f02-publication.md)) |
| 当日 | その URL から発表する | 全画面表示とキーボード操作 |
| 当日 | 参加者が手元で開く | 別 origin の sandbox で動かし、安全に開ける([知らない人のスライドも、安心して開ける](features/f17-safe-viewing.md)) |
| 後 | SNS で共有する | 題名・説明・表紙のカード、ページごとの URL とその画像、共有メニュー([URL を渡して読んでもらう](features/f03-sharing.md)、[説明したいページを画像付きで共有する](features/f05-page-ogp.md)) |
| 後 | ブログに貼る | 記事の中でめくれる埋め込み([ブログに埋め込む](features/f25-embed.md)) |
| 後 | 直した版に差し替える | 同じ URL のまま新しい版にする。新しい版は viewer で確かめてから公開する([作者のみ限定公開で発表し、一般公開する](features/f02-publication.md)) |
| 後 | ほかのスライドとつながる | スライドの中のリンクから、引用を互いに表示する([引用でつながる](features/f24-citations.md)) |
| 後 | 発表で話したことを残す | 実況記事を書いて viewer のスライドの下に載せる([発表を書き起こした記事を添える](features/f26-article.md))。第二スコープで足す |
| 後 | 録画やブログを案内する | 関連リンクを足す([関連リンクを紐付ける](features/f27-related-links.md))。第二スコープで足す |

フォロー([気になる人を、フォローする](features/f21-follow.md))とお知らせ([知りたい出来事が、お知らせに届く](features/f20-notifications.md))は、既にある実装を使う範囲で残す。新しく広げるのは、一覧の公開と、ログイン中のトップに新着を出すことだけにする。

利用場面を想像できない機能は作らない。各機能の採用理由は、誰が、どんな場面で困り、何をして、どうなればよいかで説明する。技術的に作れることだけを採用理由にしない。

## 第二スコープ: 集まる場の基礎

第一スコープで、スライドは置くだけで共有できるようになった。ただ、発表の文脈(話した内容、録画、ブログ)は、まだスライドの外に散らばっている。第二スコープでは、スライドのページを「発表の周りにあるものが集まる場所」にする。作るものは 4 つで、どれも、スライド同士、人同士の「つながり」の元を増やす。

| 作るもの | 何が変わるか |
| --- | --- |
| 実況記事 | 作者が発表を書き起こした記事を Markdown で書き、viewer のスライドの下に載せる([発表を書き起こした記事を添える](features/f26-article.md)) |
| 関連リンク | 録画、ブログ、その他のリンクを、スライドに紐付ける([関連リンクを紐付ける](features/f27-related-links.md)) |
| プロフィールの引用 | プロフィールに、引用した・引用されたスライドの一覧と数を置く([引用でつながる](features/f24-citations.md)、[気になる人を、フォローする](features/f21-follow.md)) |
| メールでのログイン | GitHub でのログインをやめ、メールに送るワンタイムコードだけにする。GitHub を持たない人も作者になれる。プロフィールは本人が書く([メールのコードでログインする](features/f28-email-login.md)) |

AI エージェントは、記事の下書きと関連リンクを置ける([AI エージェントから置く](features/f23-agent-upload.md))。公開は、スライドと同じく人が押す操作にする。

第一スコープの基準は「登壇者の手間が減るか」で、作者に新しい作業を求める機能は入れなかった。記事とリンクは作者が書くものなので、この基準と食い違う。第二スコープでは、基準を次の 3 つにする。

1. **書かなくても完結する。** 記事もリンクも、無くてスライドは共有できる。置く流れに、入力を挟まない。置いた後に、したい人だけが足す。
2. **書いた分だけ、つながる。** 作者が足したものは、読者に見えるだけでなく、ほかのスライドや人とのつながりを生む。記事の中のリンクは、引用として数えられる。
3. **数を競わせない。** 引用は誉れとして見せるが、人を並べる順位や、数を増やすための仕掛けは作らない。一覧は新しい順に並べ、多い順には並べない。

第二スコープで作らないものは、次のとおり。

| 作らないもの | 理由 |
| --- | --- |
| イベントの紐付け、同じイベントの発表、イベントのページ | 第三スコープでコミュニティと合わせて設計する。「どのコミュニティの、どのイベントか」が分かることが本当に欲しいもので、URL を揃えるだけではコミュニティという単位が残らない |
| 動画の埋め込み | viewer の CSP を広げないため。リンクだけにする |
| リンク先の題名の自動取得 | 外のサイトへの問い合わせ、失敗、内部の URL を叩かせる攻撃への備えが要る。題名は作者が入れる |
| サービスによる記事の生成([話した言葉といっしょに読む](features/f15-talk-reading.md)) | 第二スコープでは、作者(または作者のエージェント)が書く部分だけを作る |
| 引用数の順位、「よく引用される人」の一覧、引用数のバッジ | 数を増やすための相互引用を生む |
| パスワードでのログイン、Google でのログイン | メールのコードだけにする |
| ログインをだれにでも開くこと | 利用規約とプライバシーポリシーに、メールアドレスの扱いをまだ書けていない。ログインは招待制のまま |
| メールアドレスの変更の画面、受信箱を失ったときの戻し方の画面 | 問い合わせ(helpdesk)で個別に対応する |
| 記事でページの画像以外の画像を使うこと | アップロードと保存が要る。ページの画像で足りる |
| 記事を読む間、スライドを横に追従させること | viewer の iframe の扱いの判断が要る |
| 参加者が記事を書くこと | 記事を書けるのはスライドの作者だけ。参加者のレポートは、作者が関連リンクの「記事」として足す |

## 読む順序

1. [ストーリーマップ](story-mapping.canvas)で、利用者の行動、各段階の対象機能・前提・完了条件を確認する。
2. マップにある機能名のリンクから、各 feature の具体的な利用場面と受け入れ条件を読む。
3. 実装を考えるときは [開発者向け設計](dev/index.md)を読む。

実装する範囲と順序はストーリーマップ内で管理し、一覧を別の文書に複製しない。

## 決まっている方針

- 受け取るのはビルド済みの静的ファイルだけ。中身がスライドかどうかは判定しない。ページを伝える script のない HTML も、そのまま表示する。画面の言葉は「スライド」のままにし、スライド以外も置けることは宣伝しない。
- 置く入口は、ブラウザへのドロップと、AI エージェント(MCP)の 2 つ。GitHub のリポジトリからの更新は、やめた([GitHub からスライドを更新する](features/f01-github-deploy.md))。GitHub App の導入、リポジトリの連携、workflow の設定が要り、「置くだけ」と最も離れた入口だからである。ログインは、第二スコープで GitHub でのログインをやめ、メールに送る 6 桁のコードだけにする([メールのコードでログインする](features/f28-email-login.md))。
- 置いた直後は、作者だけが見られる。一般公開は、人が押す操作として残す。AI エージェントは公開できない。
- 説明のための LP は置かない。トップページをアップロードの入口にする。置く操作そのものが、何をするサービスかを伝える。
- 作者の HTML は sandbox 付きの iframe で、管理画面とは別の origin から配る。読む人のログイン情報や管理画面の操作に、スライドの JS を届かせない。
- OGP 画像は、必要になったページをサービスが撮影して保存する。アップロードの時点で全ページを撮らない。
- 引用の表示は、埋め込みではなく表紙のカードにする。SNS の投稿のタイムラインと、イベントの表示は、やめた。
- 招待制を続ける。運営が招待したメールアドレスの人だけがログインでき、ログインできた人は置ける(第二スコープで、GitHub アカウントの登録から変えた)。ログインをだれにでも開くことは、利用規約とプライバシーポリシーに、メールアドレスの扱いを書けてから決める。小さい容量・頻度の上限から始め、上限は後から運用設定で変更する。
- 第一スコープの本番のデータは、空にしてよい。やめる機能は、互換のための経路を残さずに取り除く。
- 第一スコープの画面は、白地、墨の文字、ピルのボタン、トークンだけで組む。色面と切り紙の図形は使わない(エラーの画面の生成りの面は、第一スコープの画面ではなく、既存のまま残す)。
- Workers を使い、配信と保存の費用を抑える。公開管理とアクセス制御はキャッシュより前で行う。

後に回した機能について決まっている方針は、次のとおり。第一スコープでは作らない。

- AI の生成物(記事の下書き、翻訳、レビュー)は、作者が確認して公開を選んだものだけを読者に見せる。生成クレジットは持たず、生成の回数や量の上限はプランと運用設定で決める。
- 収益はコース販売と投げ銭の手数料、PRO、TEAM。販売と投げ銭には Stripe Connect を使う。売るのはスライドを順番に並べたコースだけで、スライド単体やページごとには売らない。サービス内にポイントや残高は持たない。
- 作者が販売・一般公開を止めたり退会したりしても、購入済みの読者の閲覧は維持する。
- PRO は独自ドメイン、大容量、閲覧分析。TEAM は PRO にチーム限定共有と SSO を加える。
- タテブログへの適用は、はてな・KADOKAWA の許可が整ってから。slide 単独の開発を妨げない。

## まだ採用しない案

第一スコープの後に回したものは、次のとおり。

- 翻訳([別の言語で説明を読む](features/f06-localization.md))、サービスが下書きを作る、話した言葉といっしょに読む記事([話した言葉といっしょに読む](features/f15-talk-reading.md))。作者が書く記事は、第二スコープで作る([発表を書き起こした記事を添える](features/f26-article.md))。
- 音声での説明([ページの説明を音声で聴く](features/f07-narration.md))、発表者用の画面([発表用と観客用の画面を分ける](features/f04-presenter.md))。
- AI レビュー([良いものに、たどり着きやすく](features/f18-ai-review.md))、閲覧の解析([どのページまで読まれたか確かめる](features/f11-analytics.md))。
- プラン、独自ドメイン、容量、コース販売、チーム共有、SSO、投げ銭。
- PDF のスライドを受け取ること。
- 作者がページの画像を用意すること、公開した後に URL の名前を変えること。

SNS の投稿のタイムライン、イベントとコミュニティの表示、GitHub からの更新は、採用をやめた。共同編集・コメント、pedit や Peitho Studio からの直接連携、GitHub のネットワークを使う SNS、遠隔発表同期、登壇動画と文字起こしの対応づけも保留。具体的な利用者の場面と既存手段の困りごとが明確になった時点で feature にする。広告と広告収益還元、音声のプラットフォーム側生成は方針から外す。

[着想元](https://slides.yusu.ke/my-slides-app)、[Zenn の公開体験](https://zenn.dev/zenn/articles/zenn-cli-guide)、[LISTEN](https://listen.style/guide)は参考。各サービスの全機能を再現する計画ではない。
