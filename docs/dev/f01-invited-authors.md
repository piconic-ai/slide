# 招いた作者の実装設計

[GitHub からスライドを更新する](../features/f01-github-deploy.md) のうち、運営が登録した人が作者として使えるようにする部分(F01-AC5〜F01-AC8)を実装するための契約。アップロードは [アップロードの実装設計とタスク](f01-github-deploy.md)、作者限定の表示と公開状態は [公開管理の実装設計](f02-publication.md) を使い、ここでは「誰が作者か」の判定と、作者どうしを分ける条件を扱う。

状態: 設計。2026-11-17 に、コードを読んで調べた結果をもとに書いた(commit `d5fa0d8`)。実装は、下の「PR の分け方」の順に進める。

## いまの状態

作者は 1 人である。GitHub の user ID が設定 `GITHUB_ACTOR_ID` と同じ人だけを通す。この設定を見ているのは、次の 5 か所である。

| 場所 | 何を確かめているか |
| --- | --- |
| `src/auth/config.ts`(ログイン) | GitHub が返した user ID が、設定と同じ |
| `src/auth/owner-session.ts`(session) | session の持ち主の GitHub ID が、設定と同じ |
| `src/uploads/api.ts`(CI のアップロード) | スライドの持ち主が、設定と同じ |
| `src/preview/content.ts`(作者限定の表示を開く) | 開くための token の持ち主と、スライドの持ち主が、どちらも設定と同じ |
| `src/preview/content.ts`(作者限定の表示の配信) | session の持ち主と、スライドの持ち主が、どちらも設定と同じ |

データは、すでに行ごとに持ち主を持っている(`decks.owner_user_id`、`preview_launches.owner_user_id`、`content_sessions.owner_user_id`、`accounts.user_id`、`profiles.user_id`)。値は GitHub の user ID である。

### 作者どうしは、すでに分かれている

ログインが要る経路をすべて読み、問い合わせが「ログインした本人」に絞られているかを確かめた。**ログインした作者が、ほかの作者のスライド・版・履歴・公開状態・反応・作者限定の表示・プロフィール・アカウントを、読んだり変えたりできる経路は見つからなかった。**

- 持ち主の ID は、すべて session から取っている。request の path・本文・query から取っている所はない。
- スライドの一覧、履歴、公開状態の読み書き、削除、退会、作者限定の表示を開く操作、リポジトリの連携は、SQL の条件に持ち主を含む。
- 上限(保存量、同時のアップロード、1 日の回数、スライドの数)は、作者ごとに数えている。
- CI のアップロードは、`GITHUB_ACTOR_ID` との比較のほかに、「workflow を実行した人(`actor_id`)が、スライドの持ち主である」ことを確かめている(`isAllowedSource`)。作者 B が、作者 A のスライドに連携したリポジトリへ push できても、A のスライドにはアップロードできない。

### 「1 人」を前提にしている所

| # | 場所 | いまの動作 | 複数の作者で起きること |
| --- | --- | --- | --- |
| 1 | 上の 5 か所 | 1 つの ID と比べる | 2 人目が通らない |
| 2 | 作者限定の表示(`src/preview/store.ts`、`access-store.ts`) | token・session の持ち主と、スライドの持ち主を、それぞれ設定の ID と比べる。列どうしは比べていない | 設定を一覧に変えるだけだと、「どちらも一覧にいる」ことしか確かめない条件になる。token は、発行のときに持ち主のスライドだけに出しているので、すぐに他人のスライドが開くわけではないが、開くときと配信のときの条件としては弱くなる。列どうしを比べる条件に直す |
| 3 | スライドの ID(`decks.id` が主キー) | slug は、全作者で 1 つの名前空間 | B が、A の使っている slug で連携しようとすると、「ほかの作者のスライドです」と断られる。A の下書きの slug が存在することも、B にわかる |
| 4 | handle(`accounts.handle` は一意。ログインのときに `onConflictDoNothing` で入れる) | 先に取った人のもの | 2 人目の GitHub のログイン名が、すでにある handle と同じなら、handle の行ができない。ログインはできるが、共有 URL も一覧も出ない。本人には理由がわからない |
| 5 | 順番に頼った認可(`readTakedown`、`readPointedVersion`、`isPublishable`、反応の `listPosts`・`addPosts`・`removePost`、履歴の中の版の query) | 持ち主の条件を持たず、同じ handler で先に呼ぶ「持ち主のスライドか」の確認に頼る | いまは安全。確認を飛ばす呼び出しを足すと、穴になる |
| 6 | `saveTransition` の `ownerUserId` が省略できる | CI は渡さない(意図どおり) | 作者の操作で渡し忘れると、持ち主の条件が付かない |
| 7 | 登録から外した作者 | — | ログイン・session・アップロード・作者限定の表示は、一覧との比較で止まる。公開済みのスライドは残る(F01-AC8 のとおり) |
| 8 | テスト(`src/publication/test-support.ts` の `signIn`) | GitHub の応答を、常に 1 つの ID にしている | 2 人目として HTTP でログインするテストが書けない。「別の作者」は、設定の ID を変えることで表している |

全作者で共有していて、そのままにするもの: IP ごとの request の上限、cron の掃除の 1 回あたりの件数(古い順で、作者ごとの公平さはない)、上限の値そのもの(`UPLOAD_LIMITS`)。招くのは数人なので、困る場面が出てから考える。

## 設計

### 誰が作者か

設定を、GitHub の user ID の一覧にする。名前は `AUTHOR_GITHUB_IDS` に変える(意味が変わるので。作者 1 人のあいだの別名は残さない)。値は、ID をコンマで区切った文字列にする(`"722500,1234"`)。

- 解析は、純粋な関数 `parseAuthors(value)` で行う。数字だけの ID の、空でない集合を返す。空、数字でないもの、重複は、設定の誤りとして扱い、**誰も通さない**(ログインも、アップロードも、作者限定の表示も止まる)。誤った設定で、意図しない人を通さないためである。
- 判定は `isAuthor(authors, githubId)` の 1 つにまとめ、5 か所すべてがこれを使う。
- 誰が運営かは、これまでどおり Cloudflare Access の policy で決める。作者の一覧とは別である。

この設定は、誰に権限を与えるかを決める。変える PR は、merge の前に作者が確かめる(`dev-loop` skill の止まる条件 8 に、新しい名前を足す)。

### 作者どうしを分ける条件

「一覧にいる」ことと「そのスライドの持ち主である」ことは、別の条件である。どちらも SQL に書く。

- **作者限定の表示を開く**(`consumeLaunch`): token の持ち主が、スライドの持ち主と同じ(`preview_launches.owner_user_id = decks.owner_user_id`。列どうし)。かつ、その持ち主が一覧にいる。
- **作者限定の表示の配信**(`readAccessFacts`): session の持ち主が、スライドの持ち主と同じ(`content_sessions.owner_user_id = decks.owner_user_id`)。かつ、その持ち主が一覧にいる。
- **CI のアップロード**(`allowedDeckOwner`): スライドの持ち主が一覧にいる。workflow を実行した人が持ち主であることは、いまの `isAllowedSource` がそのまま確かめる。
- **管理画面の経路**: いまの条件(`decks.owner_user_id = ログインした本人`)を変えない。

表の 6 は閉じた。`saveTransition` は、保存する主体(`by`)を必ず受け取り、作者の操作と CI を型で区別する。

表の 5 の読み取りには、持ち主の引数を足さない。どれも、同じ handler の中で、持ち主を確かめる呼び出し(`readPublication`、`listDeckHistory`、`ownsDeck`)のあとにだけ呼ばれている。`readTakedown` は運営の操作からも呼ばれ、そこでは持ち主を問わないので、引数を足すと呼び出しごとに意味が分かれる。守りは、経路ごとに「他人のスライドは、存在しないスライドと同じに見える」ことを確かめるテストに置く。経路を足すときは、このテストも足す。

### 登録していない人、外された人

- 登録していない人が GitHub でログインすると、ログインできず、招待制であることを伝えるページが出る(F01-AC6)。いまは、理由を言わずに失敗する。
- 外された人は、次の request から、ログインした状態として扱われない(session の確認が一覧を見るため)。アップロードと、作者限定の表示も止まる。公開済みのスライドは、そのまま読める。止めるときは、運営が 1 つずつ非表示にする(F01-AC8)。

### テスト

- `signIn` に GitHub の ID を渡せるようにし、2 人の作者が同時にログインした状態を作る。これは、設定が一覧になってから書ける(PR 3)。それまでの PR 2 では、もう 1 人の作者の行を D1 に直接入れ、作者 1 人の session から、その経路を呼んで確かめる。
- 作者 A と B を用意し、B の session で、A のスライドの各経路(管理画面、履歴、公開状態の読み書き、削除、作者限定の表示を開く操作と配信、反応、リポジトリの連携)を呼ぶ。どれも、存在しないスライドと同じ応答になることを確かめる(F01-AC7)。
- B の workflow から、A のスライドへのアップロードが断られること。B が自分のスライドにアップロードし、公開できること(F01-AC5)。
- 設定が空・不正のとき、誰も通らないこと。
- 外された人の session・アップロード・作者限定の表示が止まり、公開済みのスライドが読めること(F01-AC8)。

## 決めていないこと

作者に確かめてから決める。どちらも、下の PR 1〜3 は、答えを待たずに進められる。

- **slug の名前空間**(表の 3)。共有 URL は `/@handle/slug` なので、作者ごとに同じ slug を使えると期待されうる。いまは、全作者で先に取った人のものである。作者ごとにするには、`decks` の主キーを変える migration と、スライドの ID だけで引いている query すべての見直しが要る。
- **handle がぶつかったとき**(表の 4)。GitHub のログイン名は同時には重ならないが、改名のあとで、古い handle を持つ人と重なりうる。
