# 通報の実装設計

[知らない人のスライドも、安心して開ける](../features/f17-safe-viewing.md) のうち、読者がスライドを通報し、運営が一覧で見る部分(F17-AC16、F17-AC17、F17-AC18、F17-AC25、F17-AC26)を実装するための契約。運営の画面は [運営による非表示の実装設計](f17-takedown.md)、共有 URL は [共有 URL と配信の実装設計](f03-sharing.md) を使い、ここでは通報の保存、通報のページ、ログインのあとの戻り先を扱う。

状態: 実装済み。本番でのログインつきの確認は、作者が行う(#134)。

## 保存

表 `reports`(migration `0024_reports.sql`)に、1 人につき、1 つのスライドに 1 行を持つ。

| 列 | 中身 |
| --- | --- |
| `id` | 乱数の ID |
| `deck_id` | スライドの鍵(`decks.id`) |
| `deployment_id` | 通報を受け付けたときに、一般公開されていた版 |
| `share_path` | 読者が開いていた共有 URL の path(`/@handle/slug`、ページ番号つきなら `/@handle/slug/3`) |
| `reason` | `nuisance`(迷惑行為)、`rights`(権利侵害)、`other`(その他) |
| `note` | 説明。ないときは空文字 |
| `reporter_user_id` | 通報した人の GitHub の user ID。`NULL` を許す(あとでログインなしの通報を足せるように) |
| `created_at`、`updated_at` | 最初に通報した時刻と、最後に通報した時刻(Unix 秒) |

`(deck_id, reporter_user_id)` は一意である。同じ人が同じスライドをもう一度通報すると、`saveReport`(`src/reports/store.ts`)が、理由・説明・版・共有 URL・`updated_at` を置き換える。`id` と `created_at` は変えない。

理由と説明の検証は、純粋な関数 `parseReport`(`src/reports/report.ts`)が行う。説明は、前後の空白を落として 500 文字まで。「その他」のときは、説明が要る。

## スライドの削除

`reports.deck_id` は `decks.id` を指す外部キーなので、通報の行が残っていると、スライドの行を消せない。そのため、通報を送れるようにする変更と、消す変更は、同じ PR に入れた。

- 作者がスライドを削除すると(`markDeckDeleted`)、同じ transaction で、そのスライドの通報を消す。退会で、その人のスライドがすべて削除されるときも同じである。
- 掃除がスライドの行を消すとき(`purgeDeletedDecks`)にも、その直前に通報を消す。削除のあとは通報を受け付けないので、ふつうは残っていない。削除と同時に届いた通報が残っていても、掃除が外部キーの違反で止まらないようにするためである。

## 通報のページ

viewer(`src/share/pages.ts`)の、題名の右の「⋯」メニューの中に、「通報する」のリンクを置く。通報の入口を目立たせないためである(作者、2026-11-16)。メニューは `<details>` で、script なしで開閉する。作者の HTML の中ではなく、サービス側の画面にある。読者がふだん使わない操作(今後のミュートなど)は、このメニューに足す。リンク先は `/reports/new?slide=<共有 URL の path>` である。

| 経路 | 動作 |
| --- | --- |
| `GET /reports/new?slide=…` | ログインしていなければ、401 とログインの案内を返す(viewer の「通報する」は、script が動くとき、この画面に移らず、ログインを促すモーダルを開く。F03-AC91)。ログインしていれば、対象のスライドの `/embed/…` の枠(F17-AC35)と form を返す。この応答の CSP は、ページの CSP に `frame-src 'self'` だけを足す(F17-AC36)。`result=received` が付いていれば、受け付けたことを表示する |
| `POST /reports` | CSRF を確かめ、ログインした人の ID で保存し、`/reports/new?slide=…&result=received` へ 303 で移す。1 回目も 2 回目も、同じ表示になる |

どちらも、`slide` が共有 URL の形でないとき、またはスライドがいま一般公開されていないとき(下書き、停止中、運営が非表示にしたもの、存在しないもの)は、404 を返し、何も保存しない。公開されているかは、viewer と同じ `readSharedDeployment` で確かめる。保存する版は、その関数が返した、いま公開中の版である。form から版の ID を受け取らないので、読者は、ほかのスライドの版を通報に付けられない。

viewer の中でめくったページは、通報に載らない。`share_path` は、ページを開いたときの URL から作る。`/@handle/slug/3` を開いたなら、リンクも、ログインのあとの戻り先も、保存する path も、ページ番号つきになる。

通報の経路(`/reports`、`/reports/new`)は、管理画面と同じ IP ごとの頻度制限に入る(`src/site/rate-limit-policy.ts`)。1 人 1 スライド 1 行にまとまっても、送るたびに D1 を読み書きするためである。

## 運営の画面の一覧

運営の最初の画面(`admin.slide.community/`)に、「通報されたスライド」の表を出す。検索は `listReportedDecks`(`src/reports/store.ts`)が行う。

- 削除されていないスライドのうち、通報が 1 件以上あるものを、公開の状態にかかわらず出す(停止中、非公開、運営が非表示にしたものも含む)。
- スライドごとに、`@handle/slug`、通報した人数(行の数)、通報ごとの理由・説明・日時、最後の通報の日時を出す。最後の通報が新しい順に、50 件まで。ページ送りと絞り込みはない。
- 通報した人の ID は、検索で取り出さない。画面にも出ない。
- 説明は、文字として出す(`html` の helper が escape する)。

知らない人に開く前に、見直すことが 2 つある。いまは、登録した人しか通報できないので、どちらも起きない。

- 1 つのスライドへの通報の数には、上限がない(スライドは 50 件まで)。多くの人が 1 つのスライドを通報すると、その分だけ画面が長くなる。
- 人数は、行の数である。ログインなしの通報(`reporter_user_id` が `NULL`)を足すと、同じ人の通報が複数の行になりうるので、人数の数え方を決め直す。

運営は、表の `@handle/slug` を、同じ画面の「スライドを非表示にする」に入れて、非表示にできる。通報に「確認済み」の印を付ける操作はない。

## ログインのあとの戻り先

ログインの入口 `/login?to=…` の戻り先は、`landingOf`(`src/auth/landing.ts`)が決める。`settings` は `/settings` に戻る。スライド・そのページ・プロフィールの正規の path は、`parseSharePath` で解析した部品から組み立て直して戻す。それ以外は、外部の URL や `//host` も含めて `/slides` に戻る。

当面、ログインできるのは、運営が登録した人だけである([招いた作者の実装設計](f01-invited-authors.md))。登録していない人が「通報する」からログインに進むと、招待制のページが出る。
