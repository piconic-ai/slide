# 規約のページの実装設計

[利用規約とプライバシーポリシーを読む](../features/f34-legal-pages.md) を実装するための契約。ここでは、文面の持ち方(条、項、号の並び)、下書きと正式の切り替え、経路、検査、依頼者が文面を差し替えるときの手順を扱う。決めた根拠は、第四スコープの指示書の D-20〜D-29 である。

文面そのものは、依頼者が決める。エージェントは、依頼者の依頼なしに文面を書き換えない。決まっていない値(`(日数)`、`(年数)`、`(施行日)`)も、依頼なしに埋めない。

いまの文面は、2026-11-27 制定の初版である。依頼者の依頼で、下書き(2026-11-26)を丁寧語にそろえ、誤字と脱字を直し、施行日を入れた。直した箇所と、残っている判断は、[仕様](../features/f34-legal-pages.md#決めたこと)にある。

ページを描く側は、文面の言葉を持たない。文面を差し替えても、変えるのは `texts/` と `handed-over/` の 2 つのファイルだけである。

## 文面の持ち方

利用規約とプライバシーポリシーは、`ArticleText`(`form: 'articles'`)である。

```text
題名
前文(段落の並び)
条の並び
  番号、題(「第 6 条(外部への送信)」の「外部への送信」)
  本文
    clauses: 項の並び。各項は、文と、その後に続く号の並び
    plain:   番号のない段落の並びと、その後に続く号の並び
本文の中のリンク(links)
附則の並び(history)。1 行が、日付と要点
```

条の本文は、2 つの形のどちらかになる。「第 1 条の 1、2、3 項」のように番号のある項が並ぶ条は `clauses`。「次のことをしてはなりません。」のあとに号が並ぶ条や、番号のない段落だけの条は `plain`。項の番号と号の番号は、文面に書かない。ページが `<ol>` で描き、ブラウザーが 1、2、3 と数える。文面の Markdown の番号は、1 から途中で飛ばずに並んでいることを、テストが確かめる。

「外部への送信」のページは、`TransmissionText`(`form: 'transmission'`)である。題名、冒頭の文、表の見出し 4 つ、送り先の行の並び(送り先、送る情報、目的、その事業者のポリシーの名前と URL)、附則を持つ。

リンクになる言葉は、`links` に書いた言葉だけである(`{ phrase, href }`)。いまは、プライバシーポリシー第 6 条の「外部への送信」が `/privacy/external` へのリンクになっているだけである。文の中の言葉が `phrase` と一致する最初の場所だけがリンクになる。ほかの言葉や URL は、リンクにしない。表のポリシーへのリンクだけは、行ごとの `policy.url` である。

## 下書きと正式の切り替え

文面ごとに、附則の最初の行(制定)の日付で決まる(`isDraft`)。

| 附則の最初の行の日付 | 状態 |
| --- | --- |
| `(施行日)` のまま。空。日付として読めない値(`未定`、`2026-02-30` など) | 下書き |
| `2026-12-01` または `2026年12月1日` の形で、暦にある日 | 正式 |

下書きのあいだは、次の 3 つが同時に効く。3 つの文面が別々に切り替わる。

1. 題名に「(下書き)」が付く(`<h1>` と `<title>`)。
2. 題名のすぐ下に、「この文面は下書きです。正式な内容は、施行日を入れて公開します。」が、枠線で囲んで出る。
3. 検索エンジンに載せない。`isIndexablePath` が、下書きの文面の path を載せず、`noindexPrivate` が `X-Robots-Tag: noindex, nofollow` を付ける。

日付が入ると、3 つとも外れ、その文面の path が検索に載る。

附則は、変更の履歴を兼ねる。最初の版は 1 行(`2026年11月27日: 制定`。施行日を入れる前は `(施行日): 制定`)である。改正のときは、日付と変えた条の要点の行を足す。

### 仕上げの漏れを止める(D-22)

日付が入っているのに、決まっていない値の印が文面に残っていると、テストが失敗する(`src/legal/document.pure.test.ts` の「carried … text」)。印は `(日数)`、`(年数)`、`(施行日)` で、全角のかっこと、かっこの中の空白も同じに読む(`PLACEHOLDER_WORDS`)。下書きのあいだは、印が残っていてよい。新しい種類の空欄を文面に足したときは、`PLACEHOLDER_WORDS` に言葉を足す。

## 表示言語が英語のとき

文面は日本語だけである(D-25)。英語の画面でも日本語の文面を出し、題名のすぐ下に、英語で 1 行「This page is available in Japanese only.」を出す。文面を囲む要素に `lang="ja"` を付け、この 1 行には `lang="en"` を付ける。英語の訳は作らない。

## 経路

| URL | 描くもの |
| --- | --- |
| `/terms` | 利用規約 |
| `/privacy` | プライバシーポリシー |
| `/privacy/external` | 外部への送信 |
| `/contact` | お問い合わせ(中身は変えない。仮の表示だけを外した) |

4 つとも、`src/app/routes.tsx` の中で、メンテナンスの `503` を返す仕組み(`maintenance`)より前に登録している。メンテナンス中も読める。`privacy` と `terms` は、ハンドルに選べない予約語である(`src/auth/handle-rules.ts`)。`/privacy/external` は、`/@ハンドル` の経路とぶつからない。

## フッター

フッターに、運営者の名前も、運営者のプロフィールへのリンクも置かない(2026-11-26、依頼者の判断で外した。F34-AC29)。運営者の名前は、利用規約とプライバシーポリシーの冒頭にある。サービスの外へのリンクは、GitHub のリポジトリだけである。

## 画面の決まり

[05-UI-RULES の規約のページ](../features/f34-legal-pages.md#決めたこと)に従う。

- 条の見出しは `h2`、項と号は `<ol>` の入れ子。番号を CSS で作り替えない。
- 本文と注記の幅は 40em まで。
- 注記は、色面を使わず、枠線(`--input`)で囲む。
- 「外部への送信」の表は、`data-table` を使う。幅 600px 未満では、1 つの送り先が、見出しと 3 つの項目のまとまりになって縦に並ぶ。

## 文面を差し替える手順

文面を直す、施行日を入れる、送り先を変えるときの手順である。コードを読まなくても進められるように書く。変えるファイルは、1 つの文面につき 2 つだけである。

| 文面 | 変えるファイル(1) | 変えるファイル(2) |
| --- | --- | --- |
| 利用規約 | `src/legal/texts/terms.ts` | `src/legal/handed-over/terms.md` |
| プライバシーポリシー | `src/legal/texts/privacy.ts` | `src/legal/handed-over/privacy.md` |
| 外部への送信 | `src/legal/texts/external-transmission.ts` | `src/legal/handed-over/external-transmission.md` |

(2)は、文面の Markdown である(はじめは Google ドキュメントから取り出した。初版で丁寧語にそろえてからは、Google ドキュメントとは文体が違う)。(1)は、ページが描く文面である。同じ内容にそろえておくと、テストが 2 つの一致を確かめて、写し間違いを止める。

### 1. 文面を直す

1. (2)のファイルの、直す条を直す。元の文書(Google ドキュメント)から取り出した Markdown で全体を置き換えるときは、丁寧語にそろえた文体と、初版で直した誤字が戻らないかを確かめる。
2. (1)のファイルの、直した条を、同じように直す。次の形になっている。
   - 条は `{ number: 6, title: '外部への送信', body: … }`。`number` が「第 6 条」の 6、`title` が(かっこの中の)題である。
   - 項が並ぶ条の `body` は `{ kind: 'clauses', clauses: [ { text: '…', items: [] }, … ] }`。`text` が項の文、`items` がその項に続く号の文の並びである。
   - 項の番号がない条(「次のことをしてはなりません。」と号が並ぶ条など)の `body` は `{ kind: 'plain', paragraphs: ['…'], items: ['…'] }`。`paragraphs` が号の前の文、`items` が号の並びである。
   - 項や号の番号は、書かない。並べた順に 1、2、3 と出る。
   - 条を足すときは、`articles` の並びの正しい位置に、`{ number, title, body }` を足す。
3. 「外部への送信」のように、別のページへのリンクにしたい言葉は、`links` に `{ phrase: '言葉(文の中のとおり)', href: '/…' }` を足す。
4. `pnpm test src/legal src/site/legal-pages.test.ts` を実行する。2 つの文面が違うと、どの行が違うかが出る。

### 2. 決まっていない値を決める

文面の中の `(日数)` と `(年数)` を、決まった値に書き換える。たとえば、プライバシーポリシー第 8 条の「履歴情報は (日数) 残す。」は、初版で「履歴情報は、最大 3 か月残します。」にした。(1)と(2)の両方で直す。いまの文面に、決まっていない値の印は残っていない。

### 3. 施行日を入れる

(1)のファイルの末尾の `history` の最初の行を、次のように書き換える。

```ts
// 前
history: [{ date: '(施行日)', summary: '制定' }],
// 後
history: [{ date: '2026年11月27日', summary: '制定' }],
```

日付は `2026-12-01` か `2026年12月1日` の形で書く。(2)のファイルの末尾の行 `- (施行日): 制定` も、同じ日付に書き換える(「外部への送信」の Markdown には附則の行がないので、(1)だけを直す)。初版の 3 つの文面には、`2026年11月27日` を入れてある。

日付を入れると、そのページの「(下書き)」と注記が外れ、検索に載る。日付を入れていない文面は、下書きのままである。日付を入れたのに `(日数)`、`(年数)`、`(施行日)` が残っていると、`pnpm test src/legal` が失敗し、どの印が残っているかが出る。

### 4. 施行の後に文面を変える

(1)の `history` に、行を足す。日付と、変えた条の要点を書く。

```ts
history: [
  { date: '2026年11月27日', summary: '制定' },
  { date: '2027年4月1日', summary: '第 14 条を改める' },
],
```

(2)の末尾にも、同じ行を足す(`- 2027年4月1日: 第 14 条を改める`)。文面を変えたあとの同意の取り直しは、作っていない。

### 5. 「外部への送信」の送り先を変える

(1)の `rows` に、行を足すか直す。1 行は、送り先、送る情報、目的、その事業者のポリシー(名前と URL)である。(2)の表にも、同じ行を足す。送り先が変わるのは、利用者の情報を新しい相手に送るときである。PR のテンプレートの「利用者の情報への影響」の欄が、そのときの確認になる。

ヘルプの記事は、条を番号ではなく題で指し、`src/help/legal-links.ts` が条の位置(`id`)のリンクを作る。条の題を変えたり、条を消したりしたときは、`pnpm test:pure src/help/fourth-scope-articles.pure.test.ts` が、ヘルプの記事のリンクが指す題を知らせる。禁止事項の号の数を変えたときは、同じテストが、ヘルプの英語の一覧の数を直すように知らせる。

### 6. 確かめる

```sh
pnpm test src/legal src/site/legal-pages.test.ts src/site/legal-pages-dated.test.ts
pnpm test:pure src/legal src/site/indexing.pure.test.ts
pnpm dev
```

`pnpm dev` で起動し、`/terms`、`/privacy`、`/privacy/external` を開いて、(下書き)の有無、注記、条の並びを見る。本番へ反映する手順は [本番に反映する](deploy.md) にある。

## 号の書き方

号は、1、2、3 の数字で出す。① ② にはしない(2026-11-27 に依頼者が決めた。読み上げの番号と、文面の番号が一致する)。あとで変えるときは、`src/legal/document-pages.ts` の `<ol>` の `list-style-type` を 1 か所で変える。ただし、番号を CSS で作り替えない決まり(読み上げの番号と文面の番号を一致させる)があるので、決めるときに依頼者と相談する。

## 文面と実装の食い違い

この作業では、文面も実装も直さずに、食い違いを PR の本文と最後の報告に書いた。食い違いの一覧は、依頼者が文面を仕上げるときの材料である。
