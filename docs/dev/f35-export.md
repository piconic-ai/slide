# データの書き出しの実装設計

[データを書き出す](../features/f35-data-export.md)のうち、画面から書き出す部分(作業 E)の設計。AI エージェントから書き出す部分(`export_account`、`get_slide_files`、取り出すための URL)は作業 G が、同じ集め方と zip の作り方を使って足す。

## 作るもの

| 何を | どこから | 形 |
| --- | --- | --- |
| 版ごとの zip | 1 本の管理、設定の「データを書き出す」 | `GET /slides/:deck/export/published.zip`、`prepared.zip` |
| 記事 | 同上(記事があるときだけ) | `GET /slides/:deck/export/article.md` |
| スライドの情報 | 同上 | `GET /slides/:deck/export/slide.json` |
| アカウントの情報 | 設定の「データを書き出す」 | `GET /account/export/account.json` |
| プロフィール画像 | 同上(アップロードがあるときだけ) | `GET /account/export/picture` |

どれも `GET` で、ログインしている本人の Cookie だけで答える。`/slides/` と `/account/` の下にあるので、管理 origin の頻度の上限(`MANAGEMENT_RATE_LIMITER`、IP ごとに 1 分に 120 回)がそのままかかる(F35-AC28)。新しい binding は足していない。

## どの版を書き出すか(D-31)

`versions.ts` が、1 本の管理の「新しい版」の枠と同じ `versionRows` から決める。

| 公開の状態 | 公開中の版(`published`) | 準備済みの版(`prepared`) |
| --- | --- | --- |
| まだ公開していない(版がある) | なし | いちばん新しく受け取った版 |
| 公開中 | 公開中の版 | それより新しい版があるときだけ、その版 |
| 公開を止めている | もう一度公開すると戻る版 | それより新しい版があるときだけ、その版 |
| 版がない | なし | なし |

「公開を止めている」ときの「公開中の版」は、読者には見えていないが、画面のリンクの文言は「公開中の版(zip)」のままにする(受け入れ条件の文言のとおり)。残している過去の版は、どの経路にも出さない(F35-AC5)。URL に版の ID を入れる形も作らない。

## 書き出すものの形

JSON は UTF-8、2 字下げ、末尾に改行。時刻は ISO 8601 の UTC 文字列。形の版の番号(`schemaVersion`)は、項目の意味が変わるか消えるときに上げる。項目を足すときは上げない。ファイルごとに別の番号を持つ。

| `versions[].files[]` | 配列 | パス、バイト数、SHA-256、メディアタイプ。R2 のキーは入れない |

入れないもの。トークン(ハッシュしか持たないので入れようがない)、フォロワー、自分をミュートやブロックした人、他人のスライドの中身と題名、他人のメールアドレス。ほかの人は、自分が選んだ関係(フォロー、ミュート、ブロック)のハンドルだけで現れる。

### 記事(`article.md`、D-33)

書いた Markdown をそのまま返す。公開前の編集があるときは、その編集(作者が最後に書いたもの)。ページの埋め込みは、書いたときの共有 URL のまま。何も足さない。

## 経路の守り

1. 別のサイトが起こした要求は断る。ブラウザが付ける `Sec-Fetch-Site` が `same-origin` か `none` のものだけ通す(付かない道具は通す)。ほかのサイトの画面から、本人のブラウザで zip を作らせて 1 人 1 つの枠を埋められないようにするため。`403`。
2. ログインしていなければ `303` で `/login`。利用を止められている人は、既存の `currentOwner` が停止の画面(`403`)にする(F35-AC26)。
3. スライドは、持ち主の条件つきで引く(`readExportDeck`)。無い、他人の、削除待ちは、どれも `null` で、スライドが無いときと同じ `404`(F35-AC24)。
4. 版のファイルは、持ち主、スライド、版を 1 つの条件にして引く(`readVersionFiles`)。他人のスライドの版の ID を渡しても、何も返らない。
5. 応答は、`Cache-Control: no-store`、`Content-Disposition: attachment`、`X-Content-Type-Options: nosniff`、`Content-Security-Policy: default-src 'none'; sandbox`、`Vary: Cookie`(F35-AC27)。ファイル名は英数字とハイフンだけで作る。

## zip の作り方(D-32、D-35)

### 形式

- **無圧縮(stored)。** 置かれるのは画像、フォント、動画など圧縮済みのものが多い。HTML と JS は圧縮の効きがよいが、数 MB の上限のなかで、無圧縮でも差は小さい。無圧縮にすると、各記録の大きさが DB の `size` から分かり、zip 全体の長さ(`Content-Length`)を、最初のバイトを送る前に決められる。圧縮に CPU を使わない。
- **データ記述子つき。** CRC-32 は、ファイルを読むまで分からない。そのため、ローカルヘッダーの CRC と大きさを 0 にして(フラグのビット 3)、ファイルの後ろの記述子と、最後の中央ディレクトリに書く。解凍の道具(Info-ZIP の `unzip`、Python の `zipfile`、macOS、Windows のエクスプローラー、サービス自身の zip の読み手 `src/drops/zip.ts`)は、中央ディレクトリから読むので、そのまま開ける。先頭から順に読む解凍の道具(Java の `ZipInputStream` など)は、無圧縮でデータ記述子のある記録を読めない。作者が受け取る道具は、手元の解凍と、サービスへの置き直しの 2 つで、どちらも中央ディレクトリから読む。
- **32 ビットの記録だけ。** zip64 は使わない。1 つの zip は 500 ファイル、256 MiB までなので、必要がない。
- 名前は UTF-8(フラグのビット 11)。作った環境は UNIX、モードは通常のファイル 0644(`0o100644`)。型のビットが通常のファイルなので、リンクや実行ファイルとして展開されることはない。Info-ZIP は UNIX 以外の環境で作った名前を古い文字コードとして読み、日本語の名前が崩れるため、UNIX にした。
- 時刻は、版を受け取った時刻(UTC、DOS の形式。1980 年より前は 1980 年に切る)。全ファイルで同じ。
- 並びは、パスの昇順。フォルダの記録は作らない。サービスが足したもの(`index.html` に入れるページのスクリプトなど)は入らない。R2 に保存したバイトを、そのまま流すので、置いたときのバイトと同じ(F35-AC3、F35-AC7)。記事と情報は、zip に入れない。置き直したときに余分なファイルとして公開されるため(D-32)。

### パスの安全(F35-AC8)

保存されるパスは、アップロードの検査(`uploadPathProblem`)を通っているが、zip を作るところでもう一度、`zipNameProblem` で調べる。次のどれかがあると、その版の zip を全体として断る(一部を除いて作ると、置いたままではなくなるため)。

| 断るもの | 理由 |
| --- | --- |
| `..` や `.` の区切り | 展開先の外を指す |
| 先頭の `/`、空の区切り(`a//b`) | 絶対パス |
| `\` | Windows では区切り |
| `C:` などのドライブ | 絶対パス |
| 制御文字、NUL | 名前の切り詰め、端末の操作 |
| NFC でない名前 | 置いたときの名前と違う |
| 重なる名前 | 展開で上書きされる |

断ったときは `503` と、読める画面を返す。何も流さない。大文字と小文字だけが違う名前は、大文字と小文字を区別しない環境(macOS、Windows)で展開すると、1 つに重なる。サービスの置き方がこれを許しているので、断らず、この文書に書く。

### 流し方

`zipStream` は `ReadableStream` で、引き出されたときだけ次を作る(`pull`)。1 回の引き出しで 1 つの塊を出す。

1. ファイルの順番になったら、ローカルヘッダーを出す。
2. そのファイルの R2 の本体を、受け取った塊ごとに CRC-32 を進めて、そのまま出す。
3. 終わったら、読んだバイト数が計画の大きさと同じかを確かめて、記述子を出す。
4. すべて終わったら、中央ディレクトリと終端の記録を出す。

メモリに持つのは、いま流している塊(R2 の塊の大きさ)と、先に開いた小さいファイルの本体だけ。R2 の読み出しの待ちを隠すために、あと 3 つまで先に開く。ただし先に開くのは 1 MiB 以下のファイルだけで、先に持つバイトは、上限の設定がどんなに大きくても数 MiB に収まる。

**途中で止まるとき**は、ストリームを失敗にする(R2 にファイルがない、バイト数が大きさと違う、R2 が失敗した)。中央ディレクトリを書かないので、解凍の道具はどれも「壊れた zip」として断る。最後まで流してしまった zip に、足りないファイルがあるよりよい。接続は切れるので、ブラウザは失敗したダウンロードとして見せる。

`Content-Length` は、計画した長さで、Workers では `FixedLengthStream` に通して付ける(長さが合わなければ接続が切れる)。

## Worker の上限と見積り(F35-AC10)

Cloudflare の文書(2026-11-26 に確認。[Workers の上限](https://developers.cloudflare.com/workers/platform/limits/)、[R2 の Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/))から。

| 上限 | 値 | この設計での使い方 |
| --- | --- | --- |
| 1 回の呼び出しの subrequest | 無料 50、有料 10,000。R2、KV、D1 の binding の呼び出しも数える | 1 ファイルにつき R2 の `get` 1 回。ほかは 20 回ほど(下) |
| 同時に応答の頭を待てる接続 | 6 | 先に開くのは 3 つまで、いま流している 1 つを足して 4 |
| メモリ | 128 MB | 数 MiB(塊と、先に開く小さいファイル) |
| CPU 時間 | 有料で既定 30 秒(最大 5 分) | CRC-32 だけ。下の測定 |
| 応答の大きさ | Cloudflare は制限しない | 流す |

**R2 の読み出しの回数。** 1 つの zip で、R2 を呼ぶのは、ファイル数 N の `get` と、リースの `put`、`head`、`delete` の 3 回。D1 は、ログインの確認、持ち主の確認、公開の状態、版、記事、ファイルの一覧、停止の確認で、10 回ほど。

| 版のファイル数 N | R2 の呼び出し | D1 を足した見積り | 有料の上限 10,000 に対して |
| --- | --- | --- | --- |
| 100(既定の上限) | 100 + 3 | 約 115 | 1% |
| 500(`UPLOAD_LIMITS` で上げられる最大、`MAX_FILES_SETTING`) | 500 + 3 | 約 515 | 5% |

無料のプランでは 50 なので、約 35 ファイルを超える版は書き出せない。この Worker は有料のプランで動かす前提で作る(依頼者の確認に挙げる)。

**断る上限。** `zip-plan.ts` の 2 つで、超える版は断る。

| 定数 | 値 | 根拠 |
| --- | --- | --- |
| `MAX_ZIP_FILES` | 500 | 上の見積りで subrequest が足りる最大。アップロードの上限が上げられる最大と同じなので、設定を最大にしても断られない |
| `MAX_ZIP_BYTES` | 256 MiB | 既定の上限(1 版 10 MB、1 人 50 MB)の 5 倍。32 ビットの記録に収まり、下の測定で CPU 時間が 30 秒の数十分の 1 |

超えたときは `413` と「書き出せる大きさを超えています。お問い合わせください」の画面を返す。アップロードの上限を上げる設定にしたときは、この定数も合わせて見直す。

**測定**(`zip.performance.test.ts`、`export.performance.test.ts`。Node 上で、Apple の M 系のチップ。workerd の CPU 時間の実測ではなく、仕組みが保つメモリと回数の確認である)。

| 場合 | 結果 |
| --- | --- |
| 500 ファイル、256 MiB(上限)を流す | 約 0.6 秒、常駐メモリの増えは約 6 MiB |
| 450 個の小さな JS と、5 MiB の画像 8 枚(459 ファイル、約 40 MiB)を、ローカルの R2 と D1 から、認証つきの HTTP で | 約 2 秒。R2 の `get` はちょうど 459 回 |

本番の Worker の CPU 時間と、R2 の応答の遅さは、ローカルでは確かめられない。人の確認に挙げる。

## 1 人につき同時に 1 つ(D-36、F35-AC29)

zip を作る処理は、1 人につき同時に 1 つまで。表も binding も足さずに、R2 の上のリースで作る。

- 鍵は `exports/leases/<ユーザーの ID>`。アップロードの掃除は `<版の ID>/` の下だけを見るので、巻き込まれない。ID は `[A-Za-z0-9_-]` の 128 字までを確かめてから使い、鍵の外を指せない。
- 取るときは、条件つきの `put`(`If-None-Match: *`。R2 が全体で 1 つだけ成功させる)。あれば、`customMetadata.until`(5 分後)を見る。切れていなければ `429` と `Retry-After`、切れていれば、見た実物の ETag との一致を条件に上書きする。同時に 20 人が取りに来ても 1 人だけが取る(`lease-store.test.ts`)。
- R2 の ETag は中身から決まるので、リースの中身には、そのたびに新しい乱数を入れる。同じ中身だと、前の持ち主の返却が、いまの持ち主の分を消してしまう。
- 返すのは、ストリームが終わる、失敗する、取り消されるとき(閉じたタブ、止めたダウンロード)。返す前に実物の ETag を見て、自分のものだけを消す。応答が終わった後でも完了するように、`waitUntil` に渡す。断った版(上限、パス)では、すぐ返す。
- Worker が止められて返せなかったときは、5 分で切れる。5 分以上かかる遅いダウンロードは、リースが切れて、2 つ目が始まることがある。そのときも、同時に動くのは多くて 2 つで、1 人あたりの量は変わらない。
- 同時の制限は zip だけにかける。JSON と Markdown は小さいので、待たせない。

頻度の上限(F35-AC28)は、管理 origin の IP ごとの上限をそのまま使う(D-36)。zip だけに強い上限を足すには、新しい `ratelimits` の binding が要るので足していない。1 人 1 つの枠が、IP をまたぐ連打を抑える。

## 置き直し(F35-AC9)

受け取った zip は、そのままドロップして置ける。ドロップの読み手(`src/drops/zip.ts`)は、中央ディレクトリから読み、無圧縮の記録、UTF-8 の名前、通常のファイルのモードを受け取る。根に `index.html` があるので、フォルダの根の判定は要らない。`unpackEntry` は CRC-32 と大きさを確かめるので、書き出しの CRC-32 が間違っていれば置き直しが失敗する(`slide-export.test.ts` が、置く、書き出す、置き直す、を通して SHA-256 を比べる)。

## 他人のデータが出ない作り

| 守るもの | 守り方 |
| --- | --- |
| 他人のスライド | 持ち主を条件に含めて引く。無い、他人の、削除待ちは同じ `404` |
| 他人の版、他人のファイル | 持ち主、スライド、版を 1 つの条件にして引く |
| 他人の R2 のオブジェクト | R2 のキーが、その版の接頭辞(`<版の ID>/`)の下にあるものだけ読む。行が別のキー(他人の版、画像)を指していても、読まない |
| 関係の向き | フォロー、ミュート、ブロック、管理者は、自分の側の行から引く。フォロワー、自分をブロックした人は引かない |
| トークン | `mcp_grants` の列は、名前と日時だけを引く |
| メールアドレス | 本人の `readEmail` だけ。`src/site/no-email-leak.test.ts` の対象は、設定と書き出しの 2 つのほかのまま |

## 人の確認として残るもの

- 本番の Worker の CPU 時間と、R2 の応答の遅さ。有料のプランで動いていること(subrequest の上限が 10,000 であること)。
- 実機のブラウザ(iOS の Safari を含む)で、zip のダウンロードが始まり、保存できること。
- macOS の「アーカイブユーティリティ」と Windows のエクスプローラーで、書き出した zip を開けること(開発の環境では、Info-ZIP と Python で確かめた)。
- 利用を止められている人の退会の確認に、書き出しのリンクを出すか([メールのコードでログインする](../features/f28-email-login.md) の未決事項)。止められていない人だけに出している。
