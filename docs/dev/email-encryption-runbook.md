# メールアドレスの暗号化の手順

[メールアドレスの暗号化の実装設計](f41-email-encryption.md) の鍵を、作って、登録して、控えを取り、既存の行を書き換え、入れ替えるための手順。鍵を作ること、登録すること、本番の行を書き換えることは、**依頼者が行う**(エージェントは行わない)。

この文書は、`docs/dev/deploy.md` の「メールアドレスの暗号化」の節になる。`deploy.md` の節の並び(作業 D)が決まる前に書いたので、いまは別のファイルに置いている。作業 Z が `deploy.md` にまとめ、運営の画面の枠が指す文書の場所(`src/operator/operations-email-frame.ts` の `GUIDE`)も、そのときに直す。

## 先に知っておくこと

- **鍵を失うと、だれもログインできなくなる。** 暗号化した行は、鍵がなければ開けない。メールアドレスを D1 の外に控えていないので、復旧する手段がない(控えが唯一の頼り)。鍵を失ったら、暗号化した利用者の行は、使えないまま残る。
- 3 つの secret(暗号の鍵、現在の版、検索用の鍵)は、**3 つ全部が要る**。一部だけ設定すると、設定が正しくないものとして、ログインが止まる(平文で書き始めることを防ぐため)。
- **検索用の鍵は、入れ替えない。** 変えると、暗号化した行が引けなくなる(全員が「初めての人」に見える)。この状態にならないよう、サービスは、暗号化した行が 1 つでもある環境で、検索用の鍵が合わなければ、新しい利用者を作らない。
- 暗号の鍵は、版を足して入れ替えられる(下の「鍵を入れ替える」)。
- ローカルと本番は、**別の鍵**にする。ローカルの D1 に本番の鍵で暗号化した行を入れない。本番の鍵を、リポジトリ、チャット、PR の本文に貼らない。

## 鍵を作る

暗号の鍵と、検索用の鍵は、どちらも 32 バイトの乱数。次のコマンドで、パディングなしの base64url にする(端末の履歴に残さないよう、値は画面に出さず、そのままコピーして使う)。

```sh
openssl rand -base64 32 | tr '+/' '-_' | tr -d '=\n'
```

3 つの値を作る。

| secret | 作るもの |
| --- | --- |
| `EMAIL_CIPHER_KEYS` | `1:<暗号の鍵>`。版を足したあとは `1:<鍵>,2:<鍵>` のように、コンマで並べる。版は 1 以上 9999 以下の整数 |
| `EMAIL_CIPHER_CURRENT` | 新しく書く版。最初は `1` |
| `EMAIL_LOOKUP_KEY` | 検索用の鍵。**暗号の鍵とは別の値**にする(同じ値だと、設定が正しくないものになる) |

## 控えを保管する

登録する前に、3 つの値を、パスワードマネージャーなど、サービスの外の、安全な場所に控える。版を足したときも、その都度、控えを更新する。**古い版の鍵は、その版で書いた行がなくなるまで、控えから消さない。**

## secret を登録する

```sh
pnpm exec wrangler secret put EMAIL_CIPHER_KEYS
pnpm exec wrangler secret put EMAIL_CIPHER_CURRENT
pnpm exec wrangler secret put EMAIL_LOOKUP_KEY
```

値は入力欄に貼る。`--var` と `wrangler.jsonc` の `vars` には、書かない(テストが `vars` にないことを確かめている)。

## 反映して書き換える

第四スコープの反映の順番(指示書の 06-DONE.md)の 3 と 7 に当たる。

1. 本番の D1 をバックアップする(`deploy.md` の「migration を含む変更を反映する」)。**この backup には、平文のメールアドレスが入る。** 書き換えても、取った backup は変わらない。保管先と保持期間(いつ消すか)を、先に決める。
2. 上の 3 つの secret を登録し、控えを保管する。
3. 変更を反映する(migration 0059、0060 が入る。列と索引を足すだけで、行は変えない)。
4. 運営の画面の「運用」の枠「メールアドレスの暗号化」を開く。「設定済み」と、鍵の版、平文の行の残りの件数が出る。「合いません」や「設定が正しくありません」が出たら、先へ進まず、鍵を確かめる。
5. 反映の直後から、新しく登録した人は暗号化して書かれる。すでに登録している人は、平文のまま、変わらずログインできる。
6. 「書き換える」を押す。押すたびに、最大 100 件ずつ進む。残りの件数が 0 になるまで、押す。途中で止めても、何度押しても、結果は同じ。失敗した行は、そのまま残り、次に押したときに扱われる。残りが減らないときは、ログの `email_rewrite` の `failed` を見る。
7. 0 になったら、確かめる。D1 に、平文が残っていないこと。

   ```sh
   pnpm exec wrangler d1 execute slide --remote --command "SELECT (SELECT count(*) FROM auth_user WHERE email_ciphertext IS NULL) + (SELECT count(*) FROM invited_emails WHERE email_ciphertext IS NULL) AS plain"
   ```

   結果が `0` であること。運営の画面の招待の一覧に、メールアドレスが表示されること。自分でログインできること。

## 平文が残る場所

書き換えが終わっても、次の場所には、書き換え前の平文が残る。

- 書き換える前に取った D1 の backup(保管先は依頼者が決め、決めた期間の後に消す)。
- D1 の Time Travel。保持期間のあいだ、書き換え前の状態に戻せるので、そのあいだ履歴に平文が残る。
- 作業 B が R2 へ書き出す D1 の写しがあれば、書き出した日までの平文(バケットの保持の期間に従う)。

これらを消すかどうか、いつ消すかは、依頼者が決める。サービスは、これらに触れない。

## 失敗の見方

「書き換える」を押しても平文の行が減らないときは、書き換えられない行がある。

1. ログの `email_rewrite`(`failed` の件数、`remaining`)を見る。`failed` が 0 でないのに残りが減らなければ、同じ行が失敗している。書き換える行は毎回無作為に引くので、少数の失敗する行が、ほかの行を止めることはない。
2. 失敗する行の多くは、同じメールアドレスの暗号化した招待または利用者がすでにある(組の状態がずれている)場合である。D1 で、平文の行と同じメールアドレスの `enc1:` の行が無いか調べる(メールアドレスをチャットに貼らず、手元で確かめる)。
3. 「合いません」が出るなら、鍵の取り違えである。先に鍵を直す。
4. 要求が 500 で止まったときも、もう一度押すと、続きから進む。

## 鍵を入れ替える

暗号の鍵を新しくするときは、**この順**に行う。順を変えると、前の版で書いた行が読めなくなる。

1. 新しい鍵を作り、控えに足す。
2. `EMAIL_CIPHER_KEYS` を、新しい版を足した値にする(例 `1:<前の鍵>,2:<新しい鍵>`)。`EMAIL_CIPHER_CURRENT` を、まだ変えない。
3. `EMAIL_CIPHER_CURRENT` を `2` にする。このあと新しく書く行は、版 2 になる。前の版 1 で書いた行は、そのまま読める。
4. 運営の画面で「古い版で暗号化した行」の件数を見て、「書き換える」を、その件数が 0 になるまで押す。書き換えた行は、版 2 になる。
5. 0 になったら、`EMAIL_CIPHER_KEYS` から版 1 を外す(例 `2:<新しい鍵>`)。版 1 の鍵は、控えから消してよい。外す前に、運営の画面が「古い版 0 件」と言っていることを必ず確かめる。

## 起きること

| 状況 | 何が起きるか | 直し方 |
| --- | --- | --- |
| 3 つとも未設定 | 今までどおり平文で動く。運営の画面に「未設定」。**暗号化した行が 1 つでもある環境では、新しい利用者を作らず**、ログインは止まる | secret を戻す |
| 一部だけ設定、形が違う、現在の版が鍵の中にない | ログインは 503。セッションは無いものとして扱う。運営の画面に、どの設定が正しくないかが出る | secret を直す |
| 鍵の値が間違っている(取り違え) | 運営の画面に「合いません」。ログインは失敗し、新しい利用者は作られず、書き換えは何も触れない。データは壊れない | 正しい値を登録し直す |
| 暗号の鍵の版を、行が残っているのに外した | その版で書いた人が、ログインできない(同じ版が足りないため)。ほかの人は無事 | 控えから版を戻す |
| 鍵を失った(控えもない) | **暗号化した行は、だれも開けない。** 復旧する手段はない | 利用者に再登録してもらう(行を作り直す作業が別に要る) |
| 検索用の鍵だけを失った | 暗号の鍵が残っていれば、全行を開けるが、新しい検索用の鍵で作り直す操作は、まだ用意していない | 依頼者と相談する |

## ローカルで試す

- 本番とは**別の鍵**を作る。リポジトリに入れない。`.dev.vars` に書くなら、`.dev.vars` が Git に入らないことを確かめる(`.dev.vars.example` に名前だけ載せてある)。
- 鍵を設定しないと、今までどおり平文で動く。鍵を設定すると、ログインで作った利用者は暗号化され、ローカルの送信箱(`mail_outbox`)の宛先は `enc1:` で始まる検索用の値になる。送信箱から、自分のコードを読むには、宛先を同じ形に直す必要があるので、ローカルのコマンドで読むときは、鍵なしで起動して使うのが簡単。
- ローカルの D1 を、本番の鍵で暗号化した行と混ぜない。

## ログに出るもの

足したコードのログは、`event` の名前、件数、エラーのコードだけである(`email_rewrite`、`email_rewrite_refused`)。メールアドレス、暗号文、鍵は、出ない(テストで確かめている)。
