# 仕様と issue の決まり

何を作るかは仕様に、いつ・どの単位で作るかは issue に書く。同じことを 2 か所に書かない。食い違ったときにどちらが正しいかを、読む人が迷わないようにする。

## どこに何を書くか

| 書くもの | 置き場 |
| --- | --- |
| 誰が、どんな場面で、何をして、どうなればよいか。作る範囲、作らないこと、受け入れ条件、決めたこと、未決事項 | `docs/features/fNN-*.md`(仕様) |
| 機能を作る順番と、段階ごとの完了条件 | [ストーリーマップ](../story-mapping.canvas) |
| 実装の設計(API、状態、データ、配信) | `docs/dev/fNN-*.md`、[設計の決まり](architecture.md) |
| ある作業で、どの受け入れ条件を満たすか。進み具合。残っている人の確認 | issue(作業票) |
| 変更の内容と、動いた根拠 | pull request |

それぞれの置き場が、その内容の正本である。何を作るかの相談はアーティファクトで行う(`discuss-feature` skill)が、アーティファクトは正本ではない。結論を、仕様と issue に書き写す。

issue に仕様を書かない。issue のコメントで受け入れ条件を足したり変えたりしない。変えるときは、仕様を変える PR を出す。

## 仕様を書く

feature の文書は、次の見出しを持つ(`scripts/check-docs.py` が検査する)。

| 見出し | 書くこと |
| --- | --- |
| 利用場面 | 誰が、どんな場面で、何に困るか。場面を書けない機能は作らない |
| 得られる結果 | その人が、どうなればよいか |
| 体験の流れ | 利用者の操作を、順に |
| 作る範囲 | 作るもの |
| 作らないこと | 落とした案と、その理由 |
| 受け入れ条件 | 満たしたかを確かめられる条件(下の決まり) |
| 未決事項 | まだ決まっていないこと。関わる受け入れ条件があれば、その ID を添える(「F17-AC15: 停止中の作者に何を見せるか」)。決まったら「決めたこと」に移す |

「決めたこと」の見出しは任意で、判断とその理由を書く。issue 番号を添えると、経緯をたどれる。

### 受け入れ条件

- 1 つの条件に、外から観測できる結果を 1 つ書く。「〜できる」「〜を返さない」のように、満たしたかどうかを確かめられる形にする。
- 条件ごとに ID を付ける。形は `F17-AC3`(機能番号 2 桁と、その機能の中の通し番号)。行の先頭に `- **F17-AC3** ` と書く。字下げした箇条書き(入れ子)にはしない。
- ID は変えず、使い回さない。条件をやめるときは、行を消さずに `- **F17-AC5** 削除。(理由)` と書き換える。番号が残るので、同じ ID が別の意味で使われない。
- 新しい条件には、その機能の一覧にある最も大きい番号の次を付ける。
- 条件の意味を変えるときは、古い条件を上の形で削除とし、新しい ID で書く。issue や PR が古い意味のまま参照し続けないようにするためである。
- 未決事項に ID が挙がっている条件は、決まるまで実装しない。

## issue を書く

issue は、仕様のどの受け入れ条件を、この作業で満たすかを決める作業票である。[テンプレート](../../.github/ISSUE_TEMPLATE/work.md)を使う。

- 作る前に、開いている issue と閉じた issue を検索する。同じ成果を扱う issue があれば、それを更新する。
- 1 つの issue は、1 つの PR(多くても、積み重ねた数本)で終わる大きさにする。受け入れ条件を 1 つも満たさない issue は、準備の作業であることを題名でわかるようにする。
- 「対象の受け入れ条件」には、ID だけを書く。条件の文を写さない。
- 「範囲」「範囲外」には、この作業で触るところと、同じ仕様のうち今回は触らないところを書く。「進め方」には、PR の分け方と順番を書く。「確認」には、受け入れ条件のほかに確かめること(既存の動作が変わらないこと、本番での確認など)を書く。
- 仕様に書かれていないことが必要になったら、issue に書き足さず、先に仕様を変える。作者の判断が要るなら、`discuss-feature` skill で相談する。
- 受け入れ条件と人の確認が残っている間は、閉じない。作らないと決めたときは、理由を書いて閉じる。

固まっていないアイデアは、[アイデアのテンプレート](../../.github/ISSUE_TEMPLATE/idea.md)で、わかっていることと、まだわからないことだけを記録する。作るかどうかは `discuss-feature` skill で相談し、作ると決まったら仕様に書いてから、作業の issue を作る。

## pull request を書く

[テンプレート](../../.github/pull_request_template.md)を使う。

- 満たした受け入れ条件の ID と、それを確かめた方法を対にして書く。
- 根拠は、実行したコマンドと結果、スクリーンショット、応答で示す。画面や配信を変えたときは、`verify-slide` skill で実際に動かす。
- 確かめられなかったことを、確かめたように書かない。「確かめていないこと」に書く。
- ローカルでは確かめられないもの([設計の決まり](architecture.md#人の確認が要るもの))は、「人の確認」に書く。
- 受け入れ条件を確かめるテストには、テスト名に ID を入れる(`F17-AC7: ...`)。あとから、条件ごとの根拠を検索できる。

## 状態

feature の文書の冒頭に、その機能の状態を 1 文で書く(いまの文書は「未実装の設計案」「実装中」「実装済み」「保留」などと書いている)。すべての受け入れ条件を満たし、人の確認が終わったら「実装済み」にする。条件ごとの進み具合は、issue と PR でたどる。
