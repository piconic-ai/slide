# プロフィールとプロフィール画像の実装設計

[メールのコードでログインする](../features/f28-email-login.md) のうち、プロフィールを書くこととプロフィール画像(F28-AC35〜F28-AC54)、[気になる人をフォローする](../features/f21-follow.md) のうちプロフィールに出るもの(F21-AC57〜F21-AC60)を実装するための契約。ログインと利用者の識別子は [メールのコードでログインする実装設計](f28-email-login.md) にある。

状態: 実装した(第二スコープの作業 A2、2026-11-22)。PR を 4 本に分けて積んだ。下の「PR の分け方」に、どの PR がどの条件を満たすかを書く。2026-11-24 に、プロフィール画像の縮小を Cloudflare Images の binding からブラウザに移した(F28-AC42〜F28-AC45、F28-AC85、F28-AC86 を削除し、F28-AC93〜F28-AC100 で書き直した)。2026-11-25 に、プロフィール画像の URL に版を付け、画像を変えた直後から、どのページにも新しい画像が出るようにした(F28-AC101、issue #366。下の「画像の版」)。

## データ

利用者の識別子は `auth_user.id`(サービスが発行する)。プロフィールの表は、すべてこの id を持つ。

| 表 | 列 | 決まり |
| --- | --- | --- |
| `profiles`(0037) | `user_id`、`name`、`bio`、`location`、`website` | 表示名は必須で 1〜50 文字。自己紹介は 160 文字まで、場所は 50 文字まで、Web サイトは 2048 文字まで。空の項目は、空文字でなく NULL で持つ。長さは表の CHECK でも守る |
| `profiles`(0042 で足す) | `use_gravatar` | 0 か 1。既定は 1(F28-AC47) |
| `profiles`(0048 で足す) | `gravatar_at` | 最後に Gravatar へ取りに行った時刻(秒)。まだ取りに行っていない人と、「Gravatar の画像を使う」を切った人は NULL。画像の版に使う(下の「画像の版」) |
| `profile_links`(0042) | `user_id`、`position`(1〜3)、`url` | SNS のリンク。書いた順。主キーは `(user_id, position)` なので、4 つ目は表にも入らない |
| `profile_pictures`(0043) | `user_id`、`uploaded_at` | アップロードした画像があるかを表す。画像の中身は R2 の `avatars/<user_id>` にある。`uploaded_at` は画像の版なので、0048 からはミリ秒で書く(それより前の行は秒のまま。版は、違うことだけが要る) |
| `picture_removals`(0043) | `id`、`user_id`、`removed_by`、`reason`、`removed_at` | 運営が画像を外した記録(F28-AC51)。外した後も残す |

migration は 0042(リンクと切り替え)、0043(画像と運営の記録)、0048(Gravatar を取りに行った時刻)の 3 本。どれも足すだけで、適用済みのファイルは変えない。

## 入力の検査(D-30)

`src/profile/profile-input.ts` は純粋な関数で、フォームの値を受け取り、保存できる値か、直す点の一覧を返す。直す点は、項目ごとの判別可能な union(`ProfileProblem`)で、文言は画面の側が日本語・英語で持つ。1 つ直すたびに次の点が出る、という往復をなくすため、問題は全部まとめて返す。

| 項目 | 決まり |
| --- | --- |
| 表示名 | 必須。前後の空白と、見えない文字(制御文字、ゼロ幅スペース、向きを変える記号)を取ると、1 文字以上 50 文字以下 |
| 自己紹介 | 160 文字以下 |
| 場所 | 50 文字以下 |
| Web サイト | 1 つ。`https:` の URL |
| SNS のリンク | 3 つまで。それぞれ `https:` の URL。空の欄は数えない |

- 長さは、コードポイントで数える(絵文字は 1 文字)。SQLite の `length()` も文字で数えるので、表の CHECK と食い違わない。ちょうどの長さは保存できる。
- 一行の項目は、見えない文字と改行を空白 1 つにし、空白の連続を 1 つにする。孤立したサロゲートは U+FFFD にする。絵文字の連結に使うゼロ幅の接合子(U+200C、U+200D)は残す。
- URL は、利用者が書いたとおりに `new URL` で読み、`https:` で、ホスト名に `.` があり、ユーザー名とパスワードがないものだけを受け付ける。scheme のない `example.com` は受け付けない(理由は「`https://` から書いてください」)。保存するのは、読み出した形(`href`)。2048 文字を超えるものは断る。
- 自己紹介は HTML として扱わない。保存した文字をそのままエスケープして出す(F28-AC40)。
- 保存した値も境界で検証し直す。読むときに、`https:` でない URL は「なし」にし、自己紹介は上限で切る。D1 を直接書き換えた値が、リンクにならないようにするため。
- 本文の大きさ: 1 つの項目から読むのは 1 万文字まで。それを超えるものは、切っても上限を超えているので、必ず断られる。SNS の欄は 50 まで読む。

### 自己紹介の改行

第二スコープでは、**改行を残す**(2026-11-25 に依頼者が決めた。それまでは暫定だった)。改行はすべて `\n` にそろえ、3 つ以上の連続は空行 1 つにする。行の前後の空白は取る。表示は `white-space: pre-line` で、自己紹介の中の改行だけが改行になる。扱いを変えるときは、`multiLineOf` を変える。

## プロフィールのページ

`profileCard` が、表示名、ハンドル、自己紹介、場所、Web サイト、SNS のリンクを出す。空の項目は、行も見出しも出さない(F21-AC60)。外へのリンクには、`rel="nofollow noopener noreferrer ugc"` を付ける。

## プロフィール画像

プロフィール画像は、アップロードした画像、Gravatar の画像、頭文字の順に使う(D-31)。決めるのはサービスの側で、ページには、プロフィール画像を配る経路の URL(`/avatars/<利用者の id>?v=<版>`)だけを載せる。メールアドレス、そのハッシュ、Gravatar の URL は、どのページの HTML、どの API の応答にも出さない(F28-AC48)。

| 場所 | 出し方 |
| --- | --- |
| ヘッダーのアイコン | `GET /api/session` が `avatarUrl` として版つきの経路を返し、`/share.js` が画像を重ねる |
| プロフィール、viewer の作者、フォローの一覧、設定 | サーバーが描く HTML に、頭文字の上へ `faceImage`(`src/profile/face.ts`)で画像を重ねる。どこも同じ部品を使う |

画像は、頭文字の上に重ねる。画像が 404 のとき(プロフィール画像が無い人)と読めないとき、`/share.js` が画像を隠すので、頭文字が見える。壊れた画像の印は出ない。お知らせと表紙のカードは、プロフィール画像を出さない。

### 配信の経路

`GET /avatars/:userId`(`src/profile/face-routes.ts`)。ログインは要らない。

1. `:userId` がサービスの id の形(英数字と `_`、`-`、64 文字まで)でなければ 404。メールアドレスの形(`@` や `.` を含む)は、ここで断る。
2. アカウントがなければ 404。人がいない場合と、プロフィール画像がない場合は、同じ 404 で、本文も空にする。id から、ほかのことが分からないようにする。
3. アップロードした画像があれば、R2 の `avatars/<id>` を返す。行があって物がないときは、次へ進む。
4. 「Gravatar の画像を使う」が入なら、Gravatar の画像を返す(下)。
5. どれもなければ 404。

応答は、画像だけを持つ。`Content-Type` は、保存した物の型が `image/png` なら `image/png`、それ以外(ブラウザで縮める前に保存した WebP、型のない物、ほかの型を名乗る物)は `image/webp` に固定する(`servedPictureType`、`src/profile/picture-policy.ts`。保存済みの値も信用しない)。`X-Content-Type-Options: nosniff`、`Content-Security-Policy: default-src 'none'; sandbox`。`Cache-Control` は、求められた版で決める(下の「画像の版」)。メールアドレスやハッシュは、ヘッダーにも出さない。

### 画像の版(F28-AC101)

画像を変えても、ブラウザが同じ URL で覚えた古い画像を出さないように、URL に版を付ける。以前は、設定のプレビューだけが `?v=<アップロードした時刻>` を付け、ヘッダー、プロフィール、フォローの一覧、viewer の作者は版のない `/avatars/<id>` を `public, max-age=60` で配っていた。そのため、変えてから 1 分の間は、ほかの場所に古い画像が出たり出なかったりした(issue #366)。

- URL は `facePath`(`src/profile/face.ts`、純粋な関数)だけが作る。プロフィール(`readProfile`)、ヘッダー(`/api/session`。`readProfile` の値)、viewer の作者、記事の下書きのプレビュー、フォローの一覧(`listPeople`)、設定は、どれもこの関数の URL を使う。
- 版は、すでに持っている値から、`faceSourceOf` が決めた顔の出どころで作る(`faceVersion`)。

  | 顔の出どころ | 版 | 変わるとき |
  | --- | --- | --- |
  | アップロードした画像 | `u<uploaded_at>` | アップロード(差し替えを含む) |
  | Gravatar(取りに行った後) | `g<gravatar_at>` | Gravatar へ取りに行き直したとき(画像は 24 時間、「無い」は 1 時間で取り直す) |
  | Gravatar(まだ取りに行っていない) | `g` | — |
  | なし(頭文字) | `n` | — |

  外す(本人、運営)と、行が消えるので `u…` から `g…` か `n` になる。「Gravatar の画像を使う」を切ると `n` になり、`gravatar_at` を NULL に戻す。入れ直すと `g` から始まる。
- 版の値は、それぞれの場所がもともと読んでいる query で読む。`readProfile` は `profiles` に `profile_pictures` を left join し、`listPeople` は一覧の query に `profile_pictures` の left join と列を足した。1 人ずつ問い合わせを増やさない。
- `gravatar_at` は、`/avatars/:userId` が Gravatar へ取りに行って答え(画像か「無い」)を R2 に保管したときに、保管した時刻で書く。応答しなかったときは書かない。保管済みの答えの時刻と D1 の値が違う(0048 より前に保管した答え)ときは、次に開かれたときに D1 を保管済みの時刻にそろえる。

`/avatars/:userId` の `Cache-Control` は、`faceCacheControl` が決める。

- 返す画像の版(配るその時点の出どころから作る)と、求められた `v` が同じときだけ、長く覚えてよい。アップロードした画像は `public, max-age=31536000, immutable`。その URL は、その画像だけを指す。
- Gravatar の画像は、版が合っても、サービスが Gravatar へ取りに行き直すまで(取りに行った時刻から 24 時間)の残りの秒数だけ覚えてよい(`public, max-age=<残り>`。`immutable` は付けない)。版は、だれかが画像を求めて取りに行き直したときにしか進まないので、1 年覚えさせると、Gravatar 側で画像を替えても、覚えたブラウザには古い画像が出続ける(本人のヘッダーも)。残りが 0 以下なら `no-cache`。
- それ以外は `no-cache`(毎回聞き直す)。版のない URL、いまの版でない URL(開いたままの古いページ、`/share.js` が前回の答えを覚えていて先に描く分)、`g`(まだ取りに行っていない。応答のときには取りに行った時刻があるので、版が合わない)、404。
- 版のない URL を短くする方を選んだ。版のない URL を外へ出す場所はない(oEmbed の応答と埋め込みのページは作者の名前だけで、プロフィール画像を載せない。MCP の応答にも載せない)。残るのは、版を付ける前に描いたページと、外から直接貼られた URL だけで、どちらも古い画像を出さないことを優先した。304 のための検証子(ETag)は付けていないので、`no-cache` の応答は毎回中身を送る。
- 404 も `no-cache` にした。画像がない人の 404 は、版が変わらないまま、あとで画像ができる(Gravatar を作った)ことがあるため。

版は公開のページの HTML に出る。そのため、だれでも、アップロードした時刻(ミリ秒)と、Gravatar の画像を使っているか(`u` と `g` の違い)を読める。以前これが出ていたのは、本人だけが見る設定のページだけだった。どちらも、画像そのもの(だれでも見られる)より多くを明かすものではなく、メールアドレス、その hash、Gravatar の URL は出さない(F28-AC48)ので、許すことにした。避ける必要が出たら、版を時刻の hash にする。

ヘッダーは、ページを読み込むたびに `/api/session` に聞き、答えの URL で描き直す。画像を変える操作(アップロード、外す、プロフィールの保存)は、どれもフォームの送信で、ページを読み直す。router がページの間を移すときは、ヘッダーは描き直さないが、読み込んだときにはすでに新しい版の URL を持っている。`/share.js` は、前のページで覚えた答えで先に描くので、読み込みの直後のわずかな間、前の版の URL の画像(ブラウザが覚えている古い画像)が出て、答えが来ると新しい画像に替わる。

確かめていないこと・限界:

- 同じミリ秒の中で、外してからアップロードし直すと、版が前のアップロードと同じになりうる。画面の操作では、ページを 2 回読み直すので起きない。
- 本番の Cloudflare の cache(CDN)は、Worker の応答を cache しない前提である。ブラウザの cache の動きは、`src/profile/picture-auto.browser.test.ts` で、Chromium・Firefox・WebKit の HTTP cache を通して確かめる(Playwright で request を横取りすると、ブラウザの HTTP cache が切れるので、このテストだけは横取りしない)。

### アップロード(D-34、F28-AC93〜F28-AC98)

プロフィール画像は、ブラウザが縮めてから送る(2026-11-24 の依頼者の決定。それまでは Cloudflare Images の binding で縮めていた。理由と採らなかった案は、仕様の「決めたこと」にある)。サービスは画像を復号も縮小もしない。

`POST /settings/picture`(multipart、同じ origin の form だけ、ログイン必須)。

- 先に、`Content-Length` が 512 KB に 64 KB を足した値を超えていれば、本文を読まずに断る。
- ファイルがない、または空なら「画像を選んでください。」。512 KB を超えるもの、次の検査に通らないものは、すべて「この画像は受け付けられませんでした。もう一度、画像を選んでください。」で断る(400)。ブラウザを通せば起きないことなので、理由を細かく分けて見せない。
- 検査は `cleanPicturePng`(`src/profile/picture-png.ts`、純粋な関数)。名前と、ブラウザが言う型は、見ない。
  - 512 KB 以下(`PICTURE_PNG_MAX_BYTES`。256×256 の 8 ビット RGBA を圧縮せずに書いても約 257 KB なので、色の情報を足しても収まる)。
  - PNG のシグネチャで始まる。
  - チャンクを先頭から 1 つずつ読む。長さが残りのバイトを超えない(2^32 近い長さの宣言も、足し算の前に比べるので、あふれず、確保もしない)、型が英字 4 文字、CRC が合う。チャンクは 1024 個まで(256×256 の PNG を 8 KB ずつの IDAT で書いても 64 個)。
  - 最初が IHDR(13 バイト)で、縦横がちょうど 256×256、ビット深度と色の型の組み合わせ、圧縮・フィルター・インターレースの方法が、PNG の仕様にあるもの。IHDR は 1 つだけ。
  - IEND で終わり、その後に何もない。IDAT が 1 つ以上あり、続いて並ぶ。PLTE は、色の型 3 では IDAT より前に 1 つ必要で、0 と 4 では許さない。知らない必須チャンク(型の 1 文字目が大文字)があれば断る。
  - 通ったものから、IHDR、PLTE、IDAT、IEND と、IDAT より前にある tRNS、sRGB、gAMA、cHRM だけを残し、ほかの補助チャンク(iCCP、tEXt、zTXt、iTXt、eXIf、tIME、pHYs、bKGD、acTL・fcTL・fdAT など)を取り除く。APNG は、最初の静止画だけが残る。
  - どの処理も、各バイトを定数回しか見ないので、時間は大きさに比例する(`src/profile/picture-png.performance.test.ts` で、16 倍の大きさの時間が 64 倍より小さいことを確かめる)。
  - 画素(IDAT の中身)は復号しない。中身の壊れた PNG は、配っても表示されず、`/share.js` が画像を隠して頭文字が出る。配る応答は `nosniff` と `sandbox` の CSP を持つので、画像のほかのものとして読まれない。
- R2 の `avatars/<id>` に、取り除いた後の PNG だけを、型 `image/png` で置く。元の画像は、サービスに届かない。同じ鍵に置くので、2 回目は 1 回目を置き換える。D1 の `profile_pictures` に、置いた時刻(ミリ秒。画像の版になる)の行を置く。物を先に置き、行を後にする。
- これまでに保存した WebP の画像は、そのまま残し、そのまま配る(F28-AC100)。作り直しや移し替えはしない。
- 外す操作は `POST /settings/picture/remove`。行を先に消し、物を後に消す。行が「プロフィール画像がある」ことの正なので、物の消し損ねは、だれにも読まれない。

### ブラウザで縮めて、選んだらすぐ送る(F28-AC87、F28-AC93〜F28-AC96、F28-AC99)

設定のファイル欄は、「画像を選ぶ」のピルのボタン(`label.picture-pick`)で包んだ `input[type=file]` で、input 自体は見えないが、キーボードと読み上げには残る。サーバーが描く HTML では、input は `disabled` で、ファイルを送るボタンはない。`<noscript>` の中に「スクリプトが動かないため、プロフィール画像を変えられません。…」の理由を置く。

`/share.js` の `bindPictureUpload` が、次のことをする。

1. ブラウザに `createImageBitmap`、`DataTransfer`、`canvas.toBlob` があれば、input の `disabled` を外す。なければ、欄の下に「このブラウザでは画像を縮められないため、…」を出し、欄は使えないままにする。
2. `change` で、種類(PNG、JPEG、WebP。ブラウザが種類を言わないときは読んでみる)と大きさ(1 MB)を先に確かめる。
3. `createImageBitmap(file, { imageOrientation: 'from-image' })` で読む(EXIF の向きを、ブラウザが表示する向きに合わせる。この値を知らない古いブラウザは `TypeError` を投げるので、指定せずに読み直す。既定でも画像の向きが使われる)。読めなければ「画像として読めませんでした。」、縦か横が 8192 ピクセルを超えれば「画像の縦か横が長すぎます」。
4. 中央の正方形(短い辺の長さ)を、256×256 の canvas に描き(`imageSmoothingQuality = 'high'`)、`toBlob(…, 'image/png')` で書き出す。PNG にするのは、Safari が WebP を書き出せず、JPEG は透明が黒くなるため。書き出し直すので、元のメタデータは残らない。
5. 書き出した PNG を `DataTransfer` で input の中身と入れ替え、フォームを `requestSubmit()` で送る。元のファイルは送られない。

問題があれば送らず、欄を空にして、理由を欄の下(`#picture-client-error`)に出す。文言は、`data-` 属性で渡された、ページの言語のもの。上限(256、8192、1 MB)も、`src/profile/picture-policy.ts` の値を `data-` 属性で渡す。読んで縮めて送っている間は、2 回目の選択を送らない(F28-AC87)。

### 片付け(F28-AC88、F28-AC89)

- 差し替え: 同じ鍵 `avatars/<id>` に置くので、前の画像は残らない。物を置いたあとに行を書けなかったときは、前に画像がなかった場合に限り、置いた物を消す(前の画像があるときは、行が前のままで、物は新しい。どちらも読まれる)。
- 外す: 行を先に消し、物を後に消す。行がなくても物を消すので、途中で止まって残った物は、外す操作(本人、運営)で片付く。
- 「Gravatar の画像を使う」を切る: 保管していた `gravatar/<id>` を消す。入のあいだは、期限(画像 24 時間、なし 1 時間)まで保管する。
- 退会: D1 の行と、R2 の 2 つの物を消す(上の「退会」)。
- 残るもの: `picture_removals`(運営の記録)。保管の期限が切れた `gravatar/<id>` は、次に開かれるまで物が残る(読まれず、開かれると置き換わる)。行のない `avatars/<id>` を、まとめて探して消す掃除は、作っていない。

## Gravatar(D-32、D-33)

「Gravatar の画像を使う」は、`profiles.use_gravatar`(既定は入)。アップロードした画像が無いときに限って使う。

- サービスが、Gravatar へ取りに行く。URL は `https://gravatar.com/avatar/<ハッシュ>?s=256&d=404`。ハッシュは、メールアドレスの前後の空白を取り、小文字にして、SHA-256 を 16 進で書いたもの([Gravatar の仕様](https://docs.gravatar.com/rest/hash/))。`d=404` を付けると、画像が無いとき Gravatar は 404 を返す。
- 答えは 3 つ: 画像がある(200 と画像)、無い(404)、応答しない(それ以外、接続の失敗、3 秒を超えた、画像でない型、1 MB を超える)。
- 取りに行った答えは、R2 の `gravatar/<id>` に cache し、その時刻を D1 の `profiles.gravatar_at` に書く(画像の版)。画像は 24 時間、「無い」は 1 時間(あとから Gravatar を作った人の画像が、1 時間で出るように)。「応答しない」は cache せず、古い画像が残っていればそれを返し、なければ 404(頭文字)にする。
- Gravatar へ送るのは、ハッシュだけである。読者のブラウザは、Gravatar へつながない。ページの CSP は広げない(`img-src 'self'` のまま)。

## 運営の画面

運営の画面(`admin.slide.community`、Cloudflare Access の内側)の「プロフィール画像を外す」で、その人のアップロードした画像を外せる(D-35)。ハンドルを入れ、理由を書く(必須)。外すと、`removePicture` を呼び、`picture_removals` に、外した運営の人、理由、時刻の行を残す。外した後は、Gravatar か頭文字に戻る。読者がプロフィール画像を通報する窓口は作らない(既存の通報の窓口で受ける)。

## 退会

退会すると、`profile_pictures` と `profile_links` の行、R2 の `avatars/<id>` と `gravatar/<id>` を消す。`picture_removals` は、運営の記録なので残す(中身は id、運営の人、理由、時刻で、画像もメールアドレスもない)。R2 は D1 のあとに消すので、途中で失敗しても、だれにも読まれない物が残るだけである。
