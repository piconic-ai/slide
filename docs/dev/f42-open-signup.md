# 招待なしで登録できるようにする実装設計

[招待なしで登録できるようにする](../features/f42-open-signup.md)(第四スコープの作業 R)を実装するための契約。設定の値、招待制のあいだと開いているあいだの違い、招待制を前提にした文言の一覧を書く。メールの全体の上限、登録の急増、登録の一時停止、新しい登録者の置く量、手順は、それぞれを入れる PR で、この文書に節を足す。

状態: 実装済み(第四スコープの作業 R)。本番では、2026-11-27 に招待制を外した(依頼者が secret `OPEN_SIGNUP` を入れた。issue #466)。

## 設定の値

| 設定 | 既定 | 意味 |
| --- | --- | --- |
| `OPEN_SIGNUP` | 無い | 値が `on` のときだけ、招待が無くても登録できる。それ以外(無い、空、`off`、`ON`、`true`、`1`、打ち間違い)は招待制のまま |

- 値は `wrangler.jsonc` の `vars` に書かない。書かなければ招待制のままである。本番では、secret として入れる(`wrangler secret put OPEN_SIGNUP`。[外し方と戻し方](#外し方と戻し方))。secret を変えると、build なしで、Worker の新しい version がすぐに出る。Cloudflare の画面から平文の値として入れてはいけない。リリースのたびの `wrangler deploy` が、`wrangler.jsonc` に無い平文の値を消し、気づかないうちに招待制に戻る(`keep_vars` を使っていない)。運営の画面からは変えられない(画面は、いまの値を見せるだけ)。
- 読み方は `src/auth/signup-mode.ts` の `signupModeOf` 1 つ。間違いは「開く」側に倒れない(D-125)。
- ローカルで確かめるときは、`OPEN_SIGNUP` を環境変数で入れて起動する(`.dev.vars` に書いてもよい。秘密ではない)。ログインのコードは `MAIL_OUTBOX=on` で `mail_outbox` に書かれる。確かめる順番は[ローカルで両方の値を確かめる](#ローカルで両方の値を確かめる)にある。

## 招待制のあいだと開いているあいだ

変わるのは、ログインのコードを送る判断と、コードで入れる判断だけである。登録の流れ(コード → `/welcome` で規約への同意、ハンドル、表示名)は同じである(D-126)。

| | 招待制(既定) | 開いている |
| --- | --- | --- |
| 招待の一覧に無いアドレスに、コードを送る | 送らない | 送る |
| 招待の一覧に無いアドレスが、正しいコードで入る | 入れない | 入れる。入ると、招待の一覧に、サービスの名前(`open-signup`)で載る |
| 画面の答え | どのアドレスにも「コードを送りました」(F28-AC7) | 同じ |

判断は `admitsSignIn(state, standing)`(`src/auth/signup-mode.ts`、純粋)の 1 つ。`state` は設定の値と、運営が止めているか。`standing` は、そのアドレスが招待されているか、登録しているか(止めているあいだの判断は[新しい登録を止める](#新しい登録を止める))。どちらの立場も、どの値のときも、どのアドレスにも同じ問い合わせで読む。値によって問い合わせの数が変わると、処理の長さが違いから、アドレスの状態が読めてしまうためである(F28-AC9)。

### 開いているあいだに登録した人は、招待の一覧に載る

「この人は使ってよいか」の判断は、第一スコープからずっと、招待の一覧と利用者を突き合わせる 1 つの問い合わせ(`invitedUserIds`)である。セッション、アップロード、AI エージェント、作者限定の閲覧が、これを使っている。開いているあいだに入った人のために別の仕組みを足すと、これらすべてに手が入る。そこで、入った人を、招待の一覧に載せる。

- 載せるのは、`/login/code` が `signInEmailOTP` で利用者とセッションを作ったあと。運営の招待と同じ `addInvite`(`src/auth/invites-store.ts`)を通す。
- `invited_by` は `open-signup`。運営の招待は運営のメールアドレスが入るので、`@` の有無で見分けられる。列は足さない。
- 運営の画面の招待の一覧(`listInvites`)には出さない。登録した人であって、招待ではなく、数が増えると一覧が埋まるためである。外した人を使えなくするには、招待の一覧ではなく、停止を使う(運営が同じアドレスの招待を外すと、その行は消える)。
- 運営が、`open-signup` の行があるアドレスを招待すると、その行は運営の招待になる(`addInvite` の takeOver)。退会のときに消えなくなる。
- 設定を招待制に戻しても、行は残る。外しているあいだに登録した人は、そのまま使える(F42-AC4)。コードを入れる前の人(`/welcome` の途中)は、戻したあとも、登録を終えられる。
- 行はメールアドレスを持つので、持つのは、使っている人のあいだだけにする。
  - 登録せずに終了したとき、毎時の掃除が登録の途中の人を消したとき(`leaveBeforeSignup`): `open-signup` の行を、利用者の行より先に消す。運営の招待は消さない(F28-AC64)。
  - 退会したとき(`markAccountDeleted`): 同じ。運営の招待は残す。
  - サービスが落ちて、利用者を作ったあとの `addInvite` まで進めなかったとき: 利用者はセッションを持つが、招待が無いので、次の要求で締め出され(`uninvited`)、掃除が消す。開いているあいだなら、もう一度ログインすると、また載る。

## メールの全体の上限

同じアドレスと同じ接続元の上限([メールのコードでログインする実装設計](f28-email-login.md))に加えて、サービス全体の上限をかけられる(D-127、F42-AC25〜AC28)。**既定では無効である**(2026-11-26、依頼者の決定。F42-AC29。[決めたこと](../features/f42-open-signup.md#決めたこと))。招待制をすぐ外す予定で、ログインしやすいことを優先するためである。送りすぎが問題になったら、設定で有効にする。仕組みは残してあり、コードを書き直さずに済む。

| 設定 | 既定 | 意味 |
| --- | --- | --- |
| `LOGIN_CODE_LIMITS.total` | 無い(無効) | 窓(`windowSeconds`。既定 1 時間)のあいだに、全員が請求できるコードの数。1 以上の整数で有効になる。無い、または 0 は無効。誤った値(負、小数、文字、上限 100 万超)は、設定の全部を捨てて既定に戻す(同じアドレス・同じ接続元の上限も既定に戻り、全体の上限は無効) |

- **無効のとき**: 請求を全体として数えない。`tryRecordRequest` の SQL から全体の数え方を外し(`perTotal` が `null`)、`readRequests` は全員の行を読まず、`reportMailFlood` は数えも通知もしない。`login_code_requests` に増える行は、これまでどおり請求 1 件につき 1 行(アドレスと接続元の上限のための行)だけで、全体のための行は無い。同じアドレスと同じ接続元の上限(F28-AC13、AC14)は変わらない。
- **誤った値を無効に倒す理由**: 誤った値で上限が「効いたまま」になると、ログインしやすさを優先した決定に反して、気づかないうちにログインを止める。かといって、誤った値で別の上限(同じアドレス・接続元)を広げると、守りが緩む。そこで、誤りは設定の全部を捨てて既定に戻す。既定は、同じアドレス・接続元の上限が効き、全体の上限は無い、という形で、「何も設定しなかったとき」と同じである。誤りが、何も設定しないときより緩くなることはない。
- **有効のときの数える場所**は、同じアドレスと同じ接続元の上限と同じ(`login_code_requests` の `send` の行。`tryRecordRequest`)。数えることと記録することは 1 つの SQL なので、同時に来た要求が、1 つしか入らない隙間を、そろって通ることはない。窓の外の行は、記録のたびに消える。
- 数えるのは、記録した(通した)請求である。招待されていないアドレスや、新しい登録を止めているあいだの未登録のアドレスの請求も数える。数えるかどうかがアドレスの状態で変わると、上限に達した画面が、アドレスの状態を教えてしまうためである(F42-AC26)。その分、メールの数より少し多めに数えることになり、上限は安全な側に働く。
- 招待制のあいだも、有効にしていれば、同じ上限がかかる。
- 上限に達すると、次の請求は断る。画面は「しばらくしてからやり直してください」、状態は 429、`Retry-After` は、窓にある新しい `total` 件のうち、いちばん古いものが窓を出るまでの秒数。どのアドレスにも同じである(F42-AC26)。アドレスごと、接続元ごとの上限に当たったときは、これまでどおり、いつ以降に請求できるかを出す。
- すでにコードを持つ人がコードを入れること(`/login/code`)は、この上限の対象にしない。数えるのは請求だけである。
- 80% に達したら、すぐの通知(`mail_flood`)を送る(F42-AC27)。請求のたびに、直近 1 時間の請求の数を数え、`total` の 80% を切り上げた数以上なら、通知の口を呼ぶ。同じ種類の通知は 1 時間に 1 回に間引かれる(D-58)。上限に達して断ったときも呼ぶ。通知は、件数と、運営の画面の「新しい登録」の枠へのリンクだけを持つ(アドレスも IP アドレスも入らない)。**全体の上限が無効のあいだは、この通知は出ない**。
- 数える索引は migration 0065(`login_code_requests (kind, requested_at)`)。

### 有効にする手順

1. 環境の値 `LOGIN_CODE_LIMITS` に `total` を足す(例: `{"total":100}`。ほかの値を入れているときは、その JSON に足す)。**どこに書くかは、まだ決まっていない。** この値は JSON のオブジェクトとして読む(`parseLoginCodeLimits`)。secret は文字列で渡るので、secret に入れた JSON は誤った値として捨てられ、既定に戻る。Cloudflare の画面から入れた平文の値は、次のリリースで消える。いまの作りで残るのは、`wrangler.jsonc` の `vars` に書いてリリースで出す形だけである。有効にするときに、依頼者に確かめる。
2. [通常の手順](deploy.md)で deploy する。コードの変更は要らない。
3. 戻すには、`total` を消す(または 0 にする)。
4. 数を決める目安: メールサービスの送信の上限より小さくする。決めるのは依頼者で、実測を見てから。

### 既知の危険(全体の上限)

**既定で無効にしたので、次は起きない。有効にしたときの危険として残す。**

- 全体の上限は、メールを送らない請求(招待されていないアドレス、止めているあいだの未登録のアドレス)も数える。数えるものを「実際に送ったもの」に絞ると、上限に達したとき、登録済みの人だけが 429 になり、画面の違いから登録の有無が分かってしまう(F42-AC26 を守れない)。そのため、数えるのは全部の請求にしてある。
- その結果、有効にしているあいだは、**匿名の請求だけで上限を使い切れる**。1 接続元は 1 時間に 20 通まで(接続元の上限)なので、数個の接続元から、全体の `total`(例 100 通)に届く。届くと、登録している人も 429 になる(1 時間で解ける)。
- 有効にしていないあいだは、全体としての歯止めが無い。防ぎは Turnstile(請求ごとに確かめる)と、同じアドレス・同じ接続元の上限だけである。接続元を変えて請求し続ける人は、メールの送りすぎを起こせる。備え: `mail_flood` は出ないので、気づく手がかりは、ログインのメールの送信失敗の通知(F39-AC1)と、メールサービス側の上限・料金の知らせである。「新しい登録を止める」で新しい登録を止め、接続元の上限(`perSource`)を下げ、必要なら `LOGIN_CODE_LIMITS.total` を設定して有効にする。

## 登録の急増

新しい登録(`accounts` の行ができたこと。`/welcome` で作る)を数え、急に増えたら、すぐの通知(`signup_surge`)を送る(D-128、F42-AC10)。

| 設定(`ALERT_THRESHOLDS`) | 既定 | 意味 |
| --- | --- | --- |
| `signupSurgeFactor` | 10(仮) | 直近 1 時間の登録が、その前の 7 日の 1 時間あたりの平均のこの倍数を超えたら |
| `signupSurgeMinimum` | 10(仮) | 上のとき、直近 1 時間に、この人数以上いることも要る |

- 「超えた」は `直近 1 時間 × 168 > 倍数 × その前の 7 日の人数` で決める(割らないので、丸めで決まらない)。「その前の 7 日」は、直近 1 時間を除いた 168 時間で、急増そのものが基準を押し上げない。前の 7 日が 0 人なら、最小の人数だけで決まる。
- 数えるのは `accounts.created_at`(登録した時刻)。招待制のあいだに運営が招いた人の登録も数える。判断は登録のたびに行う(1 時間ごとの cron は足さない)。判断は `signupSurgeNotice`(`src/alerts/signup-notices.ts`、純粋)、数えるのは `readSignupCounts`(`src/auth/signup-count-store.ts`)、つなぐのは `reportSignupSurge`(`src/alerts/signup-alert-routes.ts`)。通知に、メールアドレスも利用者の名前も入らない。
- 数える索引は migration 0065(`accounts (created_at)`)。

## 新しい登録を止める

運営の画面の「運用」、「新しい登録」の枠に、「新しい登録を止める」と「再開する」を置く(D-129、F42-AC11〜AC16)。招待制かどうか(`OPEN_SIGNUP` の値)は、枠が見せるだけで、変えられない。

- 状態は D1 の `signup_pause_events`(migration 0066)。押すたびに 1 行足し、いまの状態は、いちばん新しい行の `paused`。行が無ければ止めていない。行は、押した時刻と、Cloudflare Access が確かめた運営のメールアドレスを持つ(停止と非表示の操作者と同じ持ち方)。押しても状態が変わらないとき(止めているときにもう一度止める、など)は、行を足さない。確かめることと足すことは 1 つの SQL なので、同時に押しても 1 行である(`setSignupPause`)。
- 押す経路は運営の origin だけ(`POST /operations/signups/pause`、`/resume`)。Cloudflare Access の確認を通り、`Origin` がその origin でなければ 403 にする。公開の origin には、この経路が無い。ログには「止めた」「再開した」と結果だけを出し、運営のアドレスは出さない。
- 「新しい登録」とは、アドレスが**登録していない**人にコードを送り、その人を入れること、そして `/welcome` で登録を終えることである。止めているあいだの判断は `admitsSignIn(状態, 立場)`(`src/auth/signup-mode.ts`)の 1 つで、立場は「招待されているか」と「登録しているか」。
  - 登録していないアドレスは、招待の有無にかかわらず、どちらの値のときも、コードを送らず、コードで入れない(F42-AC12)。招待されていても、まだ登録していない人は、新しい登録に当たる。
  - 登録している人(利用者の行があり、アカウントがある人)は、これまでどおり(F42-AC13)。招待制のときに、招待を外された人が入れないことも変わらない。
  - 「登録している」は、利用者の行を、招待と同じ引き方(サービスがそろえた表記のメールアドレス)で探し、アカウントがあるかを見る(`isRegistered`、`src/auth/registered-store.ts`)。
  - コードを入れる前の人が登録を終えること(`POST /welcome`)も止める。止めているあいだは、アカウントを作らず、503(`X-Slide-Intended: signup_paused`。5xx の警報に数えない)と、止めている旨を返す。再開すれば、同じ画面で続けられる。すでに登録している人は、これまでどおり進む。
- 画面は、アドレスが登録済みかどうかで変わらない(F42-AC14)。
  - ログインの画面は、止めているあいだ、だれに対しても、説明の下に「新しい登録を一時的に止めています。登録済みの方は、これまでどおりログインできます。」と出す。コードを送ったあとの画面と、コードを間違えたあとの画面にも、同じ注意を出す。止めていないときは出さない。
  - 立場の問い合わせ(招待されているか、登録しているか)は、止めているか、どの値かにかかわらず、どのアドレスにも 2 つとも行う。メールを送る処理は、応答のあとに回す(F28-AC9)ので、応答の長さから、送ったかどうかは読めない。コードの行と請求の記録の数も、どのアドレスでも同じ(テストで数える)。
  - 止めていても、コードを入れる側(`/login/code`)の画面は、立場を教えない。コードを受け取っていない人は、どのアドレスでも、同じ「違います」「使えなくなりました」を見る。
  - 残る差: 応答の長さのわずかな違い(利用者の行があるか、メールを組み立てたか)は、応答のあとの処理の中にある。応答にかかる時間でも見分けにくいことは、「確かめる条件」の自動のテストでは確かめられない。実機での計測は、セキュリティのレビューで見てもらう。
- 戻す: 「再開する」を押す(F42-AC15)。止めているあいだに断られた人は、もう一度請求すればよい。止めているあいだにコードを請求した未登録のアドレスには、コードの行だけが残り、10 分で消える。
- 運営の画面の枠は、`src/operator/operations-signups-frame.ts`(純粋)、読む `operations-signups-store.ts`、押す `operations-signups-routes.ts`。「新しい登録を止める」「再開する」は、枠のいちばん下に、ほかのボタンと並べずに 1 つだけ置く(F42-AC16)。枠は、直近 1 時間と 24 時間の登録の数(`accounts.created_at`)も出す。

## 新しい登録者の置く量

登録から 7 日のあいだは、1 日(直近 24 時間)に新しく置けるスライドを 3 本までにする(D-130、F42-AC17〜AC22)。「1 日」は直近 24 時間(ローリングの窓)である(2026-11-26、依頼者の判断。[決めたこと](#決めたこと))。

| 設定 | 既定 | 意味 |
| --- | --- | --- |
| `NEW_AUTHOR_LIMITS.days` | 7(仮) | 登録(アカウントを作った時刻。`accounts.created_at`)から何日間を「新しい人」とするか。7 日ちょうどで外れる(F42-AC21) |
| `NEW_AUTHOR_LIMITS.perDay` | 3(仮) | 直近 24 時間に新しく置ける本数(F42-AC22) |

窓の長さ(24 時間)は設定の値にしない。決めたことであり、`placementWindowOf`(`src/uploads/new-author-limits.ts`。純粋)が窓を返す唯一の場所である。ヘルプの記事(`slides/daily-limit`)の「24」も、この関数の値から差し込む(`helpNumbers().newAuthorWindowHours`)。

- **どこにかかるか**(F42-AC20): 新しいスライドを始めるときの `startUpload`(`src/uploads/api.ts`)の 1 か所。ブラウザの画面、ドロップ、AI エージェント(`put_slide` など)は、どれもここを通る。断ったときはスライドも版も作らない。
- **数えるもの**(F42-AC19、F42-AC30): その人の `decks` の行のうち、作られた時刻が窓 `(now - 86400, now]` の中で、かつ次のどちらかを満たすもの。(1) ready の版を持つ(その後に消したものも数える)。(2) 最初のアップロードが続いている(期限内の `uploading`)。最初のアップロードが失敗した・期限が切れた・やめたスライドは、版を持たないので数えない(`releaseEmptySlides` が、次の開始のたびに、そのようなスライドを消した印にする。`createSlide` のコメントのとおり、数えない)。この条件は `countedNewSlides`(`src/uploads/new-author-store.ts`)の 1 か所にあり、`INSERT` の `WHERE` と `readNewSlideTimes` が同じものを使う。続いているアップロードを数えるのは、同時に始めた請求が、まだ版を持たないスライドを数え損ねて、上限を超えないようにするためである。窓は半開で、ちょうど 24 時間前に作った 1 本は窓の外である。これは「いつから置けるか」の時刻と同じ瞬間で、その時刻になれば置ける。1 本のスライドは、作った時刻で 1 回だけ数える。新しい版は、同じスライドの行に足されるだけなので、数えない。消したスライドも数える(消して置き直しても、枠は空かない)。以前に始めた同じ試行を繰り返す(再送)のは、新しいスライドではないので、ここを通らない。
- **新しい人か**(F42-AC21): `isNewAuthor`(純粋)。アカウントが無い人は「新しい人」ではなく、これまでの作者の確認(招待と停止)が先に断る。招待制のあいだに登録した人にも、同じにかかる(招待された人を外す、という分け方はしない)。
- **いつから置けるか**(F42-AC18): 窓の中の本数が `perDay` に達していたら断る。時刻は、窓の中で `perDay` 番目に新しい始めの時刻の 24 時間後(窓の中がちょうど `perDay` 本なら、いちばん古い始めの 24 時間後。設定を下げて `perDay` を超える本数があるときは、本数が `perDay` 未満になるまで待つ必要があるので、いちばん古いものではない)。`decidePlacement`(純粋)が出す。
- **断り方**: 429、コード `new_author_limit`、`availableAt`(いつから置けるか。秒)。ブラウザのドロップは 429 を、ふつうは間隔をあけて再試行するが、このコードは再試行しない。

### 同時に始めても上限を超えない作り

`guardNewAuthor` は、数を読んで断りの文を作るための先読みである。数えることと作ることは、`insertDeckWithSession`(`src/uploads/start-store.ts`)の `INSERT` の `WHERE` に、窓の中の数える `decks` の本数(`countedNewSlides`)が `perDay` 未満である、という条件を入れて、1 つの文にしてある(全体の上限の `tryRecordRequest` と同じ作り方)。同時に始めた請求が、そろって先読みを通り抜けても、作れるのは `perDay` 本までで、作れなかった請求は 0 行になり、`createSlide` が同じ `new_author_limit` を返す。`src/uploads/new-author.test.ts` が、同時に 50 本始めても 3 本までしかできないことを、ローカルの D1 と HTTP で確かめる(`WHERE` の条件を外すと、20 本できて、このテストが落ちる)。migration は足さない。窓は `decks` の既存の列(`owner_user_id`、`created_at`)で数える。

### 断りの文(画面と AI エージェント)

- **画面**(`src/drops/text.ts` の `newAuthorLimit`): 「今日はこれ以上置けません。登録して間もないあいだは、新しいスライドを置ける本数に上限があります。(日時)(日本時間)から、また置けます。」(英語は “You can't put up any more today.”)。時刻は `src/share/dates.ts` の `dayTimeFormats`(日本時間)で書く。ヘルプの記事の見出しの言葉と同じにしてあり、`src/help/screen-words.test.ts` が、記事の引用が画面の言葉にあることを確かめる。理由の下に、記事 `slides/daily-limit` へのリンクが付く(`src/drops/help-place.ts`)。
- **AI エージェント**(`src/mcp/refusal.ts`): 断りの符号 `new_author_limit` と、理由の文に「いつ以降に始められるか」(UTC の ISO 8601)を足した文を返す。同じ瞬間を、画面は日本時間で、AI エージェントは UTC で書く。`help` に `slides/daily-limit` の URL が付く(`src/mcp/refusal-help.ts`)。
- **`not_registered`**: ドロップの画面は、いままでの「いまは、このアカウントではスライドを受け取れません。」ではなく、理由(いまは作者として登録されていない)と、ログインし直しても同じときはお問い合わせを、出す。「招待」の語は出さない(F42-AC5)。AI エージェントの断り(`UploadRefusal`)は、`not_registered` を `not_allowed` にまとめず、符号をそのまま渡す。

3. 画面と AI エージェントの断りの文、ヘルプの記事、ドロップの理由からのリンク。保留にしていた `test.todo` は、本物のテストにした。

D-130 は「1 日に 3 本」と書き、「1 日」の数え方を書いていなかった。次のとおり決まった(2026-11-26、依頼者の判断)。

| 選択肢 | いつから置けるか(F42-AC18 の表示) | 長所 | 短所 |
| --- | --- | --- | --- |
| **A. 直近 24 時間(採用)** | 窓の中でいちばん古い新しいスライドの 24 時間後 | 区切りの時刻が無く、日付の変わり目に 6 本置けてしまう穴が無い。時刻帯を決めなくてよい。「いつから」が、利用者の 1 本目から数えて自然に出る | 「毎日リセット」より、説明が少し長い |

## 既知の限界

- **`+` タグの別アドレス**: `a+1@gmail.com` と `a@gmail.com` は、別のアドレスとして扱う(F28 の決まり。招待した綴りだけが招待される)。開いているあいだは、同じ人が `+` タグを変えて請求できるので、アドレスごとの上限(1 時間に 5 通。F28-AC13)は、同じ人に対して事実上効かない。実際に効くのは、1 接続元 20 通/時(F28-AC14)と全体 100 通/時である。F28-AC13 の「同じアドレス」の意味を変えないため、実装は変えていない。他人の受信箱に、1 接続元から 20 通/時まで送らせられる点に注意する。
- **新しい人の判定の回避**: 新しい登録者の置く量(F42-AC19〜AC21)は、アカウントを作った時刻で決まる。`+` タグの別アドレスで登録し直すと、別の「新しい人」として、また枠を使える。
- **停止された人の入り直し**: 停止は、アカウント(ハンドル)に対して行う。停止された人が、退会して別のアドレス(`+` タグを含む)で登録し直すのを、止める仕組みは、まだ無い。停止リスト(アドレスを正規化して HMAC で持つ。[知らない人のスライドも、安心して開ける](../features/f17-safe-viewing.md) の F17-AC37〜F17-AC43)は、開いたあとに作ると決めた(2026-11-27。issue #466)。本番に入るまでは、入り直した人を、運営がもう一度ハンドルで停止する。

## 手順

### 外す前に確かめること

本番で招待制を外すかどうかは、依頼者が決める。外す前に、次を済ませる(第四スコープの「人の確認」のうち、この作業に関わるもの)。2026-11-27 に外したときの確認の記録は、issue #466 にある。

1. **ログインのメール**: Turnstile(`TURNSTILE_SITE_KEY`、`TURNSTILE_SECRET`)と、メールサービスが入っていること。**開いているあいだは Turnstile が必須**(請求ごとの唯一の防ぎ。[既知の危険](#既知の危険全体の上限)と[既知の限界](#既知の限界)の `+` タグ)なので、開く前に、本番の `/login` に Turnstile の枠が出て、値が無い・誤った請求が断られることを確かめる。全体の上限は既定で無効である。送りすぎが問題になったら、`LOGIN_CODE_LIMITS.total` を設定して有効にする([有効にする手順](#有効にする手順)。登録の一時停止も使える)。有効にするなら、メールサービスの送信の上限より小さい数にする。
2. **通知**: Discord の webhook を登録し、`signup_surge`(と、全体の上限を有効にするなら `mail_flood`)が届くことを、ローカルで確かめた設定と同じ形で確かめる([通知の手順](alerts-runbook.md))。
3. **停止の手順**: 運営の画面の「新しい登録」の枠が開き、「新しい登録を止める」「再開する」を、いったん押して戻せること(本番で押してよい。登録している人のログインは止まらない)。
4. **規約**: 規約とプライバシーポリシーを仕上げ、施行日を入れていること。招待なしで登録する人が、同意の画面(`/welcome`)から、規約とプライバシーポリシーのページへ行けること。
5. **仮の数**: 登録の急増のしきい値、登録から 7 日間の置ける本数は、どれも仮の値。実測がないので、開いた最初の週は、運営の画面の数と通知を見て、設定で直す。
6. **新しい登録者の置く量**: 登録から 7 日のあいだ、直近 24 時間に新しく置けるのは 3 本まで(F42-AC17、AC18)。これは仮の数で、設定(`NEW_AUTHOR_LIMITS`)で変える。荒らしの置き方は、この上限に加えて、通報と運営の非表示・停止で抑える。

### 外し方と戻し方

値は、本番の secret として入れる(2026-11-27、依頼者の決定)。入れるのも消すのも、依頼者が行う。

- 外す: 次を実行し、入力欄に `on` と打つ。値は `on` だけが開く。余分な空白や改行が入ると、招待制のままになる。

  ```sh
  pnpm exec wrangler secret put OPEN_SIGNUP
  ```

- 戻す: 次を実行する。開いているあいだに登録した人は、そのまま使える。使えなくするには、停止を使う。

  ```sh
  pnpm exec wrangler secret delete OPEN_SIGNUP
  ```

- secret を変えると、build なしで、Worker の新しい version がすぐに出る。リリースの反映の途中では切り替えない(`MAINTENANCE` と同じ。[メンテナンス](deploy.md#メンテナンス作業-n)の注意)。
- secret は、リリースをまたいで残る。Cloudflare の画面から平文の値として入れると、次のリリースの `wrangler deploy` で消えて、招待制に戻る。
- 切り替わったことは、運営の画面の「新しい登録」の枠と、`/login` の説明(開いているときは「はじめての方は、コードを入力したあと、利用規約に同意して登録します。」)で確かめる。
- 戻すと、運営の画面の「新しい登録」の枠は「招待制」と出す。

### 荒らしが来たとき、最初にすること

通知(`mail_flood`、`signup_surge`)や通報が来たら、この順にする([通知の手順](alerts-runbook.md)、[不正なスライドの知らせに対応する](abuse-response.md))。

1. **登録を止める**: 運営の画面の「運用」、「新しい登録」の枠の「新しい登録を止める」。登録していない人にコードが送られなくなる。登録している人は、ログインできる。
2. **非表示にする**: 通報されたスライドを、運営の画面の「スライドを非表示にする」で隠す。迷うときは、先に隠す。
3. **停止する**: 同じ人が繰り返すとき、運営の画面の「アカウントを停止する」。
4. 落ち着いたら「再開する」。止めているあいだに断られた人は、もう一度請求すればよい。
5. 全体の上限を有効にしていて、それに達して「しばらくしてからやり直してください」が出ているとき、登録している人もコードを請求できない。窓(1 時間)が過ぎれば解ける。急ぐときは、`LOGIN_CODE_LIMITS` の `total` を上げて(または消して)、リリースで出す。無効にしているとき(既定)は、この断りは出ない。

通報から運営の操作まで(D-131)は、通報 → 翌日のメール(件数と運営の画面へのリンク)→ 運営の画面の通報の一覧 → 非表示 → 停止、と通してテストしてある(`src/operator/abuse-flow.test.ts`)。足りない操作は、足さずに、次の「足りない操作」に挙げた。

### 足りない操作

通しの確認 14 の「運営の画面から、コンテンツの非表示と、登録者の利用の停止ができる」は、できる。ただし、招待なしで登録する人が増えると、次が不便になる。足さずに報告する(D-131)。

- アカウントを探す手がかりが、ハンドルだけである。メールアドレスから、人を探せない。
- アカウントを持たない利用者(登録の途中で止まった人)は、停止できない。停止は、ハンドルで指す。
- 通報は、スライドごとである。人を通報する、新しい登録者の一覧(新しい順)から選ぶ、といった入口が無い。運営の画面の「新しい登録」の枠が出すのは、直近 1 時間と 24 時間の数だけである。
- 停止した人は、アカウントを消して(退会して)、別のアドレスで登録し直せる。停止リスト(アドレスの HMAC を持ち、登録を断る)は、開いたあとに作ると決めた(2026-11-27。issue #466)。

## ローカルで両方の値を確かめる

[アップロードを試す](f01-local-slice.md)の起動と同じ設定(`PUBLIC_ORIGIN`、`BETTER_AUTH_SECRET`、`MAIL_OUTBOX=on`)で起動し、`OPEN_SIGNUP` だけを変えて 2 回通す(D-133)。本番の値には触れない。

1. **値を付けずに起動する**(招待制)。`/login` に、招待制と読める説明が出る。運営の画面で入れていないアドレスでコードを求めても、画面は「コードを送りました」で、`mail_outbox` に行が増えない。
2. **`OPEN_SIGNUP=on` で起動し直す**(開く)。`/login` から招待制の説明が消える。同じアドレスでコードを求めると、`mail_outbox` に 6 桁のコードが入る。コードを入れると `/welcome` に着く。規約にチェックを入れて、ハンドルと表示名を決めると、登録できる。
3. **値を外して起動し直す**(戻す)。手順 2 で登録した人が、もう一度コードでログインでき、スライドの管理を開ける。運営の画面で入れていない別のアドレスには、コードが送られない。
4. 確かめた後の行は、`wrangler d1 execute slide --local` で `invited_emails` を読み、`invited_by` が `open-signup` の行がある(運営の画面の招待の一覧には出ない)ことを見る。

画面を撮るときは、[verify-slide](../../.agents/skills/verify-slide/SKILL.md) の手順に従う。
