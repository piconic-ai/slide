# フォローの実装設計

[気になる人を、フォローする](../features/f21-follow.md)ための画面、保存処理、フォロー・初公開のお知らせを扱う。

## フォローと解除の入口

プロフィールでは、ログインした読者が作者名の横の「フォロー」を押すと、その場でフォームを送信する。303 で同じプロフィールに戻ると、ボタンは枠線の「フォロー中」に変わる。もう一度押すと解除され、「フォロー」に戻る。「フォロー中」の読み上げとツールチップは「フォローを解除する」。どちらの操作も JavaScript は使わない。読者がミュートしている作者のプロフィールには、ボタンを出さない。

viewer では、作者名のそばの「フォロー」を押すと `/share.js` がフォローを送信する。送信中と、確認ページへ移る途中は、次のクリックを受け付けない。サーバーから、送った操作どおりの状態が届いたら、スライドを開き直さずに「フォロー中」に切り替える。操作が断られたとき(開いたあとで相手をミュートした、相手が停止された、など。答えは `{"following": false}` のまま)は、黙って終わらせず、確認ページへ移って理由を見せる。もう一度押すと同じ手順で解除する。再読み込みしたときはサーバーが保存済みの状態を表示する。

リンク先は常に確認ページで、スライドをめくるたびに戻り先のページ番号も更新する。スクリプトが無効なときやリンクを別タブで開いたときは確認ページを使う。通信に失敗したとき、200 以外の応答が届いたとき、JSON から真偽値の `following` を読めないときも、同じリンク先を開く。

viewer の CSP は `connect-src 'self'` で同じ origin への通信を許し、`form-action 'none'` でフォーム送信を禁止する。`/share.js` が `/api/session` を取得するのはヘッダーに `[data-account]` があるページだけである。viewer にはこの要素がないため、ログイン中も未ログイン時もこのリクエストは発生せず、ヘッダーにはサービス名と言語の切り替えが出る。

| 経路 | 動作 |
| --- | --- |
| `GET /follows/new?handle=…&slide=…` | 相手とフォローの効果を示す。未フォローなら「フォローする」、フォロー済みなら「フォローを解除する」のフォームを出す。ミュート中は設定からミュートを解除するよう案内する |
| `POST /follows` | 自分から相手へのフォローを保存する。通常のフォーム送信では、303 で元のスライドかプロフィールへ戻る |
| `POST /follows/:handle/release` | 自分から相手へのフォローを解除する。303 で、送ってきたページ(`slide` の値。プロフィール、フォロー中・フォロワーの一覧、スライド)へ戻る。`slide` がない、または正規の形でないときは `/slides` へ戻る。ログインが切れていれば、ログインの案内を返す。相手が停止中のあいだは、一覧にも確認ページにも出ないので、新しく開いた画面からは解除できない(停止中の人は、存在しない人と同じに見せるため)。停止の前から開いていた viewer・プロフィール・一覧・確認ページからは、解除できる(応答は、存在しない handle のときと同じ)。停止が解かれると、残っているフォローはそのまま続く |
| フォロー中・フォロワーの一覧の行のボタン | ログインした読者には、行ごとに「フォロー」または「フォロー中」(押すと解除)を出す。確認を挟まずにフォームを送り、同じ一覧の 1 ページ目に戻る。自分のプロフィールの「フォロー中」では、これがフォローを解除する場所になる(F21-AC12)。読者自身の行、未ログイン、停止中の読者には出さない。ボタンの読み上げには相手の名前を入れる(「@handle さんのフォローを解除する」) |

設定のページには、フォローしている人の一覧を置かない(F21-AC13)。ミュートの一覧と、お知らせの受信設定は残る。

確認ページは、存在しないハンドル、不正なハンドル、停止中の作者、本人に対して 404 を返す。相手を確認できて読者が未ログインなら、ログインの案内を 401 で返す。確認ページのフォームを送信するときにセッションが切れた場合も同じ案内になる。戻り先には正規の `/@handle`、`/@handle/following`、`/@handle/followers`、`/@handle/slug`、`/@handle/slug/ページ番号` を受け付ける。不正な値やクエリ付きの値は `/slides` に戻す。

viewer は、追加・解除のどちらも `handle` と `slide` を URL エンコードしたフォームで送り、`Accept: application/json` を付ける。この値を含むリクエストには、サーバーは操作後の状態を読み、200 と `{"following":true}` または `{"following":false}` を返す。ミュート中の作者など、フォローできない相手なら `false` になる。未ログインなら 401 と `{"error":"sign_in"}` を返す。これらの JSON 応答には `Cache-Control: no-store` を付ける。読者が停止された場合、`/follows` は既存のエラー処理で停止案内の HTML を 403 で返し、スクリプトは確認ページの URL を開く。

フォロー・ミュートの追加と解除、通知の受信設定の POST は、本文を読む前に `Content-Type` を検査する。`application/x-www-form-urlencoded` と `multipart/form-data` を受け付け、それ以外は `Accept` にかかわらず 415 を返す。フォームには既存の CSRF 検査を適用する。フォローの各経路には管理画面と同じ頻度制限を適用する。

## 関係の公開範囲とキャッシュ

フォロー中とフォロワーの一覧、その数は、だれでも見られる(F21-AC8・F21-AC9)。viewer の作者名のそばに示すのは、ページを見ている人自身がその作者をフォローしているかどうかだけで、数や他人の関係は出さない。未ログイン、作者本人、停止中の読者にはフォローの操作を出さない。フォローされた相手には、受信設定に従ってお知らせが届く。

ログイン済みの viewer はミュートと同じ `Cache-Control: private, no-cache` を使う。プロフィール、フォロー中とフォロワーの一覧、確認ページ、設定は `Cache-Control: no-store` で返す。一覧と数は見る人のミュートで変わるので、共有の cache に置かない。

## フォロー中とフォロワーの一覧

プロフィール(`/@handle`)の名前の下に、切り替え「スライド / フォロー中 / フォロワー」を置き、それぞれに数を添える(`profileTabs`、`src/profile/pages.ts`)。スライドの数は、その人の一般公開中のスライドを、一覧と同じ条件で数えたものである(`countPublicDecks`、`src/share/store.ts`)。プロフィールに並べる上限(100 件)では止まらない。開いている切り替えは `aria-current="page"` で示す。

| 経路 | 動作 |
| --- | --- |
| `GET /@handle/following` | その人がフォローしている人の一覧 |
| `GET /@handle/followers` | その人をフォローしている人の一覧 |
| `GET /@handle/following?page=2` | 2 ページ目。`followers` も同じ |

- **出す人**(`shownTo`、`src/follows/store.ts`)。アカウントのある人だけを出す。停止中の人は、だれが見ても出さない。ログイン中の人が見るときは、その人がミュートしている相手を出さない(相手が見る人をミュートしていても、それは隠さない)。数は、同じ条件で数える。一覧と数は同じ条件の式を使うので、数は、その人に見える一覧の人数と必ず合う。プロフィールの持ち主が停止中、または handle をだれも持っていないときは、プロフィールと同じ 404 を返す。
- **並びとページ**(`src/follows/people.ts`)。フォローが新しい順に、1 ページ 50 人(`PEOPLE_PER_PAGE`)まで出す。同じ秒のフォローは、相手のユーザー ID で順を決め、ページをまたいでも同じ人が 2 度出ないようにする。続きは `?page=N`(1 から)で開き、一覧の下の「次の 50 人」「前の 50 人」で進む。`?page=` が 1 以上の整数でないとき(`0`、`abc`、空)は 404 を返す。最後より先のページは、だれもいない一覧と、最後のページへ戻るリンクを返す。途中でフォローが増えると、次のページの先頭に前のページの人がもう一度出ることがある。新着を追う画面ではないので、位置を固定する仕組み(cursor)は入れていない。
- **人の行**(`src/follows/people-pages.ts`)。顔写真、名前、ハンドルを出す。名前がない人は、`@handle` を名前の位置に 1 度だけ出す。名前のリンクを行の全体に広げてあり、行のどこを押してもその人のプロフィールが開く。顔写真は GitHub から読み、読めないときと、まだ同期していないときは、名前の頭文字を出す(`/share.js` が、読めなかった `<img data-cover>` を隠す)。

### slug との衝突

`/@handle/following` と `/@handle/followers` は、スライドの共有 URL(`/@handle/slug`)と同じ形である。`parseSharePath`(`src/share/path.ts`)は、2 つ目の区切りが `following` か `followers` のとき、スライドの名前として読む前に、一覧として読む。`/@` で始まる経路はすべて `shareRoutes` の 1 つのハンドラーが受けるので、経路の登録順で隠れることはない。その名前のスライドがもし保存されていても、開くのは一覧である(スライドのほうは、どの URL からも開けなくなる)。`/@handle/following/2` のような、その名前の下のページ番号は 404 にする。大文字、`%40`、末尾の `/` の表記は、正規の表記へ 301 で転送する。

スライドの名前を決める・変える側で `following` と `followers` を断ること(F21-AC20 の前半)は、名前を扱う側([スライドの名前](f01-deck-slugs.md))が受け持つ。

## ログイン中のトップ

トップページ(`/`)は静的なファイルで、応答の時点ではだれが見ているか分からない。ログイン中の人の「自分のスライド」と「フォロー中の人の新着」は、表示の後に `GET /api/home` で取りに行く(F21-AC15〜F21-AC18、F21-AC21)。

| 項目 | 内容 |
| --- | --- |
| 応答 | `{ "own": [...], "following": [...] }`。`own` は自分のスライドを、最後に変わった新しい順に 4 件まで(`listOwnDecks`)。それぞれ、題名、1 本の管理ページ(`/slides/<名前>`)、表紙、読者が開けるかどうか(`isPublic`)を持つ。`following` は、フォローしている人の一般公開中のスライドを、公開中の版を受け取った新しい順に 4 件まで。形は「最近のスライド」の 1 件と同じ |
| ログインしていない要求 | 200 と `null` を返す。本人のデータは何も返さない。401 にしないのは、トップを開いたすべての人がこの要求を送るので、ブラウザの console にエラーを出さないためである |
| cache | どちらの応答も `Cache-Control: private, no-store` と `Vary: Cookie`。共有の cache にもブラウザにも残さない |
| 停止中の人 | ほかの本人向けの API と同じく、403 を返す。トップには何も出ない |
| 頻度制限 | `/api/session` と同じく、読者の枠(`viewer`)で数える(`src/site/rate-limit-policy.ts`)。未ログインを含め、トップを開いた全員が送るので、管理画面の枠で数えると、同じ会場の IP からトップが多く開かれたときに、その IP の作者の管理の操作まで 429 になる |

「フォロー中の人の新着」は、「最近のスライド」と同じ問い合わせ(`listPublicDecks`、`src/share/store.ts`)に、「見る人がフォローしている作者のもの」という条件(`followedBy`)を足して読む。そのため、公開を止めたスライド、運営が非表示にしたスライド、停止中の作者のスライド、見る人がミュートしている作者のスライドは、最近のスライドと同じ条件で外れる。お知らせと違い、初公開かどうかは見ない。フォローしている人が版を入れ替えると、そのスライドは先頭に戻る。

画面は 2 つのクライアントコンポーネント(`components/HomeOwnSlides.tsx`、`components/HomeFollowing.tsx`)で、枠は `src/site/home-signed-in-frames.tsx` にある。2 つは同じ要求を使い、送るのは 1 回である(`createQuery` が同じ宛先の要求をまとめる)。中身のない節は、見出しごと出さない。script が動かない環境では、どちらも出ない。

届くまでの間に画面がずれないように、前に届いた一覧の件数(`{"own":2,"following":1}` の形)を、そのブラウザの `localStorage`(`slide:home`)に置く。次に開いたとき、ヘッダーが置いた `slide:session` がログイン中を示していれば、その件数のぶんだけ、見出しと仮のカードを先に描く(`keptHomeShape`、`src/site/home-shape.ts`)。置いた値は描画の手がかりにしか使わず、中身は信じない(数は 0〜4 に丸める)。初めて開いたとき、ログアウトした後、件数が変わったときは、届いた時点で 1 度だけ画面が動く。題名が 2 行に折り返すカードがあるときも、その 1 行ぶん動く。

## 保存するもの

| テーブル・列 | 内容 |
| --- | --- |
| `follows.follower_user_id` | フォローした人の GitHub ユーザー ID |
| `follows.followee_user_id` | フォローされた人の GitHub ユーザー ID |
| `follows.created_at` | 現在のフォローを始めた時刻（Unix 秒） |
| `decks.first_published_at` | 初めて一般公開した時刻（Unix 秒）。まだ公開の記録がなければ NULL |

フォローの主キーは両者の ID の組で、自分自身へのフォローは CHECK 制約で拒む。`follows_followee` 索引は、作者のスライドを初公開するときに受け手を引くために使う。

## フォロー、ミュート、退会

| 操作 | 保存・読み取りの条件 |
| --- | --- |
| フォローする | 両者のアカウントが存在し、別人で、フォローする人が相手をミュートしていないことを挿入と同じ文で確かめる。すでにある組の時刻は保つ |
| フォローを解除する | 指定した向きの組を消す。相手に届いたお知らせは残る |
| フォロー中・フォロワーを読む | [フォロー中とフォロワーの一覧](#フォロー中とフォロワーの一覧)の条件で、相手のハンドル、名前、顔写真と、見る人がその相手をフォローしているかを、フォロー時刻の新しい順で返す |
| 相手をミュートする | ミュートの保存と同じ D1 バッチで、その人へのフォローを消す。ミュートを解除してもフォローは復元しない |
| 退会する | アカウントを削除するバッチで、本人がしたフォローと本人へのフォローを消す |

## 初公開の判定

手動公開と CI 公開は、どちらも `saveTransition` を通る。公開状態の更新と同じ D1 バッチで、更新直前の `first_published_at` を読む。一般公開への更新では、まだ NULL の場合だけ公開時刻を保存する。その更新が成立し、直前の値が NULL で、かつ直前の状態が下書き(または、再開先のない公開停止)だったときにだけ、フォロワーへの配信を呼ぶ。この列ができる前の Worker が公開したスライドは、時刻が NULL のまま公開中でありうるので、列だけでは版の更新と区別できないためである。配信の文は、その時点で公開中かどうかを見ない。直後に公開が止まっても行は入り、一覧と未読件数の表示条件が、公開中のあいだだけ見せる。版の更新、公開停止、再開を経ても最初の時刻を保つ。同じ秒に複数の更新が成立しても、初公開は一度だけである。

移行 0028 は、既存の一般公開中のスライドには公開版の `deployments.ready_at` を、停止中で再開先が残るスライドには再開先の版の `ready_at` を入れる。これは移行前の初公開時刻に代えて使う値である。どちらの版も残っていなければ NULL を保ち、次の一般公開を初公開として扱う。

旧 Worker は移行後もスライドを保存・公開できる。移行後から新 Worker への切り替えまでに旧 Worker が初公開した場合、この列は NULL のまま残り、新 Worker が次に公開状態を更新したときに初公開として扱う。

配信時のミュート・受信設定と、一覧・未読件数に含める条件は[お知らせの実装設計](f20-notifications.md)を参照する。
