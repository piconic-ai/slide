# 不正なスライドの知らせに対応する

slide は、作者の HTML と JS を配る。読者をだますスライドが公開されると、外から知らせが届く。知らせの種類ごとに、運営が何をするかをここに書く。使う道具は、[運営による非表示](f17-takedown.md)、[アカウントの停止](f17-suspension.md)、[通報の一覧](f17-reports.md)である。

Google や Cloudflare の画面と手順は、相手の都合で変わる。ここにある外部の手順は、実際に知らせを受けて通したものではない(2026-11-18 時点)。初めて使うときに、画面と合っているかを確かめ、違っていたらこの文書を直す。

## 知らせが届く経路

| 経路 | 何が届くか | どこで気づくか |
| --- | --- | --- |
| 読者の通報 | スライドごとの理由と説明 | 運営の画面(`admin.slide.community`)の「通報されたスライド」。通知はないので、見に行く |
| 問い合わせ | 権利者や読者からのメール | `contact@slide.community`(運営へ転送される) |
| Google Safe Browsing | 配信ドメイン(`slideusercontent.com`)や `slide.community` が、危険なサイトとして登録された | Search Console の「セキュリティの問題」と、そこからのメール。読者のブラウザに、赤い警告が出る |
| 事業者からの通知 | Cloudflare や registrar に届いた abuse report の転送 | Cloudflare のアカウントと、ドメインの登録者のメール |

Search Console に `slide.community` と `slideusercontent.com` を登録していないと、Safe Browsing に登録されても、知らせは届かない。登録は、依頼者が行う(#44)。

## どの知らせでも、最初にすること

1. **スライドを特定する。** 知らせにある URL から、共有 URL(`https://slide.community/@handle/slug`)を割り出す。配信の URL(`https://d-<deployment ID>.slideusercontent.com/…`)しかないときは、deployment ID から引く。

   ```sh
   pnpm exec wrangler d1 execute slide --remote --command "SELECT a.handle, d.slug FROM deployments p JOIN decks d ON d.id = p.deck_id JOIN accounts a ON a.user_id = d.owner_user_id WHERE p.id = '<deployment ID>'"
   ```

   これは読み取りだけである。D1 を手で書き換えない。

2. **スライドを開いて、知らせの内容を確かめる。** 普段使っているブラウザの profile ではなく、ログインしていない別の profile で開く。入力を求められても、何も入れない。
3. **読者をだます内容なら、運営の画面で非表示にする。** 理由には、何を見たかを書く(作者の管理画面に出る)。非表示にした直後から、共有 URL と配信は読めなくなる。
4. **同じ作者が繰り返しているなら、アカウントを停止する。** 停止すると、その作者のスライドがすべて読めなくなり、アップロードと公開が止まる。
5. **迷うときは、先に非表示にする。** 非表示は解除でき、解除すると元の公開状態に戻る。読者の被害は、戻せない。

権利侵害の申し立ては、申し立てた人が権利者かどうかを、運営だけでは判断できないことがある。判断の基準は、利用規約(#65)と一緒に決める。それまでは、依頼者が 1 件ずつ判断する。

## Safe Browsing に登録されたとき

配信ドメインは、すべての作者のスライドが共有している。1 つのスライドが原因でも、ドメイン全体に警告が出ることがある。早く直すほど、ほかの作者への影響が小さい。

1. Search Console の「セキュリティの問題」で、例として挙がっている URL を確かめる。
2. 上の「最初にすること」で、そのスライドを非表示にする。例に挙がっていない、同じ作者のスライドも確かめる。
3. 非表示にした URL が、ログインしていないブラウザで 404 になることを確かめる。
4. Search Console の同じ画面から、審査をリクエストする。何を見つけ、何をしたか(該当の内容を配信から外した、作者のアカウントを停止した)を書く。
5. 審査の結果が出るまで、Search Console を見る。警告が外れたことは、Google の透明性レポートの Safe Browsing のサイト ステータスでも確かめられる。

登録が誤りだと考えるとき(該当の内容が見つからないとき)も、同じ画面から審査をリクエストする。

## 事業者からの通知が届いたとき

1. 通知にある URL で、上の「最初にすること」を行う。
2. 通知に返信の期限と方法が書かれていれば、それに従って、行った対応を返す。
3. 通知の内容が、スライドではなく、サービスそのもの(`slide.community` のページ)を指しているときは、依頼者に知らせる。

## 記録

非表示と停止の理由・日時・操作者は、運営の画面に出る。ただし、出るのは解除するまでである。解除すると、非表示の列は空に戻り、停止の行は消える。履歴は残らない。

そのため、対応のたびに、次のものを依頼者のメールに残す。

- 外から届いた知らせ(メール、Search Console の画面の写し)。
- 対象の共有 URL と、行った対応(非表示、停止、解除)、その理由、日時、操作者。解除するときは、解除の前に、運営の画面の理由・日時・操作者を写す。
- 審査のリクエストや、事業者への返信に書いた文。

件数が増えたら、残し方を決める。

## 決まっていないこと

- 知らせを受けてから対応するまでの目標の時間。運営が 1 人のあいだは、約束しない。
- 配信ドメインを Public Suffix List に載せるか。載せると、ブラウザや Safe Browsing が、版ごとの origin を別のサイトとして扱いやすくなる。載せる手続きと、cookie への影響を調べていない。
- 権利侵害の申し立ての判断の基準と、作者の反論の受け方(#65)。
