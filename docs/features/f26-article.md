# F26 発表を書き起こした記事を添える

状態は実装済みです(第二スコープ)。保留にしていた F26-AC23 と F26-AC24 は、2026-11-25 に削除した(判定の関数と画面の文言が、働かないまま残っている)。2026-11-25 に、記事の中の外部へのリンクを整え、押したときに URL を確かめる条件を足した(F26-AC97〜F26-AC100。未実装)。同じ日に、画像にするページの上限を変える条件を足した(F26-AC101〜F26-AC104。2026-11-26 に実装した)。実装する段階は [ストーリーマップ](../story-mapping.canvas) で確認できます。

## 利用場面

勉強会に来られなかった人が、あとから公開スライドを開く。スライドには図と短い見出ししかなく、発表者がなぜその設計にしたのかは口頭でしか話されていない。登壇者は、発表を終えたあとで、話した内容を文章に残したい。ただし、記事を書くことをスライドを置く条件にはしたくない。

## 得られる結果

作者は、発表を書き起こした記事を Markdown で書き、viewer のスライドの下に載せられる。読者は、スライドと、話された内容を同じページで読める。記事の中にページ番号つきの共有 URL を書くと、そのページの画像が入り、押すとスライドがそのページに移る。ほかの人のスライドのページを書くと、そのスライドへ移れ、引用として数えられる。

記事は、無くてもスライドは共有できる。置く流れに、入力を挟まない。置いた後に、書きたい人だけが書く。

## 体験の流れ

1. 作者が、スライドの編集の「記事」の枠から「記事を書く」を押し、記事の編集ページを開く。
2. Markdown で書く。画面の上の「ビューアーで見る」を押すと、保存前の本文で、読者が見る viewer と同じ画面が開くので、見え方を確かめる。本文は、入力すると自動で保存される。下書きの間は、作者だけが viewer で記事を読者と同じ見え方で確かめられる。
3. 話した内容のページを指したいときは、ページ番号つきの共有 URL(`https://slide.community/@handle/slug/3`)を、段落に 1 行だけで書く。
4. スライドの編集の「記事」の枠で「記事を公開する」を押す。スライドが一般公開中なら、ログインしていない人の viewer にも、スライドの下に記事が載る。
5. 公開した後に直したものは、編集中の下書きとして自動で保存され、「公開記事を更新」を押すまで読者には見えない(「変更を取り消す」で公開中の本文に戻せる)。載せたくなくなったら、「記事」の枠の「記事の公開を止める」を押す。
6. 読者は、記事の中のページの画像を押す。自分のこのスライドのページなら、上のスライドがそのページに移り、スライドの位置までスクロールする。ほかの人のスライドのページなら、そのスライドのそのページが開く。

AI エージェントは、記事を読み、下書きまで書ける。公開中の記事に書いたものは、編集中の下書きに入る([AI エージェントから置く](f23-agent-upload.md))。公開と公開記事の更新は、作者が押す。

## 作る範囲

- 記事の保存。スライド 1 本につき 1 本で、版ではなくスライドに属する。状態は「下書き」と「公開中」の 2 つで、公開中の記事は、「未反映の変更あり」(編集中の下書きがある)も持つ。入力の自動保存。
- 記事の編集ページ(`/my/slides/:deck/article`)。入力欄が常にある 1 つの画面に、上に「ビューアーで見る」(viewer と同じ画面へ移る)、公開中のときは下に「公開記事を更新」「変更を取り消す」のボタンを置き、幅が十分なときは入力欄の右に記事を並べる。書き方の説明は画面に置かず、ヘルプの記事の節に書く。
- スライドの編集の「記事」の枠。状態のタグ、最後に保存した日と字数、「記事を編集する」(記事が無いときは「記事を書く」)。
- viewer の記事の節。題名、説明、関連リンク([関連リンクを紐付ける](f27-related-links.md))の下、引用の節の上に置く。見出しは付けず、本文がスライドの直下から読めるようにする。中身のないときは、節ごと出さない。
- Markdown の変換。サーバーで HTML にし、許可した要素と属性だけを出す。
- ページの埋め込み。段落にページ番号つきの共有 URL だけが 1 行で書かれているとき、そのページの画像([説明したいページを画像付きで共有する](f05-page-ogp.md))を出す。
- 記事の中の共有 URL へのリンクを、引用として数えること([引用でつながる](f24-citations.md))。

## 作らないこと

- サービスによる記事の生成と翻訳。作者(または作者の AI エージェント)が書く部分だけを作る([話した言葉といっしょに読む](f15-talk-reading.md))。
- 記事でページの画像以外の画像を使うこと。アップロードと保存が要る。ページの画像で足りる。
- 記事を読む間、スライドを横に追従させること。viewer の iframe の扱いの判断が要る。
- 参加者が記事を書くこと。参加者のレポートは、作者が関連リンクの「記事」として足す。
- AI エージェントが記事を公開する、取り下げること。
- 独自の記法。ページの埋め込みは、共有 URL を 1 行で書くだけにする。

## 決めたこと

第二スコープを作るにあたり、次のように決めた(2026-11-22)。

- 記事はスライド 1 本につき 1 本。版ではなくスライドに属し、版を差し替えても残る。
- 記事の状態は「下書き」と「公開中」。読者に見えるのは、スライドが一般公開中で、記事が公開中のときだけ。作者は viewer で、下書きを読者と同じ見え方で確かめられる。
- 公開中の記事を直したものは、公開中の本文とは別の「編集中の下書き」に自動で保存し、「公開記事を更新」を押すまで読者に反映しない(2026-11-23。依頼者が、第二スコープの最初の決定「公開中の記事を直して保存するとすぐ反映する。別の下書きを持たない」を変えた)。理由は、いまどきの自動保存と、公開中の記事の書きかけが読者に見えないことを、両立させたいからである。採らなかった案は、(a) 自動で読者に反映する(書きかけが読者に見える)、(b) 手動の保存だけにする(書いている途中で失うおそれがある)。編集中の下書きを持つのは公開中の記事だけで、下書きの記事は本文そのものを自動で保存する。公開中の記事の編集中の下書きは、作者のプレビューにだけ出る。
- 2 つのタブで同時に編集したときは、自動保存と各ボタンに、読み込んだときの版(revision)を添え、他で更新されていれば保存せずに知らせる(後の保存が先の保存を黙って上書きしない)。
- Markdown は CommonMark と、GFM の表・取り消し線・自動リンクまで。生の HTML は使えない(文字として表示する)。表示はサーバーで HTML に変換し、許可した要素と属性だけを出す。依存を足すときは、生の HTML を既定で通さないものを選び、選んだ理由を設計の文書に書く。リンクは `https:` と `http:` と `mailto:` だけ、`rel="noopener nofollow ugc"` を付ける。
- 本文は 50,000 文字まで。
- ページの埋め込みは、段落にページ番号つきの共有 URL(`https://slide.community/@handle/slug/3` の形)だけが 1 行で書かれているときに行う。文の中の URL は、ふつうのリンクにする。独自の記法は作らない。
  - その記事のスライドの URL なら、そのページの画像(第一スコープのページごとの OGP 画像)を出し、押すと viewer の上のスライドがそのページに移る。
  - ほかの一般公開中のスライドの URL なら、そのページの画像と、「△△さんの『□□』3 ページ」の説明を出し、押すとそのスライドのそのページを開く。
  - 一般公開されていないスライド、存在しないスライドやページ、非表示・停止の作者のスライドなら、画像を出さず、ふつうのリンクにする。作者のみ限定公開のスライドの題名や存在を、記事から漏らさない。
- 記事の中の共有 URL へのリンク(埋め込みも、文の中のリンクも)は、スライドの中のリンクと同じく引用として数える。数えるのは記事が公開中の間だけ。自分のこのスライドへのリンクは数えない。
- いまの版に無いページを指す埋め込みは、編集ページで作者に知らせ、読者にはふつうのリンクを出す。(2026-11-25 にやめた。下の決めたことを参照)
- 記事を書けるのはスライドの作者だけ。
- 記事の HTML は、viewer の管理 origin で出す。作者の HTML と同じ sandbox には入れない。変換の結果に script、`style` 属性、イベント属性、`iframe`、`form` が入らないことをテストで確かめる。
- viewer の並びは、幅 760px 以下では、スライド、題名と操作、作者、説明、関連リンク、記事、引用の順(縦並び)。幅 761px 以上では、スライドの下の左の列に題名と操作、記事を置く(ワイド)。記事に「記事」の見出しは付けない。記事をスライドの直下から読めるようにするためで、節の意味は `aria-label` で残す(2026-11-22)。中身のない節は、出さない。レイアウトは [URL を渡して読んでもらう](f03-sharing.md) で固定にした。
- 記事の公開の操作は、AI エージェントには渡さない。下書きまでを読み書きできる。公開中の記事では、作者の編集中の下書きを読み、そこに書く(2026-11-24。依頼者の決定。読者に見えるのは作者が「公開記事を更新」を押した後で、書くときは読んだときの revision を添え、合わなければ断る。[AI エージェントから置く](f23-agent-upload.md)の「決めたこと」)。

第二スコープの確認で、次のように決めた(2026-11-25、依頼者。issue #366 の D7、D8)。

- いまの版に無いページを指す埋め込みを、作者に知らせることはやめる(F26-AC23、F26-AC24 を削除した)。サービスは、版の総ページ数を確かには知れない。HTML のスライドには総ページ数を伝える共通の決まりがなく、HTML を読んで数えると数え違える。作者は「ビューアーで見る」で気づける。どのページも「ある」ものとして扱う(いまの動き)。
- 本文が空の記事は、公開できない(F26-AC78。いまのまま)。
- 1 つの記事で画像にするページは、違うページを 20 までにする(いまのまま)。見直しは issue #454 で扱う。(2026-11-25 に変えた。下を参照)
- 記事からほかの人のスライドを引用したときは、引用している側の viewer の「このスライドが引用しているスライド」にも出す。これまでは、引用された側の一覧と、プロフィールの一覧と数にだけ出ていた。スライドの中のリンクの引用と同じに扱うためである。[引用でつながる](f24-citations.md) の F24-AC36〜F24-AC38 で確かめる。
- 記事の中の外へのリンクも、関連リンクと同じく整えてから使い、押したときに確認の画面で URL の全体を見せる(2026-11-25、依頼者。URL を押す人の安全のため。F26-AC97〜F26-AC100。理由と整える内容は [関連リンクを紐付ける](f27-related-links.md) の「決めたこと」)。このサービスの共有 URL へのリンクは、サービスの中のページなので、確認の画面を出さない。
- 画像にするページの上限(20)は、なくす方向で考える(2026-11-25、依頼者。#454)。依頼者の言葉: 「任意のページに対して、OGP画像を作る仕組みを用意したのだから、あとは遅延で読み込みする仕組みさえ用意すれば良いのではないかと思った。」上限を超えたときに、作者に知らせることはしない(いまのまま)。21 件目からを iframe で見せる案と、上限を 50 に上げる案は、採らなかった。どうなくすかは、未決事項にある。
- 画像にするページの数の上限は、なくす。ほかのスライドは、1 本の記事で 40 本までにする(2026-11-25、依頼者。#454。F26-AC101〜F26-AC104)。依頼者の言葉: 「A. ページの数の上限はなくす。ほかの人のスライドは 1 本の記事で 40 本まで」。理由も依頼者の言葉で: 「他のひとのスライドを沢山埋め込むことはユースケースとしてまずないので。」40 本は、D1 の 1 回の問い合わせの引数の上限(100)に、1 本につき 2 つで収まる数である。そのために、問い合わせの前に、ページを handle と slug ごとにまとめる(いまは、ページごとに条件が増える)。その記事のスライドのページは D1 を引かないので、数を問わない。上限を超えても、作者に知らせない(いまのまま)。
- 同じ日に、次も決めた(依頼者が、提案した案を採った)。`http:` のリンクも `https:` と同じく整え、確認の画面を出す。`mailto:` のリンクも確認の画面を出す。ユーザー名やパスワードを含む URL は、リンクにせず文字で出す(F26-AC99)。記事の本文は保存の前に断る場面がなく、文字で出せば、読者がだまされて移ることはないためである。
