# F22 スライドを、ドロップして置く

状態は実装済みです(Firefox・WebKit・実機でのドロップは、人の確認が残る)。第二スコープで、ログインと招待をメールのコードとメールアドレスの一覧に変える(F22-AC38 から)。2026-11-27 に、ホスティングの配信設定ファイル(`_redirects`、`_headers`)を、断らずに無いものとして扱うと決めた(F22-AC48〜F22-AC54。実装済み。本番での Slidev の zip のドロップは、人の確認が残る)。実装する段階は [ストーリーマップ](../story-mapping.canvas) で確認できます。

## 利用場面

登壇の前日、エンジニアが AI や作成ツールで HTML スライドを作り終える。置き場を自分で作り込む時間はない。GitHub App の導入、リポジトリの連携、workflow の設定をしている余裕もない。できあがった HTML か zip を、そのまま渡して済ませたい。

## 得られる結果

できあがった HTML か zip をトップページに落とすだけで、スライドが置かれる。置いた時点で、作者だけが見られる URL があり、確かめてから公開できる。直した版は、同じ URL のまま差し替えられる。

## 体験の流れ

1. トップか「スライドの管理」に、HTML 1 ファイルか zip をドロップする(または「ファイルを選ぶ」)。
2. ログイン中なら、そのまま受け取る。ログインしていなければ、ファイルをブラウザの中に預かり、枠を「選んだ後」の表示に変える。「ログインして続ける」を押すと `/login` へ進み、メールのコードでログインして戻ると、預かったファイルを自動で受け取る。
3. 受け取ったスライドは、作者だけが見られる状態で、作者の viewer(`/@handle/slug`)に開く。スライドの上に「まだ公開していません。いまはあなただけが見ています。」と「公開する」が出る。題名と URL の名前は、HTML の `<title>` とファイル名から決めてある。
4. 表示を確かめ、必要なら「編集する」から URL の名前を直して、「公開する」を押す([作者のみ限定公開で発表し、一般公開する](f02-publication.md))。
5. 直した版は、スライドの編集にドロップする。公開中の版は、入れ替えの操作を押すまで変わらない。

## 作る範囲

- トップ、「スライドの管理」、スライドの編集(差し替え)のドロップ枠。
- HTML 1 ファイルと zip の受け取り。zip はブラウザで展開し、受け取りの API はファイル単位のままにする。
- 送る前の、種類・大きさ・数の確認と、断る理由の表示。
- ツールがビルドの出力に足す、ホスティングの配信設定ファイル(トップの `_redirects` と `_headers`)を、無いものとして扱うこと。
- ログイン前に選ばれたファイルを、ブラウザの中に預かること。
- 題名と URL の名前を決めること。公開する前に URL の名前を変えること。
- 受け取りを GitHub から切り離すこと。開始は、ログイン中の作者の session(ブラウザ)か、[AI エージェントから置く](f23-agent-upload.md) の認可で行う。
- 招待制。運営が招待したメールアドレスの人だけが、ログインして置ける。

## 作らないこと

- フォルダのドロップ、PDF、zip 以外の圧縮形式。
- 公開した後に URL の名前を変えること。
- 未ビルドの Markdown を受け取って、サービス側でビルドすること。
- GitHub のリポジトリからスライドを送ること。[GitHub からスライドを更新する](f01-github-deploy.md) は、やめた。
- `_redirects` と `_headers` の中身を読んで、転送やヘッダーを再現すること。slide は、置かれたファイルを path で引いてそのまま返すだけにする。作者のファイルが、読者を任意の場所へ転送したり、配信のヘッダー(CSP の `sandbox` など)を書き換えたりできないようにするためである(2026-11-27)。
- 名前を挙げていない設定ファイル(GitHub Pages の `CNAME`・`.nojekyll` など)を、無いものとして扱うこと。実物の出力で必要になってから、名前を足す。Cloudflare Pages の `_worker.js` と `_routes.json` は、これまでどおり断る(サーバーで動くプログラムを前提にした出力のため)。
- 中身がスライドかどうかの判定。受け取るのはビルド済みの静的ファイルで、ページを伝える script のない HTML も、そのまま表示する。
- 招待されていない人のログインと受け取り。ログインをだれにでも開くことは、第二スコープの範囲外で、知らない人に開く前に済ませることが残っているためである([サービスの基本の備え](../dev/service-basics.md#知らない人に開く前に済ませること))。

## 決めたこと

第一スコープを作るにあたり、次のように決めた(2026-11-19)。

- 招待制を続ける。第二スコープで、招待の持ち方を、GitHub の利用者番号の設定(`AUTHOR_GITHUB_IDS`)から、メールアドレスの一覧(D1 の表。運営の画面で足す・外す)に変えた(2026-11-22。[メールのコードでログインする](f28-email-login.md))。招待されていない人は、ログインできない(F22-AC40)。ログイン中に招待から外された人がドロップしたときは、受け取らずに、いまは招待制であることを伝える。
- 受け取るのは、HTML 1 ファイルと zip。フォルダのドロップは対象外にする。
- zip はブラウザで展開し、受け取りの API はファイル単位のままにする。zip の直下に `index.html` がなく、1 つのフォルダの中にあるときは、そのフォルダを根にする。HTML 1 ファイルは `index.html` として置く。`index.html` が決まらない zip は、受け取る前に断る。
- 上限は現行のままにする(`src/uploads/limits.ts`。1 つの版 10MB、1 ファイル 5MB、100 ファイル、1 人 20 本)。超えるものは、送る前にブラウザで断り、どの上限を超えたかを伝える。
- ページを伝える script の 1 行は、送り手が足す(ブラウザの JS、MCP の受け口)。判定は `scripts/page-script.mjs` と同じにし、処理を共有する。Worker が配るときに byte を変えない、という方針は保つ。(2026-11-24 に変えた。サービスが配るときに版のトップの `index.html` へ差し込み、送り手は足さない。ドロップしたファイルは、そのままの byte で置く。理由は [URL を渡して読んでもらう](f03-sharing.md)の「決めたこと」。送り手が足した 1 行は、作者の CSP に止められると、コンソールに違反を残していた)
- ログイン前に選ばれたファイルは、ブラウザの IndexedDB に預かる。預かるのは 1 件だけで、24 時間たったら捨てる。上限は上と同じ。戻ったときに無ければ、何も出さない。
- URL の名前は、`<title>`、ファイル名、`slide` の順で元にし、既存の slug の規則に合わせて作る。同じ人の中で重なったら `-2`、`-3` を付ける。同じ人の開始が同時に重なり、名前の選び直しを 2 回続けて取られたときだけ、最後の 1 回は、1000 以上の乱数の番号(`-1042` など)を付ける(名前だけを理由に開始を断らないため)。公開する前は、スライドの編集で変えられる。公開した後に変える仕組みは作らない。
- 置いた直後は、作者だけが見られる。公開中のスライドに新しい版をドロップしたときも、公開中の版は自動では入れ替えない。スライドの編集で、入れ替える操作を 1 回押す。
- 置いた直後の行き先は、作者の viewer(`/@handle/slug`)にする(2026-11-20)。作者は、読者が見るのと同じ画面で確かめ、そこから「公開する」と「編集する」へ進める。作者限定の viewer([作者のみ限定公開で発表し、一般公開する](f02-publication.md)の F02-AC18〜F02-AC31)を保留にしたときだけ、行き先を、これまでどおりスライドの編集(`/my/slides/:deck`)にする。このとき、F22-AC33・F22-AC35〜F22-AC37 の「viewer が開く」は、スライドの編集が開くことで満たす。
- 作者向けの画面には、受け取りの出どころ(ブラウザ、AI エージェント)も出さない(2026-11-20。F02 の「決めたこと」)。公開した後は、URL の名前を入力欄にもせず、文字としても出さない(「共有 URL」の 1 行だけ。2026-11-23 に変えた。F22-AC44)。
- 受け取りを GitHub から切り離す。開始は、ログイン中の作者の session(ブラウザ)か、MCP の認可で行う。GitHub の OIDC での開始はなくす。`deployments` の GitHub 由来の列(`source_sha`、`run_id`、`repository_id` など)は消し、出どころ(ブラウザ、MCP)を表す列に置き換える。
- スライド(deck)は、リポジトリの連携なしで作る。公開の方式は手動だけにし、リポジトリに従う方式(`repository`)はなくす。
- 本番のデータは空にしてよい。GitHub からの更新は、コード、経路、テーブル、手順と設計の文書(`docs/dev/`)ごと取り除き、互換のための経路や、使わない列を残さない。既存の行を新しい形へ移す処理は書かない。
- 画面の文言は、日本語と英語の両方を用意する。

ホスティングの配信設定ファイルは、断らずに、無いものとして扱う(2026-11-27、依頼者。#694)。

- きっかけ: Slidev の `slidev build` は、出力のトップに `_redirects`(中身は `/* /index.html 200`。Netlify や Cloudflare Pages が、どの path でも `index.html` を返すための設定)を足す。slide は、受け取れる種類を拡張子で決めている(`src/uploads/media-types.ts`)ので、拡張子のないこのファイルを、受け取れない種類として断っていた(ブラウザは送る前に `unsupported_file`、サーバーは `Unsupported static file type`)。Slidev の出力は、1 ファイルを手で消さないと置けなかった(#703 の記録)。
- 依頼者の懸念は、redirects が読者を任意の場所へ転送する危険だった。slide では起きない。版の origin は、request の path で D1 の `upload_files` の行を引き、その R2 の object を、受け取ったときに決めた種類と、サービスが決めたヘッダー(CSP など)で返すだけである(`src/preview/content-routes.ts`、`access-store.ts` の `readDeployedFile`)。`_redirects` や `_headers` を読む処理は、どこにもない。Worker の静的ファイル(`wrangler.jsonc` の `assets`)にはこの 2 つを解釈する機能があるが、対象はサービス自身の `public/` だけで、作者のファイルは R2 にあり、そこを通らない。
- 受け取ったうえで置かない(版に含めない)ことにした。置いても働かないファイルを、読者が開ける URL に残す理由がないためである。macOS が足すファイル(F22-AC5)と同じ扱いにする。
- 対象は、トップの `_redirects` と `_headers` の 2 つにする。`_headers` は、実物の出力では見つかっていないが、`_redirects` と同じホスティング(Netlify、Cloudflare Pages)の、同じ場所に置く、同じく拡張子のない設定ファイルである。断る理由も、解釈しないので害がないという根拠も、`_redirects` と同じなので、あわせて対象にした。それ以外の設定ファイルは、実物の出力で必要になってから足す(作らないこと)。
- 受け取れるようになっても、働かないもの: 転送やヘッダーの設定に頼る動き。Slidev の出力は、版の origin の `/3` を直接開くと 404 になる(`_redirects` があれば `index.html` が返る場面)。viewer は版のトップ(`/`)を開き、Slidev は文書を読み込み直さずに path を書き換えてめくる。枠が `/3` のまま文書を読み込み直す場面が viewer で起きるかは、確かめていない。Slidev の読み替え([URL を渡して読んでもらう](f03-sharing.md) の F03-AC191、F03-AC192)を作るときに確かめる。設定が働かないことは、ヘルプに書く(F22-AC53)。

[GitHub からスライドを更新する](f01-github-deploy.md) から、次の条件を引き継いだ。意味は変えていない。「アップロード」は「受け取り」に読み替える。

| 元の ID | 引き継いだ ID |
| --- | --- |
| F01-AC2 | F22-AC6、F22-AC17 |
| F01-AC3 | F22-AC20 |
| F01-AC5 | F22-AC21 |
| F01-AC6 | F22-AC22 |
| F01-AC7 | F22-AC23 |
| F01-AC8 | F22-AC24 |
| F01-AC9 | F22-AC25 |
| F01-AC10 | F22-AC26 |

誰が使えるかについては、次のように決めてある(2026-11-17)。

- 作者(運営を兼ねる)のほかに、作者が招いた人も、作者として使えるようにする。招いた人は、メールアドレスを招待の一覧に登録する(2026-11-22 に、GitHub の user ID の設定から変えた)。
- 招いた人を止めるときは、一覧から外す。外された人は、ログイン済みの状態も切れる。アカウントの停止([知らない人のスライドも、安心して開ける](f17-safe-viewing.md))は、理由を本人に伝え、スライドをまとめて読めなくする。
- slug は、作者ごとの名前にする。共有 URL が `/@handle/slug` なので、作者ごとに同じ slug を使えるのが自然である。
- handle は、初めてログインした人が `/welcome` で自分で決める(2026-11-22)。ぶつかったときは、選べず、理由が出る。GitHub のログイン名から作る方式と、ぶつかったときにログインを断る方式(F22-AC26)は、やめた。
