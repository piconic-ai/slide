# F17 知らない人のスライドも、安心して開ける

状態は実装中です(F17-AC1〜F17-AC36 は実装済み。停止リストの条件 F17-AC37〜F17-AC43 は未実装で、issue #466 で作る)。2026-11-27 に、本番で招待制を外し、登録していない人にも開いた([招待なしで登録できるようにする](f42-open-signup.md))。実装する段階は [ストーリーマップ](../story-mapping.canvas) で確認できます。

## 利用場面

読者が、SNS で見かけた知らない人の公開スライドを開く。動くスライドは JS を実行するので、勝手に別のページへ飛ばされたり、ファイルをダウンロードさせられたり、ログイン中のサービスを操作されたりしないか不安になる。

## 得られる結果

読者は作者を知らなくても、デモを動かしてよいと判断できる。作者は、読む人に警戒されずに動くスライドを届けられる。

## 体験の流れ

1. 読者が公開スライドの URL を開く。
2. スライドのデモをさわる。
3. スライドが親ページの移動、別タブ、ダウンロード、フォーム送信を試みても、ブラウザが止める。
4. 読者は、どのスライドにも共通して止められている操作と、スライドが外部と通信できることを、ヘルプページで確かめる。
5. 読者をだます内容だと思ったら、ログインして通報する。ログインしていなければ、通報を押したときにログインを求められる。
6. 運営は、運営の画面で通報を確かめて、スライドを非表示にする。作者の管理画面には、非表示にされたことと理由が出る。

## 作る範囲

- 作者の HTML を sandbox 付きの iframe で、管理画面とは別の origin から配る。
- 親ページの移動、popup、ダウンロード、フォーム送信、service worker の登録を許さない。
- 外部への通信は止めない。外部と通信できることは、ヘルプページで読者に説明する。
- 読者に、スライドに止めている操作をヘルプページで示す。
- ログインした読者がスライドを通報できる。通報は、運営の画面の一覧に出る。
- 運営がスライドを非表示にし、アカウントを停止できる。
- 運営の画面を `admin.slide.community` に置き、Cloudflare Access で守る。

## 作らないこと

- 作者の JS を静的に解析して、危険なスライドを判定・拒否すること。
- 制限を外して動かすための、読者向けの切り替え。
- 外部への通信の遮断。API を使うデモ、CDN のライブラリ、Web フォント、動画は動くスライドの価値なので、止めずに、ヘルプページで説明する。
- 通報の件数だけで自動的に非表示にすること。
- ログインなしの通報。一旦作らない。通報の保存の形は、あとで足せるように、ログインの有無に依存させない。
- 通報の通知。通知の仕組み(#60)が決まってから載せる。それまで、運営は一覧を見に行く。
- 通報した人への、結果の連絡。
- 通報の一覧の「確認済み」の印。通報が実際に届いて、一覧が読みにくくなってから考える。
- 停止中のスライドを、作者が 1 つずつ削除すること。解除のあとに行える。
- 退会した人のスライドを、運営が保持すること。証拠を残したい場面が具体的に出てから考える。
- 停止の通知と、期限つきの停止。通知は、通知の仕組み(#60)が決まってから考える。
- 期限で通報を消す処理。残す期間は、プライバシーポリシー(#65)と一緒に決める。(初版は、通報の記録を退会の後も残すと書き、期間を決めていない)
- 運営の画面の、メールアドレスを入れて停止リストの行を引く欄。見分けに困る問い合わせが実際に来てから考える(2026-11-27)。
- 停止した時点で、正規化した値が同じ、登録済みのほかのアカウントを、まとめて止めること。先に別名を用意して荒らす人が実際に出てから考える(2026-11-27)。
- 停止を解除した記録を残すこと。
- 運営の GitHub ID を、アプリの設定で持つこと。設定を変える PR で運営を増やせてしまうためである。
- 運営の中の役割分け。Cloudflare Access の policy に入っている人が運営、の 1 段だけにする。
- 手元の script で D1 を書き換える運営の操作。記録が人の注意に頼るためである。

## 受け入れ条件

- **F17-AC1** 作者の JS が、slide のログイン情報・管理画面の DOM・別の作者のスライドに届かない。
- **F17-AC2** 判定は JS の戻り値ではなく、外に出た request、開いたページの数、ダウンロードの有無で確かめる。
- **F17-AC3** 外部への通信と、同じスライド内の相対パスのファイルの読み込みは止まらない。
- **F17-AC4** 制限で止めた操作のために、スライドの表示全体が壊れない。
- **F17-AC5** スライドに止めている操作の種類と、外部と通信できることを、読者がヘルプページで確認できる。
- **F17-AC6** 削除。(通報と非表示が 1 つの条件に混ざっていたので、F17-AC7 以降に分けた)
- **F17-AC7** 運営が非表示にしたスライドは、公開中・作者限定・停止中のどの状態からでも、匿名の読者にも作者本人にも、共有 URL とファイルの配信 URL で読めない。
- **F17-AC8** 非表示のスライドは、表紙の画像、トップの一覧、プロフィールの一覧に出ない。
- **F17-AC9** 内部の cache が温まっていても、非表示にした直後の request から読めない。
- **F17-AC10** 非表示の間、作者の公開・停止・再開の操作は拒否され、公開状態は変わらない。
- **F17-AC11** 運営が解除すると、非表示にする前の公開状態に戻る。
- **F17-AC12** `admin.slide.community` の画面と操作は、Cloudflare Access が発行した token を Worker が検証できた request にだけ応答する。検証できない request には、存在しないページと同じ応答を返す。
- **F17-AC13** 作者の管理画面のそのスライドに、運営が非表示にしたことと、理由と日時が出る。
- **F17-AC14** 運営の画面に、非表示にしているスライドの一覧が、理由・日時・操作者(Cloudflare Access で確かめた本人)とともに出る。
- **F17-AC15** 運営が停止したアカウントのスライドは、すべて非表示と同じ扱いになり、その作者は新しいアップロードと公開ができない。
- **F17-AC16** ログインした読者が、viewer から、理由を「迷惑行為」「権利侵害」「その他」から選んで通報できる。説明を 500 文字まで添えられ、「その他」では説明が要る。通報には、開いていた共有 URL と版が添えられる。
- **F17-AC17** 運営の画面に、通報の一覧が出る。スライドごとに、通報した人数、理由、説明、最後の通報の日時が、新しい順に並ぶ。通報した人がだれかは出ない。
- **F17-AC18** ログインしていない読者が「通報する」を押すと、ログインを求められる。ログインすると、元のスライドに戻る。
- **F17-AC19** 運営の画面と操作は、`admin.slide.community` 以外の hostname(管理画面の origin、配信の origin)からは届かない。
- **F17-AC20** `admin.slide.community` の `robots.txt` は、すべての path を拒否する。
- **F17-AC21** `admin.slide.community` のすべての応答に、`X-Robots-Tag: noindex` と `Cache-Control: no-store` が付く。
- **F17-AC22** 削除。(停止中の作者に出す操作から、スライドの削除を外した。F17-AC32 に書き直した)
- **F17-AC23** 削除。(停止中の作者は、スライドを 1 つずつ削除できないことにした。F17-AC33 に書き直した)
- **F17-AC24** `/contact` に、問い合わせのメールアドレスが出る。
- **F17-AC25** 同じ読者が、同じスライドをもう一度通報すると、前の通報の理由と説明が置き換わり、通報した人数は増えない。
- **F17-AC26** スライドが削除されると、そのスライドへの通報も消える。
- **F17-AC27** 運営は、運営の画面で、`@handle` で指したアカウントを、理由を付けて停止できる。停止中のアカウントの一覧が、理由・日時・操作者とともに出る。
- **F17-AC28** 運営が停止を解除すると、その作者はアップロードと公開ができ、スライドは停止の前の公開状態に戻る。運営が個別に非表示にしていたスライドは、非表示のままである。
- **F17-AC29** 停止中のアカウントのプロフィール(`/@handle`)は、存在しないページと同じ応答になる。
- **F17-AC30** 停止中の人が退会して、もう一度ログインすると、停止中のままで、同じ理由が出る。
- **F17-AC31** 停止中の人は、通報とリアクションの投稿ができず、停止中であることが伝わる。
- **F17-AC32** 停止中の作者はログインでき、管理画面には、停止中であること、理由、日時、問い合わせ先と、退会の操作だけが出る。スライドの一覧と、アップロード・公開・削除の操作は出ない。
- **F17-AC33** 停止中の作者は退会できる。退会すると、停止していない人の退会と同じく、スライドとプロフィールが消える。スライドを 1 つずつ削除する操作は、拒否される。
- **F17-AC34** 通報の画面で、理由の選択肢(迷惑行為・権利侵害・その他)は、選ぶ丸と文言が横に並び、文言は通常の太さである。選択肢 1 つの押せる範囲は、高さ 44px 以上である。理由は見出し(`legend`)つきの `fieldset` にまとめ、キーボードで選べる。幅 1280px と 375px のどちらでも崩れない。(丸が文言の上に離れて出て、文言が太字になっていた崩れを直す。依頼者の指摘、2026-11-21)
- **F17-AC35** 通報の画面に、通報の対象のスライドが、同じ origin の埋め込みページ(F25 の `/embed/@handle/slug`。ページ番号つきの共有 URL なら、そのページ)の枠で出る。何を通報しているかが、その画面で分かる。枠には、スライドの共有 URL から決めた題名が付く。
- **F17-AC36** 通報の画面の CSP は、`frame-src 'self'` だけを足す。作者のスライドの origin やワイルドカードは足さない。公開されていない、公開を止めた、運営が非表示にした、停止中の作者の、存在しないスライドの通報の画面は、F17-AC16 のとおり 404 で、枠は出ない。
- **F17-AC37** 運営がアカウントを停止すると、停止リストに、そのアカウントのメールアドレスを正規化した値の HMAC(サービスだけが持つ鍵で作る)が記録される。停止リストには、停止した人のメールアドレスそのものも、正規化した値も入らない。(開いたあとに作る。issue #466)
- **F17-AC38** 正規化は、小文字にし、`@` の前の `+` から後ろを除き、`gmail.com` と `googlemail.com` のときだけ `@` の前の点も除く。停止した人と正規化した値が同じメールアドレス(`Bob.Smith+2@gmail.com` で停止した人に対して `bobsmith@gmail.com`)で登録またはログインすると、停止中として扱われ、F17-AC30 と同じく、停止中であることと理由が出る。(開いたあとに作る。issue #466)
- **F17-AC39** 正規化した値が違うメールアドレスは、停止リストに当たらない(`bob.smith@example.com` で停止した人に対して `bobsmith@example.com`、`bob@gmail.com` で停止した人に対して `rob@gmail.com`)。(開いたあとに作る。issue #466)
- **F17-AC40** 停止中の人が退会すると、その人の id とメールアドレスを持つ記録(`auth_user` の行)は消え、停止リストの行(値・理由・日時・操作者)だけが残る。もう一度登録またはログインすると、F17-AC38 のとおり停止中になる。(開いたあとに作る。issue #466)
- **F17-AC41** 停止中の人が退会したあと、運営の画面の停止中のアカウントの一覧に、その停止が「退会済み」として、理由・日時・操作者とともに出る。その行に、id、ハンドル、メールアドレスは出ない。(issue #466)
- **F17-AC42** 運営が停止を解除すると(本人の退会の前でも後でも)、正規化した値が同じメールアドレスで登録またはログインしても、停止中にならない。(issue #466)
- **F17-AC43** 正規化した値が同じために停止中になったアカウント(F17-AC38)は、もとの停止を運営が解除すると、停止中でなくなる。(issue #466)

## 決めたこと

読者への約束は「外部と通信しない」ではなく、「読者のアカウントに触れず、枠の外に出られない」に置く。外部への通信は止めず、通報を受け、運営が非表示やアカウント停止で対応する。通信先を実測して読者に見せることは、やめた。見た読者に何をしてほしいのかを説明できず、想定する脅威も特定できなかったためである(#133、#139)。次の順に作る。

1. 止めている操作と、外部と通信できることの、ヘルプページでの説明(済み)
2. 運営によるスライドの非表示(#135)
3. アカウントの停止
4. 通報(#134)。登録した人を対象に作る。

通報と運営の操作について、次のように決めた(2026-11-17)。

- 通報できるのは、ログインした人だけにする。ログインした人に向けた機能をこれから作るためである。ログインしていない人が、ログインの必要な機能を使おうとしたら、ログインを求める。
- 通報は、運営の画面の一覧で届ける。通知は作らない。
- 運営の画面は `admin.slide.community` に置き、Cloudflare Access で守る。誰が運営かは Cloudflare 側の policy で決め、アプリの設定やコードの PR では変えられないようにする。Worker は、Access が付ける token を必ず検証する。Access を通らない経路から届いた request を通さないためである。ローカルとテストでは、テスト用の鍵で署名した token で検証を通し、検証を飛ばす設定は作らない。
- Access の application と policy は、infra リポジトリ(非公開。Cloudflare の資源を Pulumi で宣言している)に書く。
- 運営の画面は、検索に載せない(`robots.txt`、`X-Robots-Tag`)。公開側のページと sitemap から、運営の画面へリンクしない。これは検索に載せないための対処で、守りは Access と token の検証に置く。
- F17-AC8 は、サーバーが新しく返す一覧に、非表示のスライドが出ないことを指す。トップの一覧の応答は、ブラウザが最長 60 秒使い回すことがあり、その間は非表示のスライドが一覧に残る。これは受け入れる(2026-11-17)。運営がすすめているように見える時間が短く、一覧から開いても、共有 URL と配信は非表示にした直後から拒否するためである。

アカウントの停止と、誰が使えるかについて、次のように決めた(2026-11-17)。

- slide.community に、アクセス制御は足さない。ログイン・アップロード・公開は、運営が招待したメールアドレスの人だけができる(第二スコープで、GitHub のアカウントの登録から変わった。[スライドを、ドロップして置く](f22-browser-drop.md))。読むことは、誰でもできる。読む側を閉じると、スライドを人に見せるという使い道が止まるためである。
- 通報やミュートなど、ログインが要る機能を使えるのも、当面は登録した人だけにする。F17-AC16・F17-AC18 の「読者」は、当面、登録した人を指す。(2026-11-27 に、本番で招待制を外した。メールアドレスを持つ人は、だれでも登録して、通報できる。下の「知らない人に開いたこと」)
- アカウントの停止(F17-AC15)は、知らない人に開く前に作る。作る時期は、2026-11-18 に「いま作る」と決め直した(下の節)。
- 停止中の作者は、ログインできる。理由を知り、自分のデータを消して去れるようにするためである。ログインさせない案は、退会のたびに運営の手作業が要るので、採らなかった。
- 問い合わせ先は、メールアドレス(`contact@slide.community`)にする。停止や通報の事情を、人に見せずに伝えられるようにするためである。GitHub の issue で受ける案は、内容が誰にでも見えるので、採らなかった。受け取ったメールは、Cloudflare Email Routing で運営へ転送する。転送の設定は infra リポジトリに書く。

通報の中身について、次のように決めた(2026-11-18)。

- 通報は、知らない人に開く前に、登録した人を対象に作る。開く直前にまとめて作ると、開く判断が遅れるためである。
- 理由は「迷惑行為」「権利侵害」「その他」の 3 つにする。「迷惑行為」には例を添える(偽のログイン画面、勝手に別のサイトへ飛ばす、宣伝だけの内容、不快な内容)。動く HTML ならではの害(情報をだまし取る、操作していないのに何かが起きる)を別々の選択肢にする案は、差が小さく、読者がどれを選べばよいか迷うので、採らなかった。
- 説明は任意で、500 文字まで書ける。「その他」のときだけ、説明を必須にする。読者は、問題のページを見ているその場で通報するので、場所を一言書けるようにする。
- 「通報する」は、だれにでも見せる。viewer の題名の右の「⋯」メニューの中に置き、ふだんの画面では目立たせない。登録していない人がログインに進むと、招待制のあいだは、`/login` の説明に、いまは招待制であることが出る([メールのコードでログインする](f28-email-login.md))。知らない人に開いたあとも、同じ画面のまま使える(2026-11-27 に開いた。`/login` には、はじめての人は規約に同意して登録する、と出る)。
- 通報の画面には、通報の対象のスライドを埋め込む(2026-11-21)。何を通報しているかを、画面で分かるようにするためである。同じ origin の埋め込みページを枠で開くので、CSP は `frame-src 'self'` だけを足し、作者のスライドを直接は動かさない。
- 通報は、1 人につき、1 つのスライドに 1 件にする。もう一度通報すると、理由と説明を置き換える。読者には、どちらのときも、受け付けたことだけを伝える。運営が知りたいのは「どのスライドが、何人から、何を理由に通報されたか」で、件数がそのまま人数になる。
- 通報した人の ID は保存する(1 人 1 件にまとめるため)。運営の画面には出さず、人数だけを出す。
- 通報は、期限では消さない。スライドが削除されたら、その通報も消す。

アカウントの停止の中身について、次のように決めた(2026-11-18)。

- アカウントの停止は、いま作る。通報が入り、通報を受けたあとに運営が取れる手段が、スライドの非表示だけになったためである。通報と同じく、開く直前にまとめて作ると、開く判断が遅れる。
- 運営は、停止を解除できる。運営が人を間違えることも、作者が問い合わせて事情が分かることもあるためである。解除すると、スライドは停止の前の公開状態に戻る。運営が個別に非表示にしたスライドは、停止とは別に扱い、非表示のままにする。
- 停止中のアカウントのプロフィールは、読者に見せない。止めるのはよほどのことなので、安全な側に倒す。名前とリンクが slide.community のページに残ると、止めた意味が薄れる。
- 停止は、利用者を識別できる値で持つ。退会して入り直しても、停止中のままにする。迷惑行為を繰り返させないためである。第二スコープで GitHub の user ID をやめるため、何で持つかは未決事項にある。(2026-11-25 に決めた。下を参照)
- 停止中の人ができるのは、停止の理由の確認、問い合わせ、退会だけにする。通報、リアクションの投稿、スライドを 1 つずつ削除する操作は、できない。削除は、解除のあとに行える。停止中のスライドは読めないので、残っていても被害は出ない。2026-11-17 に決めた「停止中も、自分のスライドを削除できる」(F17-AC22、F17-AC23)は、やめた(F17-AC32、F17-AC33)。
- 停止中の人の退会は、停止していない人の退会と同じに扱う。スライド・ファイル・プロフィールは消え、停止の記録(停止の対象を識別する値、理由、日時、操作者)だけが残る。
- 運営は、停止のときに理由を書く。理由と日時は本人の管理画面に出し、操作者は出さない(F17-AC13 と同じ)。

停止の対象を何で持つかを、次のように決めた(2026-11-25、依頼者。issue #366 の D2)。

- 停止リストに、正規化したメールアドレスの HMAC(サービスだけが持つ鍵で作る)を持つ(F17-AC37〜F17-AC40)。メールアドレスそのものは持たない。正規化は、小文字にし、`@` の前の `+` から後ろを除き、`gmail.com` と `googlemail.com` のときだけ `@` の前の点も除く。登録とログインのときに照らし合わせる。
- 理由: 招待をなくすと、`bob+2@gmail.com` のような別名で入り直せるようになる。HMAC だけを持てば、停止中の人が退会したあとに、id とメールアドレスの記録を消せる。
- 招待をなくす作業と一緒に作る(issue #466。招待は近日なくす予定)。それまでは、いまの暫定の実装(停止中の人の退会で `auth_user` の行を残す)で F17-AC30 を満たす。(2026-11-27 に、順番を変えた。停止リストより先に、本番で招待制を外した。下の節)
- ログインのときのメールアドレスの正規化(前後の空白を取って小文字にするだけ。[メールのコードでログインする](f28-email-login.md) の「決めたこと」)は、変えない。上の正規化は、停止リストで照らし合わせるためだけに使う。

知らない人に開いたことと、停止リストの中身について、次のように決めた(2026-11-27、依頼者。issue #466)。

- 本番で招待制を外した(2026-11-27)。登録した人は、通報、ミュート、フォロー、スライドを置くことが、すべてできる。読者だけの登録は作らない(#157 を #466 に統合した)。
- 停止リストは、開いたあとに作る。理由: 開いた日に、停止している人がいなかった。停止リストが本番に入るまでのあいだ、新しく止めた人は、別名で入り直せる。そのときは、運営がもう一度ハンドルで停止し、広がるときは「新しい登録を止める」を使う。
- 停止リストの 1 行に、HMAC のほかに、停止の理由、日時、操作者を持つ。入り直した人には、この行から理由を出す(F17-AC30、F17-AC38)。退会の後に残るのは、この行だけである(F17-AC40)。
- 運営が停止を解除したら、停止リストからその値を消す。解除した事実は残さない(F17-AC42、F17-AC43)。運営が人を間違えたときや、事情が分かったときに解除するので、本人について何も残さない。
- 退会した停止中の人は、運営の画面に「退会済み」と、理由・日時・操作者だけで出し、行ごとに解除できる(F17-AC41、F17-AC42)。見分ける手がかりは、理由と日時である。
- 停止した時点では、正規化した値が同じ、登録済みのほかのアカウントを、まとめて止めない。そのアカウントは、次にログインしたときから、停止リストの行によって停止中になる(F17-AC38 のまま)。別の停止の行は足さないので、もとの停止を解除すると、そのアカウントも停止中でなくなる(F17-AC43)。広がるときは「新しい登録を止める」を使う。
- HMAC の鍵は、`BETTER_AUTH_SECRET` とは別の secret にする(そちらを替えても、停止リストが残るように)。依頼者が作って本番に登録し、控えを依頼者の macOS のキーチェーンに置く。鍵を失うと、停止リストの値を作り直せない。
- 停止リストの値は、規約とプライバシーポリシーに名指しで書かない。プライバシーポリシー 第 8 条 4 項・5 項の「利用規約に反した行いの記録」に含めて読む。登録を断る根拠は、利用規約 第 3 条 3 項にある([利用規約とプライバシーポリシーを読む](f34-legal-pages.md))。
- 通報の記録は、通報した人が退会した後も残す(プライバシーポリシー 第 8 条 5 項)。期限では消さない(2026-11-18 の決定のまま)。
- 利用規約の禁止事項と運営の権限は、初版の第 8 条〜第 10 条に書いた。

トップページでの見せ方について、次のように決めた(2026-11-18)。

- トップページの機能の一覧に、この機能を載せない。作者の HTML を隔離して配ることは、他人の HTML を預かるサービスなら満たしていて当然の前提で、機能として並べると、当たり前を売りにして見えるためである。「安心」という言葉が、隔離では防げないもの(見た目でだますこと、外部への通信)まで保証しているように読めることも、理由である。
- 止めている操作と、外部と通信できることは、ヘルプページで説明する(F17-AC5)。確かめたい人は、そこで読める。

- 第四スコープで、ヘルプは、1 枚のページの節から、したいことごとの記事に分かれる([ヘルプで答えを見つける](f36-help-answers.md))。この文書の「ヘルプの節」「ヘルプの項目」は、対応する記事のことである。ヘルプの節の位置(`/help#<id>`)を指す書き方は、記事の URL を指す書き方に直す。

## 未決事項

- 停止リストを作る前に、依頼者に決めてもらうこと(F17-AC37〜F17-AC43。推測で作らない)。
  - 正規化した値が同じで、まだログインしていないアカウントの、停止中のアカウントの一覧(F17-AC27)での出方と、プロフィール・スライドを隠す時期。
  - 運営が、その同じ値のアカウントを、ハンドルでさらに停止したときの行の扱い。
  - `bob@gmail.com` と `bob@googlemail.com` を、同じ値にするか(いまの正規化は、ドメインをそろえない)。
  - 停止リストが入るまでに停止した人と、暫定の実装で退会して `auth_user` の行が残っている人を、停止リストへ入れる手順。
  - 鍵を入れる secret の名前と、鍵がないときの動き。
  - 退会済みの人が入り直したあとの、運営の画面での出方。
- 登録していない読者のログイン(#157)、通報した人の情報と停止の記録をプライバシーポリシーに書くこと(#65)、利用規約に書く禁止事項と運営の権限(#65)は、2026-11-27 に決めた(上の「決めたこと」)。

技術上の制約は [開発設計](../dev/design.md#url-と-html-の隔離) と [共有 URL と配信の実装設計](../dev/f03-sharing.md) を参照してください。
