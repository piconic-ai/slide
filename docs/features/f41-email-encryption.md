# F41 メールアドレスを暗号化して持つ

状態は、作らない機能です(2026-11-26、依頼者の判断)。第四スコープの作業 C で統合ブランチ `scope4` に積んだ実装を、本番に反映する前に、コード、migration、運営の画面の枠、設定、手順と設計の文書(`docs/dev/`)ごと取り除きました。登録者のメールアドレスは、第三スコープまでと同じく、D1 に平文で持ちます。この文書は、受け入れ条件の ID を残すために消しません。経緯は「決めたこと」と [第四スコープの統合の記録](../dev/scope4-integration.md) にあります。以前の段階は [ストーリーマップ](../story-mapping.canvas) で確認できます。

## 利用場面

運営は、登録者のメールアドレスを D1 に持っている(ログインの識別、招待の一覧)。D1 の中身だけが、何かの事故で外に出たとき、登録者のメールアドレスがそのまま読めてしまう。招待制をやめて、登録者が増える前に、データベースだけが漏れても、メールアドレスは読めない状態にしておきたい、と考えた。

この場面のために、暗号の鍵を secret として持ち、失わないように保管することを、運営に求めることになる。鍵を失うと、だれもログインできなくなり、戻す手段が無い。得られるものと釣り合わないので、やめた。

## 得られる結果

なし。この機能は提供しない。ログイン、招待、メールの送信は、第三スコープまでと同じ形で動く([メールのコードでログインする](f28-email-login.md))。

## 作らないこと

- 既存の行を書き換える操作と、運営の画面の「メールアドレスの暗号化」の枠。
- 鍵が無い環境では何もしない、という形で仕組みだけを入れておくこと。使わないコードと列、設定を残さない。
- メールアドレスのハッシュ(Gravatar に送る値)の保存。今までどおり、表示のときに作る。

## 決めたこと

メールアドレスの暗号化は作らない。仕組みも入れない(2026-11-26、依頼者の判断)。

- 鍵を失うと、だれもログインできなくなり、復旧の手段が無い。検索用の値の鍵を失っても同じで、メールアドレスから利用者を引けなくなる。運営が 1 人で、鍵の控えを確実に保管し続けることに頼る形になる。
- メールアドレスが漏えいすることより、ログインできなくなって、作者が預けたスライドを失うことの方が重い。
- 効くのは、D1 の中身だけが外に出た場合に限られる。Worker の secret や、Cloudflare のアカウントごと出た場合は、鍵も出るので守れない。
- 得られるものに対して、費用(鍵の管理、書き換えの運用、Better Auth との境の保守、鍵の入れ替え)と危険(鍵の紛失、鍵の取り違え、平文と暗号文が混ざる状態の不具合)が釣り合わない。
- 「鍵が無ければ今までどおり動く」という形で仕組みだけを残すこともしない。使わない経路は、確かめられないまま古くなり、あとで鍵を入れたときの危険だけが残る。
- 第四スコープの作業 C の実装(PR #547、#548、#550、#551、#558)は、本番に反映する前に取り除いた。本番の D1 には、この機能の列も行も入っていない。migration は、適用前だったので、ファイルごと消して番号を詰めた。取り除いたものの一覧は [第四スコープの統合の記録](../dev/scope4-integration.md) にある。作業票は #543。
- 作業 C のうち、`src/auth/config.ts` から Better Auth の組み立てを `src/auth/auth-store.ts` へ分けた整理は、暗号化と関係なく層の例外を減らすので、残した。

データベースの漏えいへの備えを、あらためて考えるときは、新しい機能の番号で、利用場面から書き直す。この文書の受け入れ条件の ID は使い回さない。
