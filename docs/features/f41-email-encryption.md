# F41 メールアドレスを暗号化して持つ

状態は未実装の設計案です(第四スコープ。統合ブランチ `scope4` に積み、本番にはまだ反映しない)。実装する段階は [ストーリーマップ](../story-mapping.canvas) で確認できます。

## 利用場面

運営は、登録者のメールアドレスを D1 に持っている(ログインの識別、招待の一覧)。D1 の中身だけが、何かの事故で外に出たとき、登録者のメールアドレスがそのまま読めてしまう。招待制をやめて、登録者が増える前に、データベースだけが漏れても、メールアドレスは読めない状態にしておきたい。

## 得られる結果

D1 に入れる登録者のメールアドレスは、暗号文と、検索用の値の 2 つにして持つ。データベースの中身だけが外に出ても、メールアドレスは読めない。ログイン、招待、メールの送信は、今までどおり動く。すでに登録している人の行は、運営の画面の操作で、反映の後に書き換える。

利用者には見えない。

## 体験の流れ

1. 運営が、暗号の鍵を作って secret に登録する(依頼者の作業。手順は `docs/dev/deploy.md`)。
2. 鍵を設定した環境では、新しく登録した人のメールアドレスは、暗号文と検索用の値だけが D1 に入る。
3. 運営が、運営の画面の「メールアドレスの暗号化」の枠で、残りの件数(まだ平文の行)を確かめ、「書き換える」を押す。少しずつ進み、残りが 0 になるまで、押すたびに続きから進む。
4. 鍵を入れ替えるときは、鍵の版を足す。前の版で書いた行も読め、書き換えると新しい版になる。

## 作る範囲

- 登録者のメールアドレスを持つ列の一覧と、それぞれの扱い(暗号化する、検索用の値だけにする、持たない)の決め。少なくとも `auth_user.email` と `invited_emails.email` が当たる。
- AES-256-GCM による暗号化と、別の鍵の HMAC-SHA-256 による検索用の値(前後の空白を取り、小文字にしてから作る)。暗号文に付ける鍵の版の番号。
- 暗号化と復号を、データベースの層(`src/db/`)の境で行うこと。Better Auth と、その外のコードには、今までどおりのメールアドレスを見せる。
- 既存の行を書き換える操作(少しずつ、再開でき、何度実行しても同じ結果)と、残りの件数。
- 運営の画面の「メールアドレスの暗号化」の枠(鍵が設定されているか、残りの件数、「書き換える」)。
- 鍵の作り方、登録、控えの保管、入れ替えの手順(`docs/dev/deploy.md`)。

## 作らないこと

- メールアドレスのほかの列の暗号化。運営の人のメールアドレス(操作の記録)の暗号化。
- 平文の列を消すこと、表を作り直すこと。本番のデータは残し、migration は足すだけにする。
- 鍵を作ること、登録すること、本番の行を書き換えること。依頼者が行う。
- 漏えいしたときの対応の手順書。
- メールアドレスのハッシュ(Gravatar に送る値)の保存。表示のときに作る。

## 受け入れ条件

- **F41-AC1** 鍵が設定されている環境で登録すると、D1 のどの表にも、その人のメールアドレスの文字列が残らない。
- **F41-AC2** その人は、同じメールアドレスでログインできる。大文字と小文字、前後の空白が違っても、今までと同じ結果になる。
- **F41-AC3** 同じメールアドレスで、2 人は登録できない。
- **F41-AC4** 招待したメールアドレスの人は、招待制のあいだも登録できる。
- **F41-AC5** 運営の画面の招待の一覧に、招待したメールアドレスが表示される。
- **F41-AC6** 鍵を設定する前に登録した人は、書き換えの前も後も、ログインできる。
- **F41-AC7** 書き換えの途中で、平文の行と暗号化した行が混ざっていても、ログインと招待が今までどおり動く。
- **F41-AC8** 「書き換える」を実行すると、平文の行が減り、最後に 0 になる。
- **F41-AC9** 「書き換える」を途中で止めて、もう一度実行しても、結果が同じである。
- **F41-AC10** 運営の画面の「メールアドレスの暗号化」の枠に、鍵が設定されているかと、残りの件数が出る。
- **F41-AC11** 暗号文に鍵の版の番号が付く。鍵の版を足して入れ替えた後も、前の版で書いた行を読める。
- **F41-AC12** 鍵の版を足した後に書き換えると、行が新しい版になる。
- **F41-AC13** 鍵が無い環境では、今までどおり平文で動き、運営の画面の「メールアドレスの暗号化」の枠に、「未設定」と出る。
- **F41-AC14** 鍵が間違っている環境では、ログインは失敗し、ほかの人のデータは壊れない。
- **F41-AC15** メールアドレス、暗号文、鍵が、ログ、エラーの文、通知の本文に出ない。
- **F41-AC16** Better Auth と、その外のコードが受け取るメールアドレスは、変更の前と同じである。
- **F41-AC17** Gravatar に送るメールアドレスのハッシュは、D1 に保存されない。
- **F41-AC18** 書き出し([データを書き出す](f35-data-export.md))のアカウントの情報には、本人のメールアドレスが平文で入る。
- **F41-AC19** 第四スコープの migration に、表や列を消す文がない。空の D1 に最初から最後まで適用でき、第三スコープの反映後の D1 にも足して適用できる。
- **F41-AC20** 登録者のメールアドレスを持つすべての列が、暗号化する、検索用の値だけにする、持たない、のどれかに分けられ、設計に書かれている。
- **F41-AC21** 鍵の作り方、登録、控えの保管、入れ替えの手順が書かれている。鍵を失うと、だれもログインできなくなることが書かれている。

## 決めたこと

第四スコープを作るにあたり、次のように決めた(2026-11-26、第四スコープの指示書)。

- D1 に入れる登録者のメールアドレスを、暗号文と、検索用の値の 2 つにして持つ。暗号は Web Crypto の AES-256-GCM。検索用の値は、暗号とは別の鍵で作った HMAC-SHA-256 で、作る前にメールアドレスの表記をそろえる(前後の空白を取り、小文字にする)(D-80)。
- 対象は、登録者のメールアドレスを持つすべての列である。少なくとも `auth_user.email` と `invited_emails.email` が当たる。設計の最初に、メールアドレスを持つ列を一覧にし、それぞれを「暗号化する」「検索用の値だけにする」「持たない」のどれにするかを決める。運営の人のメールアドレス(操作の記録)は対象にしない(D-81)。
- 暗号化と復号は、データベースの層(`src/db/`)の境で行う。Better Auth と、その外のコードには、今までどおりのメールアドレスを見せる(D-82)。
- 暗号文に鍵の版の番号を付け、鍵を入れ替えられるようにする。鍵は secret で、暗号の鍵(版ごと)と、検索用の値の鍵の 2 種類。鍵が無い環境では、今までどおり平文で動き、運営の画面に「未設定」と出す(D-08)。本番とローカルは、別の鍵を使う(D-83)。
- 既存の行は、反映の後に、運営の画面の操作で書き換える。少しずつ進み、途中で止まっても続きから再開でき、何度実行しても同じ結果になる。運営の画面に、残りの件数を出す。書き換えの途中は、平文の行と暗号化した行が混ざっても、ログインと招待が今までどおり動く。表や列は消さない(D-84、D-05)。
- メールアドレスのハッシュ(Gravatar に送る値)は、データベースに保存しない。表示のときに作る。今の実装がそうなっていることを確かめる(D-85)。
- メールアドレスを、ログ、エラーの文、通知の本文に出さない。既存の `src/site/no-email-leak.test.ts` の考え方を、足したコードに広げる(D-86)。
- 鍵の作り方、登録、控えの保管、入れ替えの手順を `docs/dev/deploy.md` に書く。鍵を失うと、だれもログインできなくなることを書く(D-87)。
- セキュリティの観点のレビューを 1 回行う(鍵の扱い、暗号文と検索用の値の作り方、平文が残る場所)(D-89)。
- 新しい secret(暗号の鍵)が無い環境では、その機能だけが何もせず、ほかは今までどおり動く(D-08)。
- 画面は、「書き換える」を、枠のいちばん下に置き、ほかのボタンと並べない。「未設定」は、枠の見出しのすぐ下に、何を設定すればよいかの 1 文と、手順の文書の場所とともに出す(05-UI-RULES.md)。
- [メールのコードでログインする](f28-email-login.md) の、メールアドレスの正規化(前後の空白を取って小文字にするだけ)は変えない。
