# F43 メールアドレスに触れる場所を限る

状態は実装済みです(第四スコープ。F43-AC1〜F43-AC16。2026-11-26 に、[メールアドレスを暗号化して持つ](f41-email-encryption.md) をやめる代わりに決めた)。実装の設計は [メールアドレスに触れる場所を限る実装設計](../dev/f43-email-handling.md)。統合ブランチ `scope4` に積む。実装する段階は [ストーリーマップ](../story-mapping.canvas) で確認できます。

## 利用場面

登録者は、ログインのために、メールアドレスを預ける。預けたアドレスが、どこで使われ、どこに出るのかを、知る方法がない。

運営は 1 人で、AI と開発し、ソースを公開している。メールアドレスは、扱いが悪いと漏れやすい情報である。漏れる道は、ログ、エラーの文、運営への通知、計測の記録、書き出し、調べるために手元に写したデータベースにある。機能を足すたびに、新しいコードがメールアドレスを読み、どこかに出してしまうかもしれない。読む場所が 1 つ増えたことは、レビューで差分を読むだけでは、気づきにくい。

データベースの中で暗号化する案は、採らない。鍵を失うと、だれもログインできなくなり、置いたスライドに届かなくなる。メールアドレスが漏れることより、こちらの方が重い。

## 得られる結果

- メールアドレスを持つ場所、読んでよいコード、出てよい場所が、リポジトリの 1 か所に、理由つきで宣言されている。宣言に無い場所が読む、または出すと、テストが失敗する。宣言を変える変更は、差分に出る。
- 登録者は、ヘルプで、メールアドレスが使われる場面を読める。その記事は、宣言から描くので、実装と食い違わない。
- 同じ人かどうかを比べる、回数を数えるなど、メールアドレスそのものが要らない所は、鍵つきのハッシュで足りる。鍵なしのハッシュは、メールアドレスでは元に戻せるので、保存しない。
- 運営は、本番のデータを手元に写すときの決まりと、メールアドレスを持つ表を除いて写す手段を持つ。

ソースを公開しているので、「読む場所と出る場所は、ここに書いたものだけ」という主張を、だれでも確かめられる。

## 体験の流れ

1. 開発者(人、または AI)が、機能を足す。新しいファイルが、メールアドレスの列を読む。
2. テストが失敗する。失敗の文に、どのファイルが、どの列に触れたかと、宣言に足す前に確かめること(出てよい場所の外に出さないこと、鍵つきのハッシュや利用者の番号で足りないか)が出る。
3. 番号やハッシュで足りるなら、そちらに直す。足りないなら、宣言に、ファイルと理由を足す。レビューする人は、宣言の差分で、読む場所が増えたことを知る。
4. 登録者が、ヘルプの「預かっている情報と、その守り方」を開く。メールアドレスを使う場面が、宣言と同じ内容で並ぶ。
5. 運営が、不具合を調べるために本番のデータを見たいとき、手順に従い、メールアドレスを持つ表を除いて写す。調べ終えたら、写しを消す。

## 作る範囲

- **宣言。** 1 つのファイルに、次の 3 つを、理由つきで持つ。
  - メールアドレスを持つ場所(表と列)。登録者のメールアドレス、運営の人のメールアドレス、鍵つきのハッシュを分ける。
  - 登録者のメールアドレスを読んでよい、または書いてよいファイル。
  - 登録者のメールアドレスが出てよい場所。
- **宣言を守るテスト。** ソースと schema を調べるテストと、実際に動かして応答、ログ、通知、計測を調べるテスト(いまの `src/site/no-email-leak.test.ts` を、宣言から回す)。
- **ハッシュの決まり。** メールアドレスから作る値は、鍵つきのハッシュだけを保存する。鍵は、既存の secret から導き、新しい secret を足さない。
- **ヘルプの記事。** 「預かっている情報と、その守り方」の、メールアドレスを使う場面を、宣言から描く。
- **本番のデータを写すときの手順と手段。** メールアドレスを持つ表を除いて書き出す手段と、写しの扱いの決まり。
- **試験と demo のデータ。** 実在しない domain のメールアドレスだけを使う。

対象は、登録者がログインのために預けたメールアドレスである。

## 作らないこと

- **データベースの中での暗号化。** [メールアドレスを暗号化して持つ](f41-email-encryption.md) は、やめた。理由は、その文書の「決めたこと」にある。
- **メールアドレスを持つ表を、別のデータベースに分けること。** D1 は、データベースをまたぐ transaction も join も持たないので、登録、退会、登録の前の掃除が 2 段になり、途中で止まった行の後始末が要る。復元(Time Travel)がデータベースごとになり、片方だけ戻すと食い違う。同じ Worker と同じ Cloudflare のアカウントの中なので、そこが破られたら守れない。分けることで効くのは、手元に写したデータの扱いで、それは、手順と、表を除いて写す手段で代える。
- **運営の招待の一覧を、ハッシュだけにすること。** 運営が、だれを招待したかを、一覧で読む。招待制をやめるときに、見直す([招待なしで登録できるようにする](f42-open-signup.md))。
- **運営の画面で、メールアドレスから人を探す機能。**
- **顔写真のない人に Gravatar を使う既定を変えること。** 規約の文面の論点で、依頼者が決める。
- **だれが、いつ、メールアドレスを読んだかの記録(監査ログ)。**
- **運営の人のメールアドレス、お問い合わせの宛先、作者がスライドや記事に書いたメールアドレスの扱い。** 対象の外である。

## 受け入れ条件

- **F43-AC1** D1 の表の列のうち、名前に `email`、`mail`、`address` を含むものは、すべて宣言に載っていて、「登録者のメールアドレス」「運営の人のメールアドレス」「鍵つきのハッシュ」「メールアドレスではない」のどれかに分けられている。宣言に無い列を足すと、テストが失敗する。
- **F43-AC2** 宣言に無いファイルが、登録者のメールアドレスの列を読む、または書くと、テストが失敗する。Better Auth が返す利用者の `email` を読むことも、同じに扱う。
- **F43-AC3** 宣言の、読んでよいファイルの行と、出てよい場所の行には、理由が 1 文ずつある。理由のない行があると、テストが失敗する。
- **F43-AC4** F43-AC1 と F43-AC2 のテストが失敗したとき、失敗の文に、触れたファイルと列、宣言のファイルの場所、足す前に確かめること(出てよい場所の外に出さないこと、利用者の番号や鍵つきのハッシュで足りないか)が出る。
- **F43-AC5** 宣言に載っているファイルが、もうメールアドレスの列に触れていない、またはファイルが無いと、テストが失敗する(宣言が、実際より広くならない)。
- **F43-AC6** 登録者のメールアドレスが出てよい場所は、宣言の一覧だけである。最初の一覧は、本人の設定の画面、本人のアカウントの情報の書き出し(画面と AI エージェントの `export_account`)、ログインの画面(本人が入れた値の表示)、その人へのログインのメールの宛先、運営の画面の招待の一覧である。
- **F43-AC7** F43-AC6 の一覧にない、ページ、API の応答、応答のヘッダー、スライドと記事の書き出し、AI エージェントの道具の答えに、どの登録者のメールアドレスも、その MD5、SHA-256 も出ない。本人が開いたときも、ほかの人が開いたときも、同じである。
- **F43-AC8** ログイン、断られたログイン、エラー、cron のすべての処理、すべての種類の通知を動かしたとき、ログ、運営への通知(すぐの通知と翌日のメール)、計測の記録に、どの登録者のメールアドレスも、その MD5、SHA-256 も出ない。
- **F43-AC9** GET で開けるページの経路を足して、メールアドレスが出ないことを確かめる対象にも、出てよい場所の一覧にも入れないと、テストが失敗する。
- **F43-AC10** メールアドレスの鍵なしのハッシュ(MD5、SHA-256 など)は、D1 にも R2 にも保存されない。Gravatar に送るハッシュは、顔写真を出すたびに作り、保存しない。
- **F43-AC11** メールアドレスから作って保存する値(ログインのコードの請求を数える値)は、鍵つきのハッシュである。同じ鍵と同じメールアドレスからは同じ値になり、鍵が違うと違う値になる。値から、鍵なしでメールアドレスを確かめられない。
- **F43-AC12** ログインのメールの控え(`mail_outbox`)は、ローカルと試験の設定(`MAIL_OUTBOX` が `on`)のときだけ書かれる。本番の設定(`wrangler.jsonc`)に `MAIL_OUTBOX` があると、テストが失敗する。書かれた行は、1 日で消える。
- **F43-AC13** ヘルプの「預かっている情報と、その守り方」に、メールアドレスを使う場面が、日本語と英語で、F43-AC6 の一覧と同じ数だけ出る。一覧に足すと、記事にも出る。記事にだけ書く、一覧にだけ書く、はできない。
- **F43-AC14** メールアドレスを持つ表を除いて D1 を書き出す手段がある。ローカルの D1 で動かすと、書き出したものに、宣言の「登録者のメールアドレス」の列を持つ表の行が 1 つも無く、ほかの表の行はある。除く表は、宣言から決まる(宣言に表を足すと、書き出しからも除かれる)。
- **F43-AC15** 本番に反映する手順の文書に、本番のデータを手元に写すときの決まりがある。不具合の調査や試験に、メールアドレスを持つ表を写さないこと、F43-AC14 の手段の使い方、写しを置く場所、調べ終えたら消すこと、D1 のバックアップと復元用の履歴にはメールアドレスが入ること、が書いてある。
- **F43-AC16** 試験の台本のデータと demo のデータに入っているメールアドレスは、実在しない domain(`example.com`、`example.org`、`example.net`、`.example`、`.test`、`.invalid`)のものだけである。それ以外の domain のアドレスを足すと、テストが失敗する。

## 決めたこと

- **暗号化をやめ、触れる場所を限る(2026-11-26、依頼者の判断)。** メールアドレスは、クレジットカードの番号などに比べれば、漏れたときの害が小さい。一方、暗号化の鍵を失うと、だれもログインできず、置いたスライドに届かなくなる。暗号化が効くのは、データベースだけが漏れた場合に限られ、Worker や Cloudflare のアカウントが破られたら効かない。得るものと、費用と危険が釣り合わない。漏れやすいのは「扱い」なので、使う機会を減らし、読む場所と出る場所を宣言して、テストで守る方が、実際に効く。
- **宣言は、テストが読むデータにする。** 文書に書くだけでは、実装とずれる。宣言を 1 つのファイルに持ち、テスト、ヘルプの記事、表を除いて書き出す手段が、同じ宣言を読む。
- **宣言に足すことは、禁じない。** 足すには、理由を 1 文書く。読む場所が増えたことが、差分で見えればよい。
- **鍵つきのハッシュの鍵は、既存の secret から導く。** 新しい secret を足さない。この鍵を失っても、メールアドレスそのものは `auth_user` に残っているので、ハッシュは作り直せる。ログインできなくなることはない。
- **鍵なしのハッシュを、マスクとして使わない。** メールアドレスは、総当たりで元に戻せる。Gravatar は鍵なしのハッシュを求めるので、保存せず、出すたびに作る(いまの実装のまま)。
- **別のデータベースに分けない。** 理由は「作らないこと」に書いた。分けることで効く経路(手元に写したデータ)は、F43-AC14 と F43-AC15 で代える。
- **対象は、登録者がログインのために預けたメールアドレスに限る。** 運営の人のメールアドレス(Cloudflare Access が渡すもの、招待した人の記録)は、宣言に「運営の人のメールアドレス」として載せるが、F43-AC6〜F43-AC8 の対象にしない。
