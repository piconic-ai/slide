# F28 メールのコードでログインする

状態は実装済みです(第二スコープ。人の確認として、メールの実際の送信、Turnstile、Gravatar の実際の取得、実機のブラウザ(iOS Safari など)でのプロフィール画像の縮小が残る)。ログイン、利用者の識別子の切り替え、招待の一覧、メールの送信、GitHub の取り除き(F28-AC1〜F28-AC34)は実装した。プロフィールの文字の項目と、設定の「プロフィール」「アカウント」(F28-AC35〜F28-AC40、F28-AC53、F28-AC54)も実装した。プロフィール画像のアップロードと配信(F28-AC41、F28-AC49、F28-AC93〜F28-AC100)も実装した。Gravatar、運営の画面でのプロフィール画像の取り外し、退会のときの消し方(F28-AC46〜F28-AC48、F28-AC50〜F28-AC52)も実装した。画像を変えた直後に、ヘッダーなどのほかの場所にも新しい画像が出ること(F28-AC101)も実装した(2026-11-25。issue #366)。第三スコープで、運営がハンドルを変えられるようにし、本人は変えられないことを F28-AC113 で書き直した(統合ブランチ `scope3` に入り、本番にはまだ反映していない)。プロフィール画像は、ブラウザが 256×256 の PNG に縮めてから送り、サービスはその PNG の構造を確かめて、表示に要らない部分を取り除いて保存する(2026-11-24。Cloudflare Images の binding は使わない)。[プロフィールとプロフィール画像の実装設計](../dev/f28-profile.md) の「アップロード」。実装の設計は [メールのコードでログインする実装設計](../dev/f28-email-login.md) と [プロフィールとプロフィール画像の実装設計](../dev/f28-profile.md)。第四スコープで、招待制を外せる設定と登録の守り([招待なしで登録できるようにする](f42-open-signup.md))、メールアドレスの暗号化([メールアドレスを暗号化して持つ](f41-email-encryption.md))、退会の確認から書き出しへの案内([データを書き出す](f35-data-export.md))を足す(F28-AC114 から。未実装の設計案)。実装する段階は [ストーリーマップ](../story-mapping.canvas) で確認できます。

## 利用場面

登壇者が、GitHub のアカウントを持っていない。あるいは、持っていても、スライドの置き場に GitHub の情報を渡したくない。運営から招待されたメールアドレスなら、持っている。パスワードを新しく作って覚えることはしたくない。

また、作者は、自分のプロフィール(名前、自己紹介、プロフィール画像、リンク)を、GitHub の公開プロフィールの写しではなく、自分で決めて出したい。

## 得られる結果

運営に招待されたメールアドレスがあれば、メールに届く 6 桁のコードだけでログインして、スライドを置ける。GitHub のアカウントは要らない。初めての人は、ハンドルと表示名を自分で決める。プロフィールは、設定で自分で書く。プロフィール画像は、何もしなければ Gravatar の画像が出て、アップロードすれば上書きできる。

## 体験の流れ

1. ヘッダーの「ログイン」(またはトップの「ログインして続ける」、フォローなどのログインを促す表示、MCP の接続の許可)から、戻り先をつけて `/login` を開く。メールアドレスを入れ、「コードを送る」を押す。
2. 6 桁のコードがメールに届く。画面は、コードの入力に変わる。コードを入れて「ログイン」を押す。
3. 初めての人は、`/welcome` でハンドルと表示名を決める。決めるまで、ほかの画面へ進めない。
4. ログインを始めた元のページへ戻る。トップでファイルを預けていた場合は、[スライドを、ドロップして置く](f22-browser-drop.md) と同じく、受け取りに進む。
5. 設定で、表示名、自己紹介、場所、Web サイト、SNS のリンク、プロフィール画像を書く。プロフィールに出る。

## 作る範囲

- `/login`(メールアドレスの入力、コードの入力)と、`/welcome`(ハンドルと表示名)。
- メールで送る 6 桁のワンタイムコード。期限、入力の回数、送信の回数の上限、ボットを防ぐ確認(Turnstile)。
- 招待の一覧(メールアドレス)と、運営の画面での足す・外す・一覧。
- 送信の口。ローカルでは、送らずに送信箱(ローカルの表やログ)に書く。本番の送信の実装は作る。
- 利用者の識別子を、GitHub の利用者番号から、サービスが発行する番号に切り替えること。
- ハンドルの決まりと予約語。
- GitHub でのログイン、GitHub からのプロフィールの同期、「GitHub でフォローしている人が参加した」お知らせの取り除き。古い経路は `/login` へ送る。
- ログインに進む入口(ヘッダー、トップ、フォローなどのログインを促す表示、MCP の接続の許可)の、`/login` への切り替え。
- 設定の「プロフィール」(表示名、自己紹介、場所、Web サイト、SNS のリンク 3 つまで、プロフィール画像)と「アカウント」(ハンドルとメールアドレスの表示)の枠。
- プロフィール画像の配信(アップロードした画像、Gravatar の画像、頭文字の順)。運営の画面の、アップロードした画像を外す操作。

## 作らないこと

- パスワード、マジックリンク、Google、GitHub でのログイン。メールのコードだけにする。
- ログインをだれにでも開くこと。利用規約とプライバシーポリシーに、メールアドレスの扱いをまだ書けていない。ログインは招待制のまま。第四スコープで、設定 1 つで外せ、戻せるようにするが、本番の値は変えない([招待なしで登録できるようにする](f42-open-signup.md))。
- 「ログインはできるが置けない人」。ログインできた人は、全員スライドを置ける。
- メールアドレスの変更の画面、受信箱を失ったときの戻し方の画面。問い合わせ(helpdesk)で個別に対応し、ヘルプにそのことを書く。
- ハンドルの変更。
- 読者がプロフィール画像を通報する専用の窓口。既存の通報の窓口で受ける。
- 利用規約とプライバシーポリシーの本文の更新。

- **F28-AC86** 削除。(理由: 2026-11-24 の依頼者の決定で、プロフィール画像の縮小を Cloudflare Images の binding からブラウザ(canvas)に移した。サービスは PNG、JPEG、WebP の別を見なくなり、「サーバーと同じ文言」が成り立たない。F28-AC96 で書き直した)
- **F28-AC87** 選んだファイルを送っている間に、もう一度選んでも、アップロードは 1 回しか送られない。
- **F28-AC88** プロフィール画像を差し替えると、前の画像は R2 に残らず、1 つの画像だけが残る。保存の途中で止まって、行のない画像が残ったときも、外す操作(本人、運営)で片付く。
- **F28-AC89** 「Gravatar の画像を使う」を切ると、取ってきて保管していた Gravatar の画像が消える。切ったままのとき、Gravatar に問い合わせない。
- **F28-AC90** 設定の「プロフィール画像」の行で、画像と、同じ行に並ぶボタンは、縦の中心がそろい、並んだ 2 つのボタンは同じ高さになる。行の下に出る通知(保存した、断った)は、行から 16px 離れる。
- **F28-AC91** `/auth/github`、`/auth/github/callback`、`/auth/invitation-only`、`/auth/handle-taken` は、見つからないページ(404)になる。`/login` へは送らない。GitHub でログインする手段は残っていない。
- **F28-AC92** 実際に送るコードのメールの差出人は、表示名が `slide.community` で、アドレスが `MAIL_FROM` の値になる(メールソフトの一覧に `slide.community` と出る)。
- **F28-AC93** 設定でプロフィール画像のファイル(PNG、JPEG、WebP)を選ぶと、ボタンを押さなくても、すぐにブラウザが画像の中央を正方形に切り出して 256×256 の PNG に縮めて送り、プロフィール画像が切り替わる。送られるのは縮めた PNG だけで、元のファイルは送られない。
- **F28-AC94** 縮めたプロフィール画像は、ブラウザがその画像を表示する向き(EXIF の向き)になる。
- **F28-AC95** 送られる PNG と、保存されるプロフィール画像には、選んだ画像のメタデータ(EXIF、PNG の文字の情報、撮った場所など)が残らない。
- **F28-AC96** スクリプトが動くとき、PNG、JPEG、WebP 以外のファイル、1 MB を超えるファイル、画像として読めないファイル、縦か横が 8192 ピクセルを超える画像は、選んだ時点で送られず、入力欄の下に理由が出て、欄は空になる。
- **F28-AC97** サービスは、縦横がちょうど 256×256 で、512 KB 以下で、構造が壊れていない(チャンクの長さと CRC が合い、IHDR が先頭、IEND が最後で、その後に何もない)PNG だけを保存する。それ以外(JPEG、WebP、ほかの大きさの PNG、壊れた PNG、PNG に見せかけた HTML や SVG)は、断られ、理由が出て、何も保存されない。
- **F28-AC98** サービスは、送られた PNG から、表示に要らない補助チャンク(文字、EXIF、時刻、アニメーションなど)を取り除いてから保存する。ブラウザを通さずに送られた PNG も同じである。
- **F28-AC99** スクリプトが動かないとき、またはブラウザが画像を縮められないとき、設定の「プロフィール画像」の欄に、画像を変えられないことと理由が出る。ファイルは選べず、ファイルを送るボタンもない。アップロードした画像を外すことはできる。
- **F28-AC100** ブラウザで縮めるようになる前に保存した WebP のプロフィール画像は、そのまま配られる。配る応答の `Content-Type` は、保存した物が何を言っても、PNG か WebP の画像の型に固定され、`X-Content-Type-Options: nosniff` が付く。
- **F28-AC101** プロフィール画像を変えると(アップロード、差し替え、外す、運営が外す、「Gravatar の画像を使う」の切り替え)、ページを開き直さなくても、ヘッダー、プロフィール、viewer の作者の画像が、すぐ新しい画像になる。同じタブでページの間を移ったときも、前の画像は出ない。
- **F28-AC102** PC でログインしたまま、スマホでもログインすると、どちらの端末でもログインしたままである。
- **F28-AC103** ログインしたあと、23 時間以内ごとに操作を続けていれば、ログインから何日たっても、ログインは切れない。
- **F28-AC104** 最後に期限が延びてから 24 時間、何も操作しないと、ログインが切れる。期限が延びるのは、1 時間に 1 度までである。
- **F28-AC105** ある端末でログアウトすると、その端末のログインだけが切れ、ほかの端末はログインしたままである。
- **F28-AC106** 削除。(理由: 2026-11-25 の依頼者の判断で、端末ごとにログアウトできるようになり、「ほかの端末からログアウト」と、ほかの端末の数の表示は要らなくなった。F28-AC112 で書き直した)
- **F28-AC107** 招待の一覧から外された人と、退会した人は、すべての端末でログインが切れる。
- **F28-AC108** 設定の「アカウント」に、ログインしている端末が一覧で出る。各行に、端末の大まかな名前(「iPhone・Safari」「Mac・Chrome」など)、ログインした日時、最後に使った日時が出る。いまの端末の行には「この端末」と出る。期限の切れた端末は出ない。
- **F28-AC109** 一覧のほかの端末の行で「ログアウト」を押すと、その端末のログインだけが切れ、押した端末と、残りの端末はログインしたままである。
- **F28-AC110** ほかの人の端末や、ない端末を指定して「ログアウト」を送っても、どの端末のログインも切れない。
- **F28-AC111** 端末について保存するのは、大まかな名前だけである。user agent そのものと接続元(IP アドレス)は保存しない。名前がわからない端末は「不明な端末」と出る。
- **F28-AC112** 設定の「アカウント」の端末の一覧で、いまの端末の行にも、ほかの行と同じく右端に「ログアウト」が出る。押すと、その端末のログインだけが切れて、トップに戻る。一覧の外には、ログアウトのボタンも「ほかの端末からログアウト」もない。
- **F28-AC113** 本人は、決めたハンドルをあとから変えられない。変える必要があるときは、お問い合わせを受けて運営が変える([コミュニティをつくる](f30-communities.md) の F30-AC7)。
- **F28-AC114** 利用を止められていない人の退会の確認のページの、確認の入力欄より上に、「退会の前に、データを書き出せます。」と、設定の「データを書き出す」へのリンクが出る([データを書き出す](f35-data-export.md))。
- **F28-AC115** 招待制のあいだ(設定 `OPEN_SIGNUP` が外れていないとき。既定)、招待されていないメールアドレスには、コードが送られない。招待制を外しているときの動きは、[招待なしで登録できるようにする](f42-open-signup.md) の F42-AC2〜F42-AC5 にある。
- **F28-AC116** 招待制のあいだ、`/login` の説明に、いまは招待制であること、運営が登録したメールアドレスでだけログインできることが出る。招待制を外しているときは、招待が要ると読める文言が出ない(F42-AC5)。
- **F28-AC117** メールアドレスを暗号化して持つようになっても([メールアドレスを暗号化して持つ](f41-email-encryption.md))、ログイン、招待、メールの送信は、今までどおり動く。
- **F28-AC118** メールアドレスは、どの API の応答にも出ない。ただし、本人の設定ページを組み立てる応答と、本人の書き出し(アカウントの情報の JSON、AI エージェントの `export_account`。[データを書き出す](f35-data-export.md))を除く。ログにも出ない。

## 決めたこと

第二スコープを作るにあたり、次のように決めた(2026-11-22)。

- 招待するメールアドレスは D1 の表に持ち、運営の画面(Cloudflare Access で守られた画面)で足す・外す。運用設定の値には持たない。後でログインをだれにでも開き、置くことだけを招待制に残すときも、同じ表を「置ける人」の一覧として使える。
- メールの送信は「送信の口」を 1 つ作り、ローカルでは送らずに送信箱に書く。本番の送信の実装は作るが、secret、DNS(SPF、DKIM、DMARC)、送信サービスの登録は依頼者が行う。送信のサービスは、設計の文書で候補を比べて決める。
- 利用者の識別子を、GitHub の利用者番号から、サービスが発行する番号(Better Auth の利用者の id)に切り替える。所有者・フォロー・ミュート・お知らせ・通報・MCP など、利用者の識別子を持つすべての表が対象。本番のデータは空にしてよいので、既存の行を移す処理は書かない。
- ログインはメールに送る 6 桁のコードだけ。Better Auth の現行のドキュメントを読み、メールのワンタイムコードの仕組みがあればそれを使う。記憶で決めない。
- コードの有効期限は 10 分。1 つのコードへの入力は 5 回まで。5 回間違えるとそのコードは無効になる。
- コードの送信には、メールアドレスごとと接続元ごとの回数の上限を置く。値は設計の文書で決め、運用設定で変えられるようにする。ボットを防ぐ確認(Turnstile)を置く。
- 招待されていないメールアドレスが入力されても、画面と応答は同じ「コードを送りました」にし、コードは送らない。招待されているかどうかを、応答の内容・時間で知られないようにする。
- ログインそのものを招待制にする。ログインできた人は、全員スライドを置ける。
- 初めてログインした人は、`/welcome` でハンドルと表示名を決め、利用規約とプライバシーポリシーに同意するまで、ほかの画面へ進めない。ログアウトの代わりに、「登録せずに終了する」で終われる(2026-11-23。F28-AC4 を F28-AC56 で書き直した)。
- ハンドルの決まりは、いまの `accounts` の制約(英小文字、数字、`-`、1〜39 文字、`-` で始まらない)を保つ。予約語を足す: 既存と新しい経路の先頭の語(`login`、`welcome`、`settings`、`slides`、`help`、`auth`、`api`、`mcp`、`embed`、`events`、`notifications`、`operator`、`_preview` など)と、`admin`、`slide`、`support`、`me` のような紛らわしい語。一覧は設計の文書に書き、テストで経路の一覧と突き合わせる。ハンドルは本人には変えられない(第三スコープで、お問い合わせを受けて運営が変え、前の URL を転送できるようにした)。
- メールアドレスは、本人の設定ページ以外のどの画面、どの API 応答、どのログにも出さない。
- メールアドレスの変更、受信箱を失ったときの戻し方の画面は作らない。ヘルプに、問い合わせで個別に対応することを書く。
- MCP の接続の許可(OAuth の同意)は、新しいログインの session で動くようにする。未ログインなら `/login` へ進み、戻ってきて同意の画面を出す。
- プロフィールは本人が設定ページで書く。表示名(必須、50 文字まで)、自己紹介(160 文字まで)、場所(50 文字まで)、Web サイト(1 つ)、SNS のリンク(3 つまで)。URL は `https:` だけを受け付ける。
- プロフィール画像は、アップロードした画像、Gravatar の画像、頭文字の順に使う。「Gravatar の画像を使う」の切り替えを置き、既定は入にする。
- Gravatar の画像は、サービスが取りに行って配る。ページにメールアドレスのハッシュや Gravatar の URL を載せない。viewer と管理画面の CSP を広げない。取りに行った画像は cache し、Gravatar に画像が無いときは頭文字にする。
- アップロードできる画像は PNG、JPEG、WebP、1 MB まで。正方形に縮めて R2 に置き、サービスから配る。元の画像は保存しない(縮める場所は、2026-11-24 にブラウザへ移した。下の決めたことを参照)。
- プロフィール画像は、ブラウザ(canvas)で縮める(2026-11-24、依頼者)。Cloudflare Images の binding は使わない(`wrangler.jsonc` から外した)。ブラウザが、選んだ画像を読み(EXIF の向きは、ブラウザが表示する向きに合わせる)、中央を正方形に切り出して 256×256 の PNG に書き出して送る。サービスは、届いた PNG を信用せず、構造(シグネチャ、IHDR の縦横、長さ、CRC、チャンクの並び)を確かめ、表示に要らない補助チャンクを取り除いて保存する。スクリプトが動かないときは、プロフィール画像を変えられない。これまでに保存した WebP の画像は、そのまま配る。
  - 理由: Cloudflare Images の Free プランは、月 5,000 件の変換を超えると、新しい変換がエラーになる。1 人で運用するので、この上限を抱えたくない。PNG にするのは、Safari が canvas から WebP を書き出せず、JPEG は透明が黒くなるため。書き出し直すので、元の画像のメタデータは残らない。
  - サービスが保存する PNG の上限は 512 KB にした。256×256 の 8 ビット RGBA を圧縮せずに書いても約 257 KB(262,400 バイトと、わずかな枠)なので、色の情報を足しても十分に収まる。上限は、1 回のアップロードで保存する物の大きさと、確かめる処理の量を抑える。
  - 残すチャンクは、IHDR、PLTE、IDAT、IEND と、IDAT より前にある tRNS(透明)、sRGB・gAMA・cHRM(色の意味)。ブラウザが色の情報を付けて書き出したとき、色が変わらないように残す。埋め込みの色のプロファイル(iCCP)は取り除く。圧縮されたデータで、画像を見るすべての人のブラウザが読むことになり、sRGB で描いた canvas には要らないため。文字(tEXt、zTXt、iTXt)、eXIf、tIME、pHYs、アニメーション(acTL、fcTL、fdAT)などは取り除く。知らない必須チャンクがあれば断る。画素は復号しない(画素が壊れた PNG は表示されず、頭文字が出る)。
  - 採らなかった案: (1)Images の binding のまま使う。Free の月 5,000 件の上限を超えると、プロフィール画像を変えられなくなるため。(2)Images Paid にする。費用がかかるため。(3)サービス(Workers)で自前に縮める。Workers で JPEG や WebP を復号して縮めるのは、CPU 時間とメモリーの面で重く、復号の処理の不具合を抱えることになるため。
- 不適切なプロフィール画像への対応は、運営の画面から、その人のアップロードした画像を外せる操作だけを作る。読者からの通報の種類は足さない。
- 自己紹介とリンクは、第二スコープでは公開中のスライドの有無にかかわらず出す(ログインが招待制なので、広告目的の登録は起きない)。ログインをだれにでも開くときに、出す条件を見直す。
- 「GitHub でフォローしている人が参加した」お知らせは、GitHub の情報を前提にするので、取り除く([知りたい出来事が、お知らせに届く](f20-notifications.md))。
- メールアドレスの正規化は、前後の空白を取って小文字にするだけにする。`+` つきのアドレスは、元のアドレスとは別のアドレスとして扱う。運営は、人が入力するとおりのアドレスを招待する(2026-11-22、作業 A1 が実装の設計で決めた)。
- 送信の回数の上限の既定は、メールアドレスごとに 1 時間 5 通、接続元ごとに 1 時間 20 通。環境の値 `LOGIN_CODE_LIMITS` で変える(2026-11-22、同上)。
- 運営の画面の招待の一覧には、招待したメールアドレスが出る。メールアドレスを出さない範囲(F28-AC22、F28-AC118)は、読者と本人に向けた画面と API で、運営の画面は含まない。
- Web サイトと SNS のリンクは、`https://` から書いた URL だけを受け付ける。`example.com` のように scheme を省いたものは、補わずに断り、理由を出す(2026-11-22、作業 A2 が実装の設計で決めた)。
- 本番のデータは空にしてよい。本番の唯一のアカウントは、いまの GitHub でのログインのまま退会し、新しい方法で作り直す(issue #331)。

- 退会のあとは、トップではなく `/goodbye` を見せる(2026-11-23、依頼者)。退会できたことを、利用者が確かめられるようにするため。載せるのは、実際に消えるもの(スライド、記事、関連リンク、共有 URL、フォロー・ミュート・お知らせ、プロフィール、プロフィール画像、メールアドレス)だけで、運営の招待や、ハッシュだけの記録が残ることは書かない(依頼者が、注記は不要と判断した)。
- 規約への同意は、`/welcome` で取る。`/login` では、確認を促す文とリンクだけを出し、同意は求めない(2026-11-23、依頼者)。同意した日時(秒)を、アカウントの行(`accounts.terms_accepted_at`)に記録する。規約の版は、本文が固まるまで残さない。
  - 理由: 同意の前は、保存を最小にする。同意しない人の記録(メールアドレスを持つ `auth_user`)は、本人の操作(「登録せずに終了する」)と、毎時の掃除(24 時間)で消す。コードを送ってから `/welcome` に進む流れは、emailOTP の定番の流れで、Better Auth の仕組みの上に載る。
  - 採らなかった案: (1)自前のワンタイムコードにして、同意の前はメールアドレスを保存しない。招待の確認と送信の回数は、すでに表のハッシュで持てるが、Better Auth の emailOTP(期限、回数、一度きり、保存の封じ方)を自前で作り直すことになり、守りの実装が増えるため。(2)`/login` で同意を取る。ログインのたびに同意を求める画面になり、同意の前に利用者の記録が `auth_user` に残る点は同じ(コードを入れた時点で作られる)で、初回の画面(`/welcome`)で取るほうが自然なため。
- コードのメールの差出人の表示名は `slide.community` にする(2026-11-24、依頼者)。表示名がないと、Gmail の一覧に `noreply` と出るため。件名と本文にも、サービス名の `slide.community` を使う。

- 複数の端末で、同時にログインできるようにする(2026-11-25、依頼者)。手元のスマホと PC の両方でスライドを見たいため。ログインの期限は、最後の操作から 1 日にし、使っている間は延ばし続ける。ログインからの絶対的な上限は置かない。設定の「アカウント」に「ほかの端末からログアウト」を置く。端末の一覧は、初めは出さなかった。

- 端末ごとにログアウトできるようにする(2026-11-25、依頼者)。「ほかの端末からログアウト」だけでは足りず、端末を選んで切りたい。見分けるために、ログインのときの user agent から、OS とブラウザの大まかな名前(「iPhone・Safari」など)だけを作って session に保存する。user agent そのものと IP アドレスは、これまでどおり保存しない。一覧には、その名前、ログインした日時、最後に使った日時(期限を延ばした時刻。1 時間単位)を出す。プライバシーポリシーに、この名前を保存することを書く(本文の更新は人の確認に挙げる)。
  - 採らなかった案: 何も新しく保存せず、日時と「この端末」だけで見分ける。端末が 3 つ以上あると、どれがどれかわからないため。
- 端末の一覧のいまの端末の行にも「ログアウト」を置き、一覧の外のログアウトのボタンと「ほかの端末からログアウト」はなくす(2026-11-25、依頼者)。一番下のログアウトは、どの端末を切るのかがわかりにくく、端末ごとに切れるなら「ほかの端末からログアウト」は要らないため。ヘッダーのメニューのログアウトは残す。

第二スコープの確認で、暫定で動かしていたものを、次のように決めた(2026-11-25、依頼者。issue #366 の D1、D3〜D6)。どれも、いまの動きのままにする。

- 退会した人のメールアドレスは、招待の一覧に残す。退会した人は、同じメールアドレスで、もう一度登録できる。招待制は近日なくす予定で、そのときにこの問いはなくなる。
- プロフィール画像に選べるファイルの上限は、1 MB のままにする(F28-AC96)。必要になったら上げる。
- 画像を選んで切り替わった後に、「プロフィール画像を変えました。」を出す。
- プロフィール画像の URL の版(`?v=u<ミリ秒>`、`?v=g…`。#396)から、だれでも、画像をアップロードした時刻と、Gravatar の画像を使っているかを読める。これを許す。
- 自己紹介の改行は残す(3 つ以上の連続は空行 1 つにする)。
- Web サイトと SNS のリンクは、`https://` から書いた URL だけを受け付け、scheme を補わない(2026-11-22 の決めたことのまま)。
- 運営がプロフィール画像を外すときは、理由を必須にする(F28-AC51)。
- 運営に外された画像を、本人はすぐにアップロードし直せる。
- 「Gravatar の画像を使う」の既定は入にする(F28-AC47)。
- 第二スコープのワイヤーフレームとの差は、そのままにする(issue #366 の D12): スライドの編集は既存の 1 列のまま([URL を渡して読んでもらう](f03-sharing.md) の F03-AC141)、設定のプロフィール画像のファイルの入力は素の表示のまま、トップの注記に「メールのコードで」を足さない。
- 停止中の人が退会して入り直したときに停止のままにする条件(F17-AC30)は、停止リストに、正規化したメールアドレスの HMAC だけを持って満たす(2026-11-25、依頼者。issue #366 の D2)。招待をなくす作業と一緒に作る(issue #466)。中身は [知らない人のスライドも、安心して開ける](f17-safe-viewing.md) の「決めたこと」と F17-AC37〜F17-AC40 にある。ログインのときのメールアドレスの正規化(上の 2026-11-22 の決めたこと)は変えない。

第四スコープで、次のように決めた(2026-11-26、第四スコープの指示書)。

- 招待制は、設定 1 つ(`OPEN_SIGNUP`)で外せ、戻せる。既定は、今までどおりの招待制。外している間は、招待の一覧に無いアドレスにもログインのコードを送り、登録できる。登録の流れ(規約への同意、ハンドル)は変えない。このスコープでは、本番の値を変えない(D-125、D-126、D-158)。
- ログインのメールに、サービス全体の 1 時間あたりの上限(既定は 100 通。仮)を足す。運営の画面に「新しい登録を止める」を置き、止めている間は、登録していないアドレスにコードを送らず、ログインの画面にはだれに対しても同じ表示を出す。F28-AC7 から F28-AC9 の、招待されているかどうかを応答から知られない条件は、招待制のあいだの動きである。中身は [招待なしで登録できるようにする](f42-open-signup.md) にある(D-127、D-129)。
- 登録者のメールアドレスは、D1 に、暗号文と検索用の値の 2 つにして持つ。暗号化と復号は、データベースの層(`src/db/`)の境で行い、Better Auth と、その外のコードには、今までどおりのメールアドレスを見せる。メールアドレスの正規化(前後の空白を取って小文字にするだけ)は変えない。中身は [メールアドレスを暗号化して持つ](f41-email-encryption.md) にある(D-80、D-82)。
- 退会の確認のページに、「退会の前に、データを書き出せます。」と、設定の「データを書き出す」へのリンクを置く。本人の書き出しには、本人のメールアドレスが平文で入る([データを書き出す](f35-data-export.md))(D-34、D-40)。

## 未決事項

- Gravatar にメールアドレスのハッシュを送ることを、プライバシーポリシーにどう書くか(本文の更新は第二スコープの範囲外。人の確認に挙げる)。
- 規約の版を残すか。いまは、同意した日時だけを残している。規約とプライバシーポリシーの本文が固まったら、版(または本文の hash)を残すかを決める。
- 利用を止められている人の退会の確認でも、「データを書き出す」へのリンクを出すか(停止中の人は、書き出せない)。03-DECISIONS.md の D-30 は、停止中の人の書き出しの画面を作らず、お問い合わせを受けて運営が対応する、とだけ決めている。出さずに、お問い合わせへ案内する形が考えられる。F28-AC114 は、止められていない人だけを対象にしている。作業 E の実装の前に、依頼者に確かめる。
