# F38 メンテナンスを知らせる

状態は、メンテナンス中のページと読めるページ(F38-AC9〜AC18、AC22)、メンテナンスの印(F38-AC23 のサービスの側)を実装済みで、予告の帯、運営の入口、見張りの Worker の扱いは未実装の設計案です(第四スコープ。統合ブランチ `scope4` に積み、本番にはまだ反映しない)。設計は [メンテナンスの実装設計](../dev/maintenance.md)。いまのメンテナンスの動きは [サービスの基本の備え](../dev/service-basics.md#エラーページとメンテナンス) にある。実装する段階は [ストーリーマップ](../story-mapping.canvas) で確認できます。

## 利用場面

運営が、D1 を復元する、大きな更新を入れるなどのために、サービスを止める。いまは、止めたあとに「メンテナンス中です」と出るだけで、いつまで止まるのか、なぜ止まっているのかが分からない。利用者は、止まる前に知ることもできない。登壇の直前に止まると、発表の準備に響く。

運営も、止めている間に、管理 origin の画面を開いて確かめたい。いまは、止めると運営も画面を開けない。

## 得られる結果

サービスを止める予定は、前もって、全ページの上の帯で知れる。止まっているあいだは、いつ終わる見込みかと、理由が読める。規約とヘルプは、止まっているあいだも読める。運営は、止まっているあいだも、運営の入口を通って、管理 origin の画面を確かめられる。

## 体験の流れ

1. 運営が、運営の画面の「メンテナンスの予定」に、開始の見込み、終了の見込み、理由の区分を入れて、「予告を出す」を押す。
2. 終了の見込みまで、全ページのヘッダーの上に、予告の帯が出る。「(日時)から(日時)まで、メンテナンスのためサービスを止めます。」と、ヘルプの記事へのリンクが並ぶ。
3. 運営が、決めた時刻に、secret `MAINTENANCE` を切り替えてメンテナンスを始める。切り替えは、今までどおり `wrangler` か Cloudflare の画面で行う。
4. 利用者がどのページを開いても、「メンテナンス中です」のページ(`503`)が出る。終わる見込み、理由、読めるページへのリンクが並ぶ。利用規約、プライバシーポリシー、「外部への送信」、お問い合わせ、ヘルプは、そのまま読める。
5. 運営は、運営の入口を通って、管理 origin の画面を開き、確かめる。
6. 運営が secret を消してメンテナンスを終える。予告の帯は、終了の見込みを過ぎれば出なくなる。

## 作る範囲

- secret `MAINTENANCE` の値に、終わる見込みの時刻と理由の区分を入れられるようにすること(値 `on` は今までどおり効く)。
- メンテナンス中のページ(終わる見込み、理由、読めるページへのリンク)と、`Retry-After` を見込みに合わせること。
- メンテナンス中も読めるページの一覧の拡張(「外部への送信」、ヘルプのすべてのページ)。
- 予告の帯と、運営の画面の「メンテナンスの予定」の枠(入力、「予告を出す」「予告を消す」)。
- 運営がメンテナンス中も管理 origin の画面を開ける入口。
- 見張りの Worker のメンテナンスの扱い(通知の中身は [運営が異常に気づく](f39-operator-alerts.md))。
- 始め方、確かめ方、終え方の手順(`docs/dev/deploy.md`)。ヘルプの「メンテナンス中です」の記事の材料。

## 作らないこと

- 一部の機能だけを止める切り替え(読むだけの状態など)。
- ステータスページ、メールでの一斉の知らせ。
- secret を運営の画面から切り替えること。切り替えは、今までどおり `wrangler` か Cloudflare の画面で行う。
- 配信 origin を運営だけに開くこと。
- 予定を複数持つこと。予定は 1 つだけ持つ。
- 予告の帯を閉じるボタン。

## 受け入れ条件

- **F38-AC1** 運営が予定(開始の見込み、終了の見込み、理由の区分)を入れると、すべてのページのヘッダーの上に、予告の帯が出る。
- **F38-AC2** 予告の帯に、「(日時)から(日時)まで、メンテナンスのためサービスを止めます。」と、ヘルプの「メンテナンス中です、と出たとき」の記事へのリンクが出る。日時は、表示言語に合わせ、日本時間で出る。
- **F38-AC3** 予告の帯に、閉じるボタンがない。
- **F38-AC4** 予告の帯は、終了の見込みを過ぎると出ない。
- **F38-AC5** 運営が予定を消すと、予告の帯は出ない。
- **F38-AC6** 予定は 1 つだけ持つ。新しい予定を入れると、前の予定は置き換わる。
- **F38-AC7** 開始まで 3 日を切っている予定を入れるとき、運営の画面に注意が出るが、予定は入れられる。
- **F38-AC8** 運営の画面に「メンテナンスの予定」の枠があり、開始の見込み、終了の見込み、理由の区分の入力、「予告を出す」「予告を消す」、いま出している予告、切り替えの手順へのリンクが出る。
- **F38-AC9** メンテナンス中のページに、「メンテナンス中です」と、終わる見込みの時刻(日本時間と UTC)、理由が出る。
- **F38-AC10** 終わる見込みが入っていないとき、メンテナンス中のページは時刻を出さない。
- **F38-AC11** 理由は、決まった区分(データベースの保守、サービスの更新、その他)の文で出る。
- **F38-AC12** メンテナンス中のページに、ヘルプ、利用規約、プライバシーポリシー、お問い合わせへのリンクが出る。
- **F38-AC13** メンテナンス中の応答は `503` で、`Retry-After` が、終わる見込みまでの秒数になる。
- **F38-AC14** 終わる見込みが無いとき、または見込みを過ぎているとき、`Retry-After` は 300 になる。
- **F38-AC15** secret の値が `on` のとき、メンテナンスは変更の前と同じに動く。
- **F38-AC16** secret の値が、読めない形のとき、`on` と同じに動く。
- **F38-AC17** メンテナンス中も、`/terms`、`/privacy`、`/privacy/external`、`/contact`、ヘルプのすべてのページ、`/robots.txt` が読める。
- **F38-AC18** メンテナンス中のページと、メンテナンス中も読めるページは、D1 が使えないときも開く。
- **F38-AC19** 運営は、メンテナンス中も、運営の入口を通って、管理 origin の画面を開ける。運営でない人は、同じ URL で `503` になる。
- **F38-AC20** 運営の入口は、メンテナンス中でないときは、何もしない。
- **F38-AC21** メンテナンス中でも、配信 origin は、運営の入口を通っても `503` のままである。
- **F38-AC22** メンテナンス中は、cron の処理が動かない。
- **F38-AC23** メンテナンス中の応答に、メンテナンス中であることを示すヘッダーが付き、見張りの Worker が、メンテナンス中の応答と障害の応答を見分けられる。
- **F38-AC24** 見張りの Worker は、メンテナンス中に「ページが開けない」の通知を出さない。
- **F38-AC25** 見張りの Worker は、メンテナンスが始まったことと終わったことを、1 回ずつ知らせる。
- **F38-AC26** 見張りの Worker は、終わる見込みを 30 分過ぎてもメンテナンスが続いているとき、すぐの通知を送る。
- **F38-AC27** 予告の帯は `role="status"` を持ち、日時は `<time datetime="…">` で出る。帯の中のリンクの押せる範囲は高さ 44px 以上である。
- **F38-AC28** 予告の帯とメンテナンス中のページの文言が、日本語と英語の両方で出る。

## 決めたこと

第四スコープを作るにあたり、次のように決めた(2026-11-26、第四スコープの指示書)。

- 切り替えは、今までどおり secret `MAINTENANCE` で行う。値 `on` は今までどおり効く。加えて、終わる見込みの時刻と理由の区分を、値に入れられるようにする。メンテナンス中のページは、D1 を読まずに、この値だけから作る。D1 を復元している間にも出すページだからである(D-115)。
- メンテナンス中のページに、終わる見込みの時刻(日本時間と UTC)と理由を出す。`Retry-After` も、その時刻までの秒数に合わせる(見込みが無いときは今の 300)。理由は、決まった区分(データベースの保守、サービスの更新、その他)から選ぶ(D-116)。
- 予告は、運営の画面で、開始の見込み、終了の見込み、理由の区分を入れる。入れると、終了の見込みまで、全ページの上に帯が出る。開始まで 3 日を切っている予定を入れるときは、運営の画面に注意を出すが、入れられる(D-117)。
- 運営は、メンテナンス中も管理 origin の画面を開いて確かめられる。運営であることは、Cloudflare Access を通ったことで確かめる。配信 origin は対象にしない。この仕組みは、セキュリティの観点のレビューを 1 回受ける(D-118)。
- メンテナンス中も、`/terms`、`/privacy`、`/privacy/external`、`/contact`、ヘルプのすべてのページ、`/robots.txt` は読める(D-119)。いまは、`/robots.txt`、`/terms`、`/privacy`、`/contact`、`/help`、`/help/bot` が読める([サービスの基本の備え](../dev/service-basics.md#エラーページとメンテナンス))。ここに「外部への送信」と、ヘルプのすべてのページを足す。cron の掃除が止まることは、いまのままである。
- 見張りの Worker は、メンテナンス中は「ページが開けるか」の通知を止める。メンテナンスが始まったことと終わったことを、Discord に 1 回ずつ知らせる。終わる見込みを 30 分過ぎても続いていれば、すぐの通知を送る(D-120)。
- 一度開いたスライドは、メンテナンス中も保存した版で読める([通信が切れても読める](f37-offline-reading.md))(D-121)。
- `docs/dev/deploy.md` に、始め方、確かめ方、終え方を書く。`release` の反映の途中は切り替えないことを書く。ヘルプに「メンテナンス中です」の記事を置く([ヘルプで答えを見つける](f36-help-answers.md))(D-122)。
- secret の値は、`on;until=2026-12-01T03:00:00Z;reason=database` の形にする。`until` は UTC の `YYYY-MM-DDTHH:MM:SSZ` だけを読み、`reason` は `database`、`update`、`other` のどれか。読めない値は `on` と同じに止める。未設定、空、`off` だけが止めない。終わる見込みが過ぎているときは、見込みが無いのと同じに扱う。`Retry-After` は 1 日までに切る(作業 N の設計。[メンテナンスの実装設計](../dev/maintenance.md#値の形))。
- メンテナンス中の `503` には、`Retry-After`、`X-Slide-Intended: maintenance`、`X-Slide-Maintenance: on` または `on;until=<UTC>` を付ける。名前は見張りの Worker と一度開いたスライドの Service Worker が見分けに使う(作業 N の設計)。
- 画面は、予告の帯をヘッダーの上に幅いっぱいで 1 本だけ出し、`role="status"` を付ける。メンテナンス中のページの並びは、題名、終わる見込み、理由、読めるページへのリンクの順にする(02-PAGES.md の 13、14)。
- メンテナンス中の `503` の扱いは、[通信が切れても読める](f37-offline-reading.md) と合わせる。先に終わった方の形に、後の方が合わせる。

## 未決事項

次は、作業 N の設計で決める。決まっても、上の受け入れ条件の意味は変わらない。

- 運営の入口で、運営 origin から管理 origin へ、運営であることをどう渡すか。Cookie や URL の値で渡すなら、推測できない値にし、短い時間で切れ、メンテナンス中だけ効くようにする。
- 予告の帯を出すために、すべての要求で D1 を読まない形(読む回数の見積もり)。
