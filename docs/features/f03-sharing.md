# F03 URL を渡して読んでもらう

状態は実装済みです(共有 URL、viewer、ページごとの共有、共有メニュー、ヘルプ。実際のブログサービスでの埋め込みは、人の確認が残る)。viewer の固定のレイアウト(F03-AC117、F03-AC129 から F03-AC139)は実装済みで、2026-11-26 に依頼者が本番の画面で確かめた。2026-11-25 に、配るときに差し込む script を作者の meta の CSP より前に置き、CSP を書き換えない形に変えた(F03-AC151〜F03-AC153。本番の Cloudflare を通した配信と、実機の iOS Safari での人の確認が残る)。第三スコープで、ログイン中のトップの画面のずれを測る対象に「フォローしているコミュニティの新着」を足した(F03-AC80。2026-11-25 の依頼者の回答。統合ブランチ `scope3` に入り、本番にはまだ反映していない)。2026-11-26 に、会場の 1 つの IP の読者 10,000 人が開けるように、閲覧の上限を上げる条件を足した(F03-AC154、F03-AC155)。同じ日に、スライドの編集の並びを「スライド」の枠に合わせて書き直した(F03-AC156、F03-AC157。実装中)。同じ日に、トップの一覧を 4 つのタブにまとめ、「もっと見る」で続きを足すと決めた(F03-AC158〜F03-AC171、F03-AC176、F03-AC178、F03-AC179)。2026-11-27 に、ページの持ち方が slide の決まりと違うツール(suraido.js、reveal.js、Slidev)のスライドを、サービスが読み替えると決めた(F03-AC184〜F03-AC201。未実装)。実装する段階は [ストーリーマップ](../story-mapping.canvas) で確認できます。

## 利用場面

勉強会の終了時、登壇者が参加者へ資料の URL を渡す。参加者はログインせずスマートフォンで開き、後日 PC で同じ資料を読み返す。

## 得られる結果

作成ツールをインストールしていない相手にも、ブラウザだけで資料を届けられる。

## 体験の流れ

1. 公開した資料の共有 URL をコピーする。
2. 相手が URL を開き、資料を閲覧・操作する。
3. 読んだ人が、viewer の「共有」から、スライド全体や、いま見ているページを、URL のコピー、SNS への投稿、[ブログへの埋め込み](f25-embed.md)で広める。
4. 使い方を知りたい人は、ヘルプで、置き方から埋め込みまでを 1 か所で読む。

## 作る範囲

- /@handle/slug 形式の資料 URL と、ページ番号つきの URL(`/@handle/slug/6`)。ページごとの画像は [説明したいページを画像付きで共有する](f05-page-ogp.md) で扱う。
- ページ構成。トップをアップロードの入口にし、説明のための LP は置かない。すべての画面に、共通のヘッダーとフッターを付ける。
- viewer の構成。幅 761px 以上は「ワイド」で固定する。スライドを画面の横幅いっぱい(最大 1600px、それより広い画面では中央)に広げ、その下の左の列に題名と操作のボタン(「全画面」「共有」「⋯」。作者本人には、先頭に「編集する」)と記事、右の列に作者と「フォロー」、説明、関連リンク([関連リンクを紐付ける](f27-related-links.md))、引用([引用でつながる](f24-citations.md))を置く。右の列は記事を読み進めても見えていて、説明・関連リンク・引用のどれかがあるときだけ作る(作者だけなら右の列を空けたまま、題名と操作、作者、記事を同じ左の列に並べる)。記事([発表を書き起こした記事を添える](f26-article.md))には見出しを付けず、本文がスライドの直下から読める。幅 760px 以下は縦並びで、スライド、題名と操作、作者、説明、関連リンク、記事、引用の順に 1 列に並ぶ。中身のない節は、出さない。公開する前のスライドは、[作者だけが見られる](f02-publication.md)。
- ログイン中のヘッダー。サービス名、お知らせのベル、アカウントのメニュー(「プロフィール」「スライドの管理」「コミュニティの管理」「設定」「ログアウト」)。
- スライドの編集(`/my/slides/:deck`)。公開と新しい版(「スライド」の枠)、URL の名前(公開する前だけ)、記事、関連リンク、削除だけを置く画面。中身は [作者のみ限定公開で発表し、一般公開する](f02-publication.md) が受け持つ。
- 画面の移り方。ヘッダーとフッターを残して、本文だけを差し替える。
- 共有メニュー。「URL をコピー」「いま見ているページの URL をコピー」「X に投稿」「Bluesky に投稿」「埋め込みコードをコピー」。
- ヘルプ。置き方、ページごとの共有、引用、ブログへの埋め込み、AI エージェントから置く、フォロー、ログイン、記事、関連リンク、プロフィール、安全について、規約、プライバシー(ログイン、記事、関連リンク、プロフィールは第二スコープで足す)。
- 資料の独自 JS を隔離して動かし、相対パス・ルート相対パスのファイルを読み込む。外部への通信の制限は [知らない人のスライドも、安心して開ける](f17-safe-viewing.md) で扱う。
- ツールごとの読み替え。ページの持ち方が slide の決まり(1 始まりの `#3`)と違うツールのスライドを、サービスが読み替える。「読み替えの対象のスライド」は、suraido.js で作ったスライド(0 始まりの `#2`)、reveal.js で作ったスライド(0 始まりの `#/2`。縦のスライドを持つスライドでは、読む順の通し番号をページ番号にする)、Slidev で作った、既定の設定のスライド(path の `/3`)である。作者は、ツールの設定を変えなくてよい。
- ページ認識のアダプターがない HTML も、元の資料として表示する。

## 作らないこと

- コメント欄、独自ドメイン。フォローは、[気になる人を、フォローする](f21-follow.md) で作ることにした(2026-11-18)。
- どんな HTML でもページを自動判定すること。読み替えるのは、名前を挙げたツール(suraido.js、reveal.js、Slidev)の出力だけで、そのツールの出力と分かる手がかりがあるときに限る。手がかりのない HTML の中身(見出しや `<section>` の数など)から、ページを推測しない。名前を挙げていないツールは、実物の出力で動きを確かめ、条件を足してから対象にする。
- ページの持ち方が合わないツールについて、作者にツールの設定(reveal.js の `hash`・`hashOneBasedIndex`、Slidev の `routerMode`)を変えてもらうこと。使えない組み合わせを、制限としてヘルプに書いて済ませること。作者は、ツールがビルドした出力をそのまま置くためである(2026-11-27。理由は「決めたこと」)。
- トップページでの価値の説明(さわる、わかる、あつまる、クリエイターへ)と、説明用の模型。置く操作そのものが、何をするサービスかを伝える。
- ログインの説明のページ(`/start`)。ログインのボタンは、メールのコードでログインする `/login` へ直接進む([メールのコードでログインする](f28-email-login.md))。
- viewer の SNS の投稿のタイムライン、イベントとコミュニティの表示。
- viewer のレイアウトを、利用者が選べるようにすること。選択式をやめ、PC は固定のワイド、幅 760px 以下は縦並びにした(2026-11-23。理由は「決めたこと」)。
- 色面と切り紙の図形を使った見た目の作り込み。第一スコープの画面は、白地、墨の文字、ピルのボタン、トークンだけで組む。

- **F03-AC63** 管理画面の CSP は、router のために広げない。足すものはなく、どのページも、これまでの CSP のままである。(「`connect-src` に `'self'` を足しただけ」を直した。`connect-src 'self'` は `/api/session` のために元からある。)
- **F03-AC71** viewer の作者のスライドの枠が、自分で別の deck の origin へ移ろうとしたとき、viewer の CSP(`frame-src`)が、request を出す前に断る。

第一スコープを作るにあたり、次のように決めた(2026-11-19)。

- 説明のための LP は置かない。トップページをアップロードの入口にする。トップから外した説明のうち、必要なものはヘルプへ移す。
- `/start` は `/` へ、`/my/slides/new` は `/my/slides` へ、303 で送る。
- トップは、静的なファイルを生成して、表示の後にログインの状態で中身を切り替える方式を保つ(`GET /api/session`)。
- viewer のヘッダーは、ほかの画面と同じ共通のものにする。
- 日付は `src/share/dates.ts` の書式にそろえる。日本語は「2026年11月19日」。
- プロフィール画像がないときは、頭文字を出す。
- トップの最近のスライドは、横に流さず、折り返す格子にする。
- 共有メニューの項目は、上の 5 つ。ブラウザが OS の共有(`navigator.share`)に対応しているときは、「ほかのアプリで共有」を 6 つ目に足す。

- 画面の文言は、日本語と英語の両方を用意する。

第一スコープの見直しで、次のように決めた(2026-11-20)。

- ログイン中のヘッダーは、サービス名、お知らせのベル、アカウントのメニューの 3 つにする。「スライドの管理」は、アカウントのメニューの中にだけ置く。ログイン中のトップに「自分のスライド」は置かない(2026-11-21。理由は F21-AC15)。置いた直後の viewer の「編集する」(F03-AC29)も、入口である。
- 作者が自分のスライドの viewer を開くと、操作のボタンの先頭に「編集する」を出す。押すと、スライドの編集へ進む。読者には出さない。作者本人かどうかは、サーバーが判定して出し分ける(viewer は、サービス自身の markup と `/share.js` だけを動かす)。
- `/my/slides/:deck` の呼び名を「スライドの編集」にする。画面の題、戻るリンク、文言、ヘルプ、文書をそろえる。URL は変えない。
- スライドの管理(`/my/slides`)の各行の「管理する」は「編集する」にする。行の表紙と題名は、viewer へのリンクにする。
\1
- 英語の題は、スライドの編集が `Edit slide`(1 本のスライドを編集するため、複数にしない)、スライドの管理が `Your slides` にする。スライドの編集の戻るリンク、アカウントのメニュー(「スライドの管理」の行は残る)、ヘルプの本文、エラーの文も、同じ呼び名にそろえる。

viewer のレイアウトは、選択式をやめて固定にした(2026-11-23)。

- 幅 761px 以上は「ワイド」、幅 760px 以下は「縦並び」で固定する。レイアウトを選ぶボタンとメニュー、ブラウザへの保存、記事の有無による既定は作らない(一度作ったが取り除いた)。理由: 説明も関連リンクも引用もないスライドでは、横並びが空白だらけになる。選ぶ・保存する・既定を決める分岐が増えるわりに、読者が選びたい場面が見つからなかった。
- 採らなかった案: 利用者が「縦並び」「横並び」「ワイド」から選び、ブラウザに保存する。記事があるスライドだけ既定を「横並び」にする。どちらも、上の理由で取りやめた。
- ワイドの幅の上限は 1600px とし、それより広い画面では、スライドも含めて全体を中央に置く。理由: 広い画面でスライドと文章が離れすぎないようにする。スライドは、その 1600px の範囲いっぱいで、角丸はつけない。理由: 画面の端まで届くときと同じ見た目にそろえ、1600px より広い画面で角だけが変わらないようにする。
- 右の列は、説明・関連リンク・引用のどれかがあるときだけ作る。作者の行だけなら、右の列を空けたまま、題名と操作、作者、記事を同じ左の列に並べる。理由: 記事などの有無で、スライドごとに題名の位置がずれないようにする(2026-11-26 に、中央の 1 列から改めた)。判断は、サーバーが描くときに決める(`hasSideColumn`、`src/share/viewer-side.ts`)。ミュートを解除して一覧が入れ替わっても、列の有無は変えない。
- 右の列では、引用のカードを 1 列にする。理由: 列は 280px から 3 分の 1 ほどの細さで、2 列ではカードが小さくなりすぎる。
- 作者・説明・関連リンク・引用は、`.viewer-side` の 1 つの要素にまとめる。理由: 記事を読み進めても右の列を残す(`position: sticky`)には、1 つの要素が要る。そのため、markup では引用が記事より前に来る。縦並びでは、CSS で記事を引用の前に見せる。読み上げと Tab の順だけが、縦並びの見た目と違い、引用が記事の前になる。
- 作者を題名と操作の行の外(`.viewer-side`)に置く。幅 599px 以下では、これまで「題名、作者、操作」の順だったが、「題名、操作、作者」になる。
- 「記事」の見出し(`h2`)をなくした。理由: 記事をスライドの直下から読めるようにするため。節の意味は `aria-label` で残す。記事の本文の見出しは、これまでどおり `h3` から始まる。
- レイアウトは CSS(`.viewer-layout` の `data-side` と `grid-template-areas`)だけで決め、script を使わない。理由: 要素を作り直さず、スライドの枠(iframe)や CSP に触れない。ちらつきも起きない。

ページ番号つきの URL は、作者が何もしなくても働くようにした(2026-11-24)。

- サービスが、版のトップの `index.html` を配るときに、ページを伝える script を inline で差し込む。理由: Claude などが生成した HTML は、自分で厳しい CSP を `<meta http-equiv="Content-Security-Policy">` に書くことが多く(例: `default-src 'none'; script-src 'unsafe-inline'; …`)、外のファイルの `/_preview/pages.js` が止められて、ページ番号が伝わらなかった。差し込みは配るときに行い、置いたファイルは変えない。置き直さなくても、すでにある版にも効く。
- 差し込む位置は、`<head>` の先頭近く(meta の CSP の後、作者の最初の script の前)。作者の HTML のほかの部分は変えない。(2026-11-25 に変えた。下を参照)
- meta の CSP の扱い: CSP がなければ、そのまま差し込む。script を決める指定が `'unsafe-inline'` を含み、ハッシュ・nonce・`'strict-dynamic'` を含まなければ、CSP を変えない(ハッシュを足すと `'unsafe-inline'` が無視され、作者の inline の script が止まるため)。それ以外は、差し込む script のハッシュを 1 つだけ足す(F03-AC144)。作者の CSP を必要以上に弱めないため、ほかの許可は広げない。(2026-11-25 にやめた。下を参照)
- 差し込むのはトップの `index.html` だけにする。viewer が開くのはトップで、ページ番号はトップの fragment である。ほかの HTML のページが伝えた番号は、トップのページ番号と取り違えられる。
- 作者が `/_preview/pages.js` を書いた HTML にも差し込み、2 つのうち先に動いたほうだけが働く(F03-AC146)。外の script が CSP で止められるかを配信の側で判定する案は採らなかった。CSP の照合(`'self'`、host、`'strict-dynamic'` など)を配信の側で正しく再現するのは難しく、外れると、ページが伝わらないか、二重に伝わる。
- 差し込めない HTML は、元のまま配る(安全側。F03-AC147。2026-11-25 に F03-AC153 で書き直した)。

配るときに差し込む script の置き場所を変える(2026-11-25、依頼者。issue #366 の D11)。

- 差し込む script を、作者の meta の CSP より前に置き、作者の meta の CSP を書き換えない(F03-AC151〜F03-AC153)。ハッシュを足すことも、CSP を読んで調整することも、やめる。meta の CSP は、その要素より後ろの内容にだけ効くので、前に置いた script は止められない。理由: 作者の CSP を書き換えずに済み、CSP の読み取りと調整の処理(と、その不具合の余地)を抱えなくてよい。
- 利用者から見た動きは変えない。厳しい CSP のスライドでもページ番号つきのアドレスに変わり、CSP の違反が出ないこと(F03-AC143、F03-AC145)、ページが二重に伝わらないこと(F03-AC146)、`ETag` と `304`(F03-AC148)は、そのまま満たす。
- 配信の HTTP の header の CSP(`sandbox …; worker-src 'none'; frame-ancestors …`)は、meta の CSP より前に置いた script にも効く。script を制限しないので、これまでどおり変えない(一般公開のファイルの `worker-src` だけは、F37 で、サービスの Service Worker の URL 1 つになる)。
- 上の 2026-11-24 の「差し込む位置」と「meta の CSP の扱い」は、これに置き換わる。

閲覧の上限を上げる(2026-11-26、依頼者。#454)。

- 依頼者の言葉: 「一旦、上限を上げてください。10000人超のイベントでも平気にしてください。」「今後、恒久対応をする issueを切ってください。」
- きっかけ: 記事の画像のページ数の上限をなくすと(#454)、Chromium では記事のすべてのページの画像を開いた時に読み込むため(BarefootJS の router が region を複製し、`loading="lazy"` が効かない)、100 ページの記事を同じ会場の IP の読者 6 人が 1 分以内に開くと、IP ごとに 1 分 600 回の閲覧の上限を超えていた。依頼者は、この害を受け入れて上限をなくし、そのかわりに閲覧の上限を上げると決めた。
- 共有 URL・トップページ・ページの画像の上限(`VIEWER_RATE_LIMITER`)と、版の origin の上限(`CONTENT_RATE_LIMITER`)を、IP ごとに 1 分 5,000,000 回と 6,000,000 回にする(F03-AC154、F03-AC155)。数え方は [サービスの基本の備え](../dev/service-basics.md#リクエスト頻度の上限) にある。ページの画像を閲覧の上限の外に出す案は採らなかった。この値では、閲覧の上限は 1 つの IP からの読み出しをほとんど止めず、外に出しても得るものが小さいうえ、恒久の対応で上限を別にするときに、数え方を 2 度変えることになるためである。
- これは一旦の対応である。Chromium でもページの画像を遅れて読み込むようにし、そのあとで、ページの画像の上限を別にするか、閲覧の上限を見直すことを、別の issue で扱う。

トップの一覧を、タブにまとめると決めた(2026-11-26。相談のワイヤーフレームは https://claude.ai/artifact/1NhahnmrwKkVgCeXRprN3i)。公開されたスライドがまだ少なく、節を縦に積むと、どの節も中身が薄いまま画面が長くなるためである。

- タブは「最近のスライド」「最近のコミュニティ」「フォロー」「フォローコミュニティ」の 4 つ。これまでの節(「最近のスライド」「新着のコミュニティ」「フォロー中の人の新着」「フォローしているコミュニティの新着」)の中身を、それぞれのタブへ移す(F03-AC158)。
- 最初に開くタブは、ログインの有無によらず「最近のスライド」(F03-AC159)。
- タブの状態は URL に持たない(F03-AC159)。トップは静的なファイルのままにする。
- 最初に出すのは 2 段に収まる件数にとどめ、「もっと見る」を押すごとに最大 100 件足す(F03-AC161、F03-AC162)。最初から多く出して負荷を上げても、見られなければ意味がない。足すときは、だらっと眺めるのにちょうどよい量にする。
- 「すべて見る」(別のページへ進むリンク)はトップに置かず、「もっと見る」(その場で足す)にする。
- ログインしていない人にも、フォローの 2 つのタブを出す。スライドは出さず、ログインしてフォローすることを薦める(F03-AC167、F03-AC168)。フォローで何が得られるかを、トップで知ってもらうためである。
- 並べるものが 1 件もないタブは、場所を残さず、文だけにする(F03-AC176)。最初は、届く前後でフッターが動かないよう 0 件でも場所を保つことにしていたが、幅 375px では 1 列に 8 件ぶんの場所が空白として残り、見づらかった。0 件になるのは、まだ公開がないときと、フォローしていないとき・ログインしていないときに限られ、画面が 1 度縮むことより、空白が残ることのほうが困る(2026-11-26、依頼者の指摘)。
- 幅 600px 未満では、届いた件数が少ないときも、届かなかった分の場所を残さない(F03-AC179)。スマホでは 1 列に並ぶので、3 件しかないと、残り 5 件ぶんの空白がスライドとフッターの間に残った。画面が 1 度縮むことより、空白が残ることのほうが困る(2026-11-26、依頼者の指摘)。幅 600px 以上では、空白は多くても 1 段ぶんなので、場所を保つ。

- 2026-11-26 依頼者の指示で、スライドの管理とスライドの編集の URL を `/slides` から `/my/slides` の下へ移した。`/slides` のような一等地の URL を空けるためである。転送は置かない(F03-AC173)。`slides` は、経路が空いても、ハンドルの予約語に残す。API(`/api/slides/...`)と共有 URL(`/@handle/slug`)は変えない。

peitho の綴りに合わせる(2026-11-26、依頼者の報告)。

- 依頼者の報告: peitho で作ったスライドで、ページを送っても URL にページ番号が入らなかった。原因は CSP ではなく、peitho の viewer が、ページを fragment ではなく query(`history.replaceState` で `?slide=5`)に書くようになっていたことだった。差し込む script は fragment だけを読んでいた。
- 差し込む script は、query の `slide` があればその番号を、なければこれまでどおり fragment の番号を読む(F03-AC174)。peitho は開いたときの fragment(viewer が渡す `#3`)を残したまま query を書き換えるので、query を先に読む。query の値がページ番号の形でないときは、何も伝えない。
- viewer がスライドに渡す綴りは `#3` のまま変えない。peitho も `#3` を読んで、そのページから開く。

ページの持ち方が違うツールは、サービスが読み替える(2026-11-27、依頼者。#694)。

- きっかけ: 実在のツールの出力を置いて、いまの動きを記録した(#694、#703、#706、#707。Chromium)。suraido.js(0.5.0)は fragment に 0 始まりの番号を持つので、`/@handle/slug/3` が 4 ページ目を開き、めくったあとのアドレスバーも 1 つ小さい番号になった。reveal.js(6.0.2、既定の設定)も `#3` を 0 始まりで読んで 4 ページ目を開き、めくっても自分の URL を書かないので、アドレスバーが変わらなかった。Slidev(53.2.0)はページを path(`/3`)で持ち、`#3` を読まないので、どの URL でも 1 ページ目から開き、めくったページにアドレスバーが追従しなかった。peitho と Marp は、期待どおりに動いた(#699、#700)。
- 決めたこと: この違いは、サービスが吸収する。ツールごとの読み取りを、サービスが差し込む「ページを伝える script」に足す(F03-AC184〜F03-AC201)。作者のファイルは変えず、作者にツールの設定を求めない。理由: 作者は、ツールがビルドした出力をそのまま置く。ページ番号つきの URL が、どのツールで作ったかによって 1 つずれたり働かなかったりすると、読者は別のページを見せられ、作者は原因に気づけない。
- 採らなかった案: 使えない組み合わせを制限としてヘルプに書く。作者に設定(reveal.js の `hash`・`hashOneBasedIndex`、Slidev の `routerMode`)を変えてもらう。
- 「どんな HTML でもページを自動判定しない」(作らないこと)は変えない。読み替えるのは、名前を挙げたツールの出力だけで、そのツールの出力と分かる手がかりがあるときに限る(F03-AC195、F03-AC196)。手がかりのないスライドは、これまでの決まり(`#3`、`?slide=3`)で読む。手がかりに使うのは、ツールが自分の出力に書く印と、ツールが公開している API に限り、題名や本文の語は使わない。ツールごとに何を使うかは、設計で決めて、[共有 URL と配信の実装設計](../dev/f03-sharing.md#ツールごとの読み替え)に書く(suraido.js は、下のとおり、動き出した後の印で判定する)。
- サービスがページ番号を渡してスライドを開くところは 4 つある(viewer の枠、記事のページの画像を押したときの移動、ページの画像の撮影、埋め込みの枠)。どれも同じ番号が同じページを指すようにする(F03-AC193、F03-AC194、F03-AC198)。URL は 3 ページ目なのに、画像が 4 ページ目、ということを起こさないためである。読み替えが入る前に撮ったページの画像は、ずれたページを写しているので、撮り直す(F03-AC194)。
- reveal.js の縦のスライド(`#/h/v`)は、読む順の通し番号で、1 つのページ番号に写す(F03-AC199〜F03-AC201。2026-11-27、依頼者)。どのスライドにも、重ならない番号が 1 つ付く。採らなかった案: 横の番号だけをページ番号にする。縦に重なるスライドを指す URL が作れず、同じ番号のまま別のスライドが見えるためである。
- suraido.js の出力かどうかは、実行時に判定する(F03-AC184〜F03-AC186。2026-11-27、依頼者)。サービスが差し込む「ページを伝える script」が、スライドが動き出した後に、suraido.js の印(CSS のカスタムプロパティ `--suraido-*`、DOM の `data-suraido-*`)を見て判定し、ページ番号を読み替える。ビルドした `index.html` には、suraido.js の出力と分かる印がないためである。作者には何も頼まず、置いたファイルも変えない。採らなかった案(後に回す): 置いたときにサービスが判定して覚えておく。実行時の判定が遅れて、開いた直後に 1 つずれたページが見えることが問題になったら、検討する。
- 実物で確かめたのは、各ツールの上の版の、既定の設定の出力である。reveal.js の縦のスライドは、実物の出力ではまだ確かめていない(fixture を足して確かめる)。suraido.js の名前を付けたページとステップ、既定でない設定(Slidev の `routerMode: hash`)は、未決事項に残した。
- ツールの版が上がって綴りが変わったことに、テストで気づく仕組み(最新の版でビルドし直して確かめる workflow)は、後で検討する。いまは作らない(#694)。

- 第四スコープで、ヘルプは、1 枚のページの節から、したいことごとの記事に分かれる([ヘルプで答えを見つける](f36-help-answers.md))。この文書の「ヘルプの節」「ヘルプの項目」は、対応する記事のことである。ヘルプの節の位置(`/help#<id>`)を指す書き方は、記事の URL を指す書き方に直す。
