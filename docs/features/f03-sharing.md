# F03 URL を渡して読んでもらう

状態は実装済みです(共有 URL、viewer、ページごとの共有、共有メニュー、ヘルプ。実際のブログサービスでの埋め込みは、人の確認が残る)。viewer の固定のレイアウト(F03-AC117、F03-AC129 から F03-AC139)は実装中で、実際の画面での人の確認が残る。2026-11-25 に、配るときに差し込む script を作者の meta の CSP より前に置き、CSP を書き換えない形に変えた(F03-AC151〜F03-AC153。本番の Cloudflare を通した配信と、実機の iOS Safari での人の確認が残る)。第三スコープで、ログイン中のトップの画面のずれを測る対象に「フォローしているコミュニティの新着」を足した(F03-AC80。2026-11-25 の依頼者の回答。統合ブランチ `scope3` に入り、本番にはまだ反映していない)。2026-11-26 に、会場の 1 つの IP の読者 10,000 人が開けるように、閲覧の上限を上げる条件を足した(F03-AC154、F03-AC155)。実装する段階は [ストーリーマップ](../story-mapping.canvas) で確認できます。

## 利用場面

勉強会の終了時、登壇者が参加者へ資料の URL を渡す。参加者はログインせずスマートフォンで開き、後日 PC で同じ資料を読み返す。

## 得られる結果

作成ツールをインストールしていない相手にも、ブラウザだけで資料を届けられる。

## 体験の流れ

1. 公開した資料の共有 URL をコピーする。
2. 相手が URL を開き、資料を閲覧・操作する。
3. 読んだ人が、viewer の「共有」から、スライド全体や、いま見ているページを、URL のコピー、SNS への投稿、[ブログへの埋め込み](f25-embed.md)で広める。
4. 使い方を知りたい人は、ヘルプで、置き方から埋め込みまでを 1 か所で読む。

## 作る範囲

- /@handle/slug 形式の資料 URL と、ページ番号つきの URL(`/@handle/slug/6`)。ページごとの画像は [説明したいページを画像付きで共有する](f05-page-ogp.md) で扱う。
- ページ構成。トップをアップロードの入口にし、説明のための LP は置かない。すべての画面に、共通のヘッダーとフッターを付ける。
- viewer の構成。幅 761px 以上は「ワイド」で固定する。スライドを画面の横幅いっぱい(最大 1600px、それより広い画面では中央)に広げ、その下の左の列に題名と操作のボタン(「全画面」「共有」「⋯」。作者本人には、先頭に「編集する」)と記事、右の列に作者と「フォロー」、説明、関連リンク([関連リンクを紐付ける](f27-related-links.md))、引用([引用でつながる](f24-citations.md))を置く。右の列は記事を読み進めても見えていて、説明・関連リンク・引用のどれかがあるときだけ作る(作者だけなら作らず、題名と操作、作者、記事を、記事の幅の 1 列で中央に並べる)。記事([発表を書き起こした記事を添える](f26-article.md))には見出しを付けず、本文がスライドの直下から読める。幅 760px 以下は縦並びで、スライド、題名と操作、作者、説明、関連リンク、記事、引用の順に 1 列に並ぶ。中身のない節は、出さない。公開する前のスライドは、[作者だけが見られる](f02-publication.md)。
- ログイン中のヘッダー。サービス名、お知らせのベル、アカウントのメニュー(「プロフィール」「スライドの管理」「設定」「ログアウト」)。
- スライドの編集(`/slides/:deck`)。公開、共有 URL、新しい版、引用されたスライド、削除だけを置く画面。中身は [作者のみ限定公開で発表し、一般公開する](f02-publication.md) が受け持つ。
- 画面の移り方。ヘッダーとフッターを残して、本文だけを差し替える。
- 共有メニュー。「URL をコピー」「いま見ているページの URL をコピー」「X に投稿」「Bluesky に投稿」「埋め込みコードをコピー」。
- ヘルプ。置き方、ページごとの共有、引用、ブログへの埋め込み、AI エージェントから置く、フォロー、ログイン、記事、関連リンク、プロフィール、安全について、規約、プライバシー(ログイン、記事、関連リンク、プロフィールは第二スコープで足す)。
- 資料の独自 JS を隔離して動かし、相対パス・ルート相対パスのファイルを読み込む。外部への通信の制限は [知らない人のスライドも、安心して開ける](f17-safe-viewing.md) で扱う。
- ページ認識のアダプターがない HTML も、元の資料として表示する。

## 作らないこと

- コメント欄、独自ドメイン。フォローは、[気になる人を、フォローする](f21-follow.md) で作ることにした(2026-11-18)。
- どんな HTML でもページを自動判定すること。
- トップページでの価値の説明(さわる、わかる、あつまる、クリエイターへ)と、説明用の模型。置く操作そのものが、何をするサービスかを伝える。
- ログインの説明のページ(`/start`)。ログインのボタンは、メールのコードでログインする `/login` へ直接進む([メールのコードでログインする](f28-email-login.md))。
- viewer の SNS の投稿のタイムライン、イベントとコミュニティの表示。
- viewer のレイアウトを、利用者が選べるようにすること。選択式をやめ、PC は固定のワイド、幅 760px 以下は縦並びにした(2026-11-23。理由は「決めたこと」)。
- 色面と切り紙の図形を使った見た目の作り込み。第一スコープの画面は、白地、墨の文字、ピルのボタン、トークンだけで組む。

- **F03-AC81** ログインしていない人がトップを開くとき、CLS が 0.1 以下である。ログイン中の人のための場所を、先に取らない。
- **F03-AC82** ログイン中の人がほかの画面からトップへ移る(ページ全体を読み込まない)とき、CLS が 0.1 以下である。
- **F03-AC83** 最近のスライドの仮の表示は、届いたときの表示(題名 2 行ぶんと日付の行を含む)と同じ高さで、届いた件数が少なくても、題名が長くても、フッターの位置が変わらない。1 本も公開されていないときも、読み込めなかったときも、場所は変わらず、そのことと(失敗のときは)取り直すボタンを同じ場所に出す。
- **F03-AC63** 管理画面の CSP は、router のために広げない。足すものはなく、どのページも、これまでの CSP のままである。(「`connect-src` に `'self'` を足しただけ」を直した。`connect-src 'self'` は `/api/session` のために元からある。)
- **F03-AC71** viewer の作者のスライドの枠が、自分で別の deck の origin へ移ろうとしたとき、viewer の CSP(`frame-src`)が、request を出す前に断る。
- **F03-AC72** viewer(と埋め込み)へのリンクと、viewer からのリンクは、ページ全体の移動になる。理由: viewer は作者のスライドの枠を持ち、CSP がほかの画面と違う(フォームを許さない、枠は 1 つの deck の origin だけ)ため。CSP を広げずに差し替えると、移った先のフォームや枠が動かず、広げると守りが弱まる。作者だけが開ける版の viewer も同じで、router は取りに行かない。
- **F03-AC73** フォームの要る画面へ、フォームを許さない画面(ヘルプ、規約)から移るとき、ページ全体の移動になる。移った先の画面は、移る前の画面の CSP の下で動くので、フォームが送れないままにしないためである。そのほか、移る先が移る前の画面の CSP の許す範囲を超える(たとえば作者のスライドの表紙の画像を出す画面へ、出さない画面から移る)ときも、ページ全体の移動になる。
- **F03-AC75** 共有メニューのコピーのボタンは、押して「コピーしました」に変わっても、メニューの幅、各行の高さと位置が変わらず、行に枠がつかない。幅 1280px と 375px のどちらでも。理由: いちばん長い行(「いま見ているページの URL をコピー」)を押すと、その行が短くなってメニューが狭まり、位置がずれていた(依頼者の指摘、2026-11-21)。ボタンは、ふだんの文言と「コピーしました」の長いほうの大きさを、先に取る。コピーしたことを伝える読み上げ(F03-AC18)は、そのまま保つ。
- **F03-AC76** フッターは、本文が短い画面(お知らせが空、存在しない画面、設定など)でも、画面の下に置かれる。本文が長い画面では、本文の下に続き、重ならない。幅 1280px と 375px のどちらでも。ヘッダーとフッターは `main` の外にあるので、router が `main` の中身を差し替えても崩れない。viewer の枠の高さは変えない。
- **F03-AC74** 単独で置いたリンク(文の中のリンクを除く)の押せる範囲は、幅 1280px と 375px のどちらでも、高さ 44px 以上である。描いた高さが小さいリンクは、見た目を変えずに当たり判定を広げる(`05-UI-RULES.md` の「押せるもの」)。
- **F03-AC64** viewer の作者の HTML の枠の CSP と sandbox は、変わらない。
- **F03-AC65** スライドの編集の戻るリンクの文言が、「スライドの管理」へ戻ることを示し、「1 本の管理」の呼び名が画面に残っていない。
- **F03-AC66** ヘルプの本文に、「1 本の管理」の呼び名が残らず、スライドの編集と書かれている。
- **F03-AC67** 画面を移った後、その画面の CSS が当たっている(計算後のスタイルが、ページ全体を読み込んだときと同じである)。

- 採らなかった案: 利用者が「縦並び」「横並び」「ワイド」から選び、ブラウザに保存する。記事があるスライドだけ既定を「横並び」にする。どちらも、上の理由で取りやめた。
- ワイドの幅の上限は 1600px とし、それより広い画面では、スライドも含めて全体を中央に置く。理由: 広い画面でスライドと文章が離れすぎないようにする。スライドは、その 1600px の範囲いっぱいで、角丸はつけない。理由: 画面の端まで届くときと同じ見た目にそろえ、1600px より広い画面で角だけが変わらないようにする。
- 右の列は、説明・関連リンク・引用のどれかがあるときだけ作る。作者の行だけなら、列を作らず、題名と操作、作者、記事を記事の読みやすい幅(44em)の 1 列で中央に並べる。理由: 右の列のぶんを空白にしない。判断は、サーバーが描くときに決める(`hasSideColumn`、`src/share/viewer-side.ts`)。ミュートを解除して一覧が入れ替わっても、列の有無は変えない。
- 右の列では、引用のカードを 1 列にする。理由: 列は 280px から 3 分の 1 ほどの細さで、2 列ではカードが小さくなりすぎる。
- 作者・説明・関連リンク・引用は、`.viewer-side` の 1 つの要素にまとめる。理由: 記事を読み進めても右の列を残す(`position: sticky`)には、1 つの要素が要る。そのため、markup では引用が記事より前に来る。縦並びでは、CSS で記事を引用の前に見せる。読み上げと Tab の順だけが、縦並びの見た目と違い、引用が記事の前になる。
- 作者を題名と操作の行の外(`.viewer-side`)に置く。幅 599px 以下では、これまで「題名、作者、操作」の順だったが、「題名、操作、作者」になる。
- 「記事」の見出し(`h2`)をなくした。理由: 記事をスライドの直下から読めるようにするため。節の意味は `aria-label` で残す。記事の本文の見出しは、これまでどおり `h3` から始まる。
- レイアウトは CSS(`.viewer-layout` の `data-side` と `grid-template-areas`)だけで決め、script を使わない。理由: 要素を作り直さず、スライドの枠(iframe)や CSP に触れない。ちらつきも起きない。

ページ番号つきの URL は、作者が何もしなくても働くようにした(2026-11-24)。

- サービスが、版のトップの `index.html` を配るときに、ページを伝える script を inline で差し込む。理由: Claude などが生成した HTML は、自分で厳しい CSP を `<meta http-equiv="Content-Security-Policy">` に書くことが多く(例: `default-src 'none'; script-src 'unsafe-inline'; …`)、外のファイルの `/_preview/pages.js` が止められて、ページ番号が伝わらなかった。差し込みは配るときに行い、置いたファイルは変えない。置き直さなくても、すでにある版にも効く。
- 差し込む位置は、`<head>` の先頭近く(meta の CSP の後、作者の最初の script の前)。作者の HTML のほかの部分は変えない。(2026-11-25 に変えた。下を参照)
- meta の CSP の扱い: CSP がなければ、そのまま差し込む。script を決める指定が `'unsafe-inline'` を含み、ハッシュ・nonce・`'strict-dynamic'` を含まなければ、CSP を変えない(ハッシュを足すと `'unsafe-inline'` が無視され、作者の inline の script が止まるため)。それ以外は、差し込む script のハッシュを 1 つだけ足す(F03-AC144)。作者の CSP を必要以上に弱めないため、ほかの許可は広げない。(2026-11-25 にやめた。下を参照)
- 差し込むのはトップの `index.html` だけにする。viewer が開くのはトップで、ページ番号はトップの fragment である。ほかの HTML のページが伝えた番号は、トップのページ番号と取り違えられる。
- 作者が `/_preview/pages.js` を書いた HTML にも差し込み、2 つのうち先に動いたほうだけが働く(F03-AC146)。外の script が CSP で止められるかを配信の側で判定する案は採らなかった。CSP の照合(`'self'`、host、`'strict-dynamic'` など)を配信の側で正しく再現するのは難しく、外れると、ページが伝わらないか、二重に伝わる。
- 差し込めない HTML は、元のまま配る(安全側。F03-AC147。2026-11-25 に F03-AC153 で書き直した)。

配るときに差し込む script の置き場所を変える(2026-11-25、依頼者。issue #366 の D11)。

- 差し込む script を、作者の meta の CSP より前に置き、作者の meta の CSP を書き換えない(F03-AC151〜F03-AC153)。ハッシュを足すことも、CSP を読んで調整することも、やめる。meta の CSP は、その要素より後ろの内容にだけ効くので、前に置いた script は止められない。理由: 作者の CSP を書き換えずに済み、CSP の読み取りと調整の処理(と、その不具合の余地)を抱えなくてよい。
- 利用者から見た動きは変えない。厳しい CSP のスライドでもページ番号つきのアドレスに変わり、CSP の違反が出ないこと(F03-AC143、F03-AC145)、ページが二重に伝わらないこと(F03-AC146)、`ETag` と `304`(F03-AC148)は、そのまま満たす。
- 配信の HTTP の header の CSP(`sandbox …; worker-src 'none'; frame-ancestors …`)は、meta の CSP より前に置いた script にも効く。script を制限しないので、これまでどおり変えない。
- 上の 2026-11-24 の「差し込む位置」と「meta の CSP の扱い」は、これに置き換わる。

閲覧の上限を上げる(2026-11-26、依頼者。#454)。

- 依頼者の言葉: 「一旦、上限を上げてください。10000人超のイベントでも平気にしてください。」「今後、恒久対応をする issueを切ってください。」
- きっかけ: 記事の画像のページ数の上限をなくすと(#454)、Chromium では記事のすべてのページの画像を開いた時に読み込むため(BarefootJS の router が region を複製し、`loading="lazy"` が効かない)、100 ページの記事を同じ会場の IP の読者 6 人が 1 分以内に開くと、IP ごとに 1 分 600 回の閲覧の上限を超えていた。依頼者は、この害を受け入れて上限をなくし、そのかわりに閲覧の上限を上げると決めた。
- 共有 URL・トップページ・ページの画像の上限(`VIEWER_RATE_LIMITER`)と、版の origin の上限(`CONTENT_RATE_LIMITER`)を、IP ごとに 1 分 5,000,000 回と 6,000,000 回にする(F03-AC154、F03-AC155)。数え方は [サービスの基本の備え](../dev/service-basics.md#リクエスト頻度の上限) にある。ページの画像を閲覧の上限の外に出す案は採らなかった。この値では、閲覧の上限は 1 つの IP からの読み出しをほとんど止めず、外に出しても得るものが小さいうえ、恒久の対応で上限を別にするときに、数え方を 2 度変えることになるためである。
- これは一旦の対応である。Chromium でもページの画像を遅れて読み込むようにし、そのあとで、ページの画像の上限を別にするか、閲覧の上限を見直すことを、別の issue で扱う。
