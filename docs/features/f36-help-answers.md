# F36 ヘルプで答えを見つける

状態は実装済みです(第四スコープの作業 H1、H2。F36-AC37 は、「1 日」が直近 24 時間と決まってから足した)。統合ブランチ `scope4` に積み、本番にはまだ反映しない。実装の設計は [ヘルプの枠の実装設計](../dev/f36-help-frame.md)。実装する段階は [ストーリーマップ](../story-mapping.canvas) で確認できます。

## 利用場面

作者や読者が、「zip でスライドを置くには」「ログインのコードが届かない」のように、したいことや困ったことを決めて、ヘルプを開く。いまのヘルプは、1 枚のページに節が並んでいる。目次から節を探すだけで、言葉で探せない。節が長く、1 つの節に複数の「したいこと」が入っているので、答えの場所が分かりにくい。ヘルプの外から答えを指すリンクも、節の位置(`/help#<id>`)で、ページの途中を指すだけである。

このスコープで、書き出し、メンテナンス、保存した版、登録など、利用者の迷いやすい機能が増える。増えた機能の答えを、迷いやすい画面から 1 回で見つけられるようにしたい。

## 得られる結果

ヘルプが、したいことごとの記事に分かれる。入口で狙いを選ぶか、言葉で探して、答えの記事にたどり着ける。迷いやすい画面(設定の各枠、1 本の管理、コミュニティの編集、AI エージェントの接続、退会の確認、置けなかった理由を出す場所)から、対応する記事へ 1 回で行ける。このスコープで増えた機能の答えが、記事としてある。

## 体験の流れ

1. 利用者が `/help` を開く。検索の欄と、8 つの狙い(はじめる、スライドを置く・直す、記事とリンクを添える、読む・共有する、つながる、AI エージェント、アカウントとデータ、安全と規約)が並ぶ。
2. 言葉で探すときは、検索の欄に語を入れて「探す」を押す。`/help?q=<語>` に、合った記事が、題名に合うものを上にして並ぶ。合う記事がなければ、0 件と、狙いの一覧、お問い合わせへのリンクが出る。
3. 狙いを選ぶときは、狙いの名前を押す。`/help/<狙い>` に、記事の題名と最初の 1 文が並ぶ。
4. 記事(`/help/<狙い>/<記事>`)を開く。最初の 1 文が答えで、手順は番号つきの列、うまくいかないときの理由と対処が続く。末尾に、関係する記事と、解決しないときのお問い合わせへのリンクがある。
5. 設定や 1 本の管理などで迷ったときは、枠の見出しの横か説明の文の末尾にあるリンクから、対応する記事へ行く。スライドを置けなかったときは、理由の表示から、対応する記事へ行く。

## 作る範囲

- 記事の仕組み。1 記事を 1 つのファイルでリポジトリに持つ(日本語と英語の両方)。記事のファイルを足すだけで、狙いの一覧と検索に出る。
- 3 段のページ(`/help`、`/help/<狙い>`、`/help/<狙い>/<記事>`)と、検索(`/help?q=<語>`)。
- いまのヘルプの節を、記事に移すこと。サービスの中の `/help#<id>` の形のリンクを、記事の URL に直すこと。
- このスコープで増えた機能の記事(下の受け入れ条件の表)。
- 迷いやすい画面からの、記事へのリンク。置けなかった理由と断った理由の場所からの、記事へのリンク。AI エージェントの道具が断るときの答えに入れる、記事の URL。
- 検索エンジンへの指定(入口、狙いの一覧、記事は載せる。検索の結果は載せない)。メンテナンス中も、ヘルプのすべてのページを読めること。
- `/help/bot` を、URL も内容も変えずに、「安全と規約」の一覧からリンクすること。

## 作らないこと

- 外部の検索サービス、クライアントの側の検索、helpdesk との連携。ヘルプチャット、問い合わせの履歴の管理。
- 記事を運営の画面から編集する仕組み。記事は、リポジトリのファイルである。
- 動画、画像つきの手引き。
- 規約に書いていないことを、記事に書くこと。規約の文面を、記事で言い換えて増やすこと。
- 外に貼られた古い `/help#<id>` のリンクを、対応する記事へ送ること。`/help` の入口に着く。

## 決めたこと

第四スコープを作るにあたり、次のように決めた(2026-11-26、第四スコープの指示書)。

- ページは 3 段にする。`/help`(入口)、`/help/<狙い>`(記事の一覧)、`/help/<狙い>/<記事>`(1 記事)。狙いは次の 8 つで、この順に並べる(D-45)。

  | 狙い | URL の名前 |
  | --- | --- |
  | はじめる | `start` |
  | スライドを置く・直す | `slides` |
  | 記事とリンクを添える | `articles` |
  | 読む・共有する | `sharing` |
  | つながる | `community` |
  | AI エージェント | `agent` |
  | アカウントとデータ | `account` |
  | 安全と規約 | `safety` |

- `/help/bot` は、URL を変えない。Luma の配信を読むときの User-Agent に書いてあるためである。「安全と規約」の一覧から、このページへリンクする([Luma の配信でコミュニティに紐づける](f33-luma-feeds.md))(D-46)。
- いまの `/help#<id>` の形のリンクは、サービスの中のものをすべて、対応する記事の URL に変える。外に貼られた古いリンクは `/help` の入口に着く。これは受け入れる(D-47)。
- 記事は、1 記事を 1 つのファイルにして、リポジトリに置く。上限や条件の数字は、いまのヘルプと同じように、コードの定数から差し込む。日本語と英語の両方を持つ(D-48)。
- 1 記事は、1 つの「したいこと」に答える。題名は「zip でスライドを置く」のように、したいことそのものにする。記事は次の順に書く。最初の 1 文で答えを言う。手順は番号つきの列にする。うまくいかないときの理由と対処を書く。末尾に、関係する記事と「解決しないときは問い合わせる」を置く。ボタンや見出しの文言は、画面と同じ言葉を使う(D-49)。
- 検索は `/help?q=<語>` で、サーバーの側で、記事の題名と本文を探す。索引はコードと一緒に作り、外部の検索サービスも、新しい script も使わない。日本語は、語に分けずに部分一致で探す。題名に合うものを、本文に合うものより上に出す。0 件のときは、狙いの一覧とお問い合わせへのリンクを出す(D-50)。
- ヘルプのページは、すべて検索エンジンに載せる(検索の結果のページを除く)(D-51)。
- 迷いやすい画面から、対応する記事へリンクする。設定の各枠、1 本の管理、コミュニティの編集、AI エージェントの接続、退会の確認、置けなかった理由と断った理由を出す場所が対象である(D-52)。
- helpdesk との連携は作らない(D-53)。
- メンテナンス中も、ヘルプのすべてのページは読める。ヘルプに「メンテナンス中です」の記事を置く(D-119、D-122)。
- 「安全と規約」に、禁止されていること、非表示にする基準、異議の申し立て方を書く。言葉は、利用規約の第 8 条と第 9 条に合わせる。規約の文面は下書きなので、記事の側は、条の番号ではなく条の題と位置(`id`)でリンクする。規約に書いていない基準を、記事で足さない(D-132)。
- 「預かっている情報と、その守り方」は、プライバシーポリシーと「外部への送信」へのリンクを中心にし、文面に書いてあることを言い換えて増やさない。メールアドレスの暗号化は、作らないと決めたので([メールアドレスを暗号化して持つ](f41-email-encryption.md)、2026-11-26)、記事に書かない。記事には、実際に行っていることだけを書く。
- 検索の語の長さの上限は、64 文字にした(作業 H1)。欄の `maxlength` も同じ値で、超えた語は 64 文字で切って探す。語は空白で分け、5 語までを、すべて含む記事を探す。英数字も文字も含まない語(記号だけ)には、合う記事が無い。
- 記事の URL の名前と、いまの節を移した先は、[ヘルプの枠の実装設計](../dev/f36-help-frame.md) の対応表のとおりである(作業 H1)。
- 画面の文言を引くときは、かぎ括弧で囲み、画面と同じ言葉にする。記事の題名は、実際の画面の文言に合わせて直してよい。保留になった作業の記事は書かず、どれを書かなかったかを PR に書く。
- 入口の狙いは、カードにせず、見出しとリンクの列で組む。検索の欄は、`<form method="get" action="/help">` と `<input type="search" name="q">` で、script なしで動く(05-UI-RULES.md)。
- このスコープより前の機能の文書にある「ヘルプの節」「ヘルプの項目」は、対応する記事のことである。ヘルプの節を指すリンクの書き方(`/help#article` など)は、記事を指す書き方に直した([発表を書き起こした記事を添える](f26-article.md) の F26-AC107、[URL を渡して読んでもらう](f03-sharing.md) の F03-AC181、F03-AC182、[Luma の配信でコミュニティに紐づける](f33-luma-feeds.md) の F33-AC21)。

公開前の読み直し([#672](https://github.com/piconic-ai/slide/issues/672))で、次のように決めた(2026-11-27)。

- ヘルプの新しい登録者の数(日数、本数)は、コードの既定の値(`parseNewAuthorLimits({})`)から取る。本番は `NEW_AUTHOR_LIMITS` を設定していないので、ヘルプは実際と合う。運営がその値を変えるときは、同じ変更で、ヘルプが数を取る元(`src/help/numbers.ts`)も変える(2026-11-27、#672 の 4)。
- ヘルプの検索で 0 件だった語の記録は、「預かっている情報と、その守り方」に書く。プライバシーポリシーの文面は、ここでは変えない(#65)。書くのは、記録の実際(50 文字まで、0 件だった語だけ、人を見分ける値が無い、元の記録は最大 3 か月、件数の集計は残る)だけである(2026-11-27、#672 の 6)。
- 運営に変えてもらえるのは、自分のハンドルと、自分が管理者のコミュニティのハンドルである([メールのコードでログインする](f28-email-login.md) の F28-AC113、[コミュニティをつくる](f30-communities.md) の F30-AC7)。ヘルプは、「自分では変えられない、運営に頼める」と言う(2026-11-27、#672 の 8)。
