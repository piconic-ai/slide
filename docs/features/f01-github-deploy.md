# F01 GitHub からスライドを更新する

状態は scope1 で実装済みです。実装する段階は [ストーリーマップ](../story-mapping.canvas) で確認できます。

## 利用場面

勉強会の前日、登壇者が GitHub の Markdown を修正する。ビルドとアップロードを手作業で繰り返すと、古い資料を公開しやすい。いつものブランチへ push し、Actions の結果からアップロードされた版を確認する。

## 得られる結果

手元で使っている作成ツールを変えずに、同じ手順で公開候補を用意できる。

## 体験の流れ

1. GitHub でログインし、スライドとリポジトリ、許可するブランチを関連付ける。
2. 作者が用意した Actions の手順で必要なビルドを済ませ、ビルド済みディレクトリをアップロードする。
3. ダッシュボードでコミット、検証結果、下書きの版を確認する。

## 作る範囲

- アップロード対象はビルド済みの HTML・JS・CSS・画像などの静的ファイルだけとする。
- Markdown などのビルド方法は作者が手元や CI で設定する。サービスと公式 Action はビルドを担当しない。
- 初期は本人のアカウントだけで利用し、ファイル数・容量・頻度は小さく制限する。上限は運用設定で後から変更できる。
- 一つのリポジトリから複数のスライドを明示的に指定する。
- 失敗理由と再試行の結果を確認できるデプロイ履歴。

## 作らないこと

- 未ビルドの Markdown を受け取ってサービス側でビルドすること。
- 公式 Action がビルドツールを選んだり、依存関係を導入したりすること。
- アップロードの成功を、利用者が選んでいない一般公開と同一視すること。

## 受け入れ条件

- 制作方法にかかわらず、完成した静的ディレクトリを同じアップロード手順で送れる。
- 許可された本人だけがアップロードでき、上限を超えた場合は理由を確認できる。
- アップロードの失敗や再送で、公開中の版が途中のファイルに置き換わらない。
- 許可されていないリポジトリや pull request から本番の公開状態を変えられない。
