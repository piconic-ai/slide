# F01 GitHub からスライドを更新する

状態は実装中です(scope1 の分は実装済み。招いた人が使えるようにする F01-AC5〜AC8 は、仕組みを実装済み。2 人目の登録はまだ)。実装する段階は [ストーリーマップ](../story-mapping.canvas) で確認できます。

## 利用場面

勉強会の前日、登壇者が GitHub の Markdown を修正する。ビルドとアップロードを手作業で繰り返すと、古い資料を公開しやすい。いつものブランチへ push し、Actions の結果からアップロードされた版を確認する。

## 得られる結果

手元で使っている作成ツールを変えずに、同じ手順で公開候補を用意できる。

## 体験の流れ

1. GitHub でログインし、スライドとリポジトリ、許可するブランチを関連付ける。
2. 作者が用意した Actions の手順で必要なビルドを済ませ、ビルド済みディレクトリをアップロードする。
3. ダッシュボードでコミット、検証結果、下書きの版を確認する。

## 作る範囲

- アップロード対象はビルド済みの HTML・JS・CSS・画像などの静的ファイルだけとする。
- Markdown などのビルド方法は作者が手元や CI で設定する。サービスと公式 Action はビルドを担当しない。
- 運営が登録した GitHub アカウントの人だけが利用する。ファイル数・容量・頻度は小さく制限する。上限は運用設定で後から変更できる。
- 一つのリポジトリから複数のスライドを明示的に指定する。
- 失敗理由と再試行の結果を確認できるデプロイ履歴。

## 作らないこと

- 未ビルドの Markdown を受け取ってサービス側でビルドすること。
- 公式 Action がビルドツールを選んだり、依存関係を導入したりすること。
- アップロードの成功を、利用者が選んでいない一般公開と同一視すること。
- 登録していない人のログインとアップロード。知らない人に開く前に済ませることが残っているためである([サービスの基本の備え](../dev/service-basics.md#知らない人に開く前に済ませること))。

## 受け入れ条件

- **F01-AC1** 制作方法にかかわらず、完成した静的ディレクトリを同じアップロード手順で送れる。
- **F01-AC2** 許可された本人だけがアップロードでき、上限を超えた場合は理由を確認できる。
- **F01-AC3** アップロードの失敗や再送で、公開中の版が途中のファイルに置き換わらない。
- **F01-AC4** 許可されていないリポジトリや pull request から本番の公開状態を変えられない。
- **F01-AC5** 運営が登録した GitHub アカウントの人は、ログインでき、自分のスライドをアップロード・公開・管理できる。
- **F01-AC6** 登録していない人がログインしようとすると、ログインできず、招待制であることが伝わる。
- **F01-AC7** 登録した人は、ほかの作者のスライドの管理画面、作者限定の表示、アップロード、公開の操作に届かない。
- **F01-AC8** 登録から外された人は、ログイン・アップロード・公開ができない。公開済みのスライドは残り、運営が 1 つずつ非表示にできる。

## 決めたこと

誰が使えるかについて、次のように決めた(2026-11-17)。

- 作者(運営を兼ねる)のほかに、作者が招いた人も、作者として使えるようにする。slide のコードを一緒に書く人が、自分のスライドも載せられるようにするためである。コードを書く権限は、GitHub のリポジトリ側で付ける。
- 招いた人は、GitHub の user ID を設定の一覧に登録する。一覧を変える PR は、誰に権限を与えるかを決める変更なので、作者が確かめてから merge する。
- 知らない人には、まだ開かない。開く時期と条件は決めていない。
- 招いた人を止めるときは、一覧から外す。アカウントの停止([知らない人のスライドも、安心して開ける](f17-safe-viewing.md))は、知らない人に開く前に作る。
